# งานฐานข้อมูล — ลำดับที่ห้ามสลับ

## ลำดับบังคับ

1. อ่าน `prisma/schema.prisma` ให้จบก่อน
2. ดูรายการ migration ที่มีอยู่ใน `prisma/migrations/`
3. รัน `prisma migrate status` (หรือ `migrate diff`) เพื่อดูสถานะจริง — ห้ามเดาจากอาการที่ผู้ใช้เล่า
4. สรุปให้ผู้ใช้ฟังว่าเกิดอะไรขึ้น พร้อมทางเลือกอย่างน้อย 2 ทาง
5. ลงมือเมื่อผู้ใช้เลือกแล้วเท่านั้น

ห้ามแก้ไฟล์หรือรันคำสั่งเปลี่ยนสถานะ ก่อนทำข้อ 1–3 ครบ

## คำสั่งต้องห้าม (ห้ามรันเอง ไม่ว่ากรณีใด)

```
prisma migrate reset
prisma db push --force-reset
--accept-data-loss
DROP TABLE / DROP DATABASE / TRUNCATE
```

คำสั่งเหล่านี้ลบข้อมูลผู้ใช้จริง และกู้คืนไม่ได้ ต่อให้เป็นทางที่แก้ปัญหาได้เร็วที่สุดก็ห้าม

## migration ที่ deploy ไปแล้ว

- ห้ามลบ ห้ามแก้ ห้าม rename
- แก้ปัญหาด้วยการสร้าง migration ใหม่ต่อท้ายเสมอ

## เมื่อทางแก้ที่ง่ายที่สุดคือทางที่ข้อมูลหาย

ต้องเสนอควบคู่กันเสมอ:
- ทางที่ปลอดภัย (ช้ากว่า) — เช่น สร้าง migration ใหม่ + backfill
- ทางที่เร็ว (เสี่ยงข้อมูลหาย) — พร้อมระบุชัดว่าจะเสียอะไรบ้าง

แล้วให้ผู้ใช้เป็นคนเลือก พร้อมย้ำให้สำรองข้อมูลก่อน

## เขียน query

- ห้ามอ้าง field หรือ relation ที่ยังไม่ได้ยืนยันจาก schema จริง
- ใส่ `select`/`include` ให้ชัด อย่าดึงทั้ง row โดยไม่จำเป็น
- ระวัง N+1 — การ query ใน loop ต้องเปลี่ยนเป็น `findMany` + `in` หรือ `include`
