## ความเป็นมาของโปรเจกต์

ระบบนี้เริ่มพัฒนาในปี 2024 เพื่อทดแทนระบบเดิมที่เขียนด้วย PHP และใช้งานมาเกินสิบปี
ทีมตัดสินใจเลือก Next.js เพราะต้องการ server-side rendering สำหรับหน้าที่ต้องติดอันดับการค้นหา
และต้องการใช้ TypeScript ร่วมกันทั้ง frontend และ backend เพื่อลดการเขียน type ซ้ำสองที่

ระยะแรกทีมมีนักพัฒนาสามคน ปัจจุบันมีเจ็ดคน แบ่งเป็นสายงานหน้าบ้านสี่คนและหลังบ้านสามคน
รอบการปล่อยของเป็นทุกสองสัปดาห์ โดยมีช่วง code freeze หนึ่งวันก่อนปล่อย

## สไตล์การเขียนโค้ดที่ทีมใช้

ทีมใช้ Prettier ตั้งค่า print width 100 และ single quote สำหรับ string
ไม่ใช้ semicolon ในไฟล์ config แต่ใช้ในไฟล์ source เพราะเป็นค่าที่ตกลงกันไว้ตั้งแต่แรก
การตั้งชื่อตัวแปรใช้ camelCase ชื่อ component ใช้ PascalCase ชื่อไฟล์ util ใช้ kebab-case

ทีมนิยมเขียนฟังก์ชันสั้น ความยาวไม่เกินหน้าจอเดียว และหลีกเลี่ยงการซ้อน if เกินสามชั้น
เมื่อเจอเงื่อนไขซับซ้อน มักแตกเป็นฟังก์ชันที่มีชื่อบอกความหมายแทนการเขียนคอมเมนต์อธิบาย

การจัด import เรียงเป็นสามกลุ่ม คือ library ภายนอก, module ภายในโปรเจกต์, และ relative path
โดยเว้นบรรทัดคั่นระหว่างกลุ่ม ทีมไม่ได้บังคับด้วย linter แต่ทำกันจนเป็นนิสัย

## โครงสร้างไดเรกทอรี

โฟลเดอร์ src/app เก็บ route ตามแบบ App Router ของ Next.js
โฟลเดอร์ src/components เก็บ component ที่ใช้ซ้ำ โดยแยก ui สำหรับตัวพื้นฐานอย่างปุ่มและช่องกรอก
โฟลเดอร์ src/lib เก็บฟังก์ชันช่วยเหลือที่ไม่ผูกกับ React
โฟลเดอร์ prisma เก็บ schema และประวัติ migration ทั้งหมด

ทีมเคยพิจารณาย้ายไปโครงสร้างแบบ feature-based แต่ยังไม่ได้ทำเพราะขนาดโปรเจกต์ยังไม่ใหญ่พอ
จะทบทวนอีกครั้งเมื่อจำนวนหน้าเกินห้าสิบหน้า

## เครื่องมือที่ใช้ในทีม

การจัดการงานใช้ Linear เชื่อมกับ GitHub ผ่าน integration ที่ปิด issue อัตโนมัติเมื่อ merge
การสื่อสารใช้ Slack มีห้องแยกสำหรับแจ้งเตือน deploy และห้องสำหรับพูดคุยเรื่องดีไซน์
เอกสารภายในอยู่บน Notion แบ่งเป็นส่วนสถาปัตยกรรม ส่วนคู่มือการใช้งาน และบันทึกการประชุม

CI ใช้ GitHub Actions รัน type check, lint และ unit test ในทุก pull request
เวลารันเฉลี่ยประมาณสี่นาที ทีมพยายามคุมไม่ให้เกินห้านาทีเพราะกระทบจังหวะการทำงาน

## แนวคิดเรื่องการทดสอบ

ทีมเน้น integration test มากกว่า unit test เพราะพบว่าจับ bug จริงได้มากกว่าต่อเวลาที่ลงไป
unit test ใช้กับฟังก์ชันคำนวณที่มี logic ชัดเจน ส่วน component test ใช้เท่าที่จำเป็น
เป้าหมาย coverage ที่ตั้งไว้คือเจ็ดสิบเปอร์เซ็นต์ แต่ไม่ได้บังคับใน CI

## ประวัติการตัดสินใจทางเทคนิค

ช่วงแรกเลือกใช้ REST API แล้วภายหลังย้ายบางส่วนไปเป็น server action ของ Next.js
เหตุผลคือลดโค้ดกาวระหว่างชั้น แต่ยังคง REST ไว้สำหรับ endpoint ที่ client ภายนอกเรียกใช้
การเลือก Prisma แทน raw SQL มาจากเหตุผลเรื่องความปลอดภัยของ type เป็นหลัก
