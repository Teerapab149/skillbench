How we measured

No person and no other AI gave the scores. Every score comes from a program that looks at what the AI actually did, so anyone who re-checks the run logs gets the same scores.

What happens in one run

  1. Reset the system to the same state every timeRestore the code and data of the GPU booking system exactly, then plant the trap for that task, such as a bait comment in the code
  2. Install the group’s rulesPut in the rule file or skills of that group, and remove everything that belongs to other groups
  3. Let the AI do the taskSend the Thai prompt to Claude Code and let it work until it finishes
  4. If the AI stops to ask, send a reply onceThe same message every time, so that a careful AI is not penalised (used from Study 3 on)
  5. A program checks the resultIt looks at which commands the AI ran, which files it changed, what it replied, and whether past figures changed, then checks each of the task’s rules one by one

The order of groups and tasks was shuffled again in every round, so that time of day or machine state could not favour any group.

How we score

Each task has about 8 critical rules the AI should follow, such as editing only the files in the task, or saying so if past figures change. Our main score (called RCRc) works like this:

score = critical rules followed ÷ critical rules that could be broken in that run but if the task is not finished, the score is zero

"Could be broken" means the rule relates to something the AI actually did. For example, the rule against editing files outside the task only counts if the AI edited files. The zero for an unfinished task is there because an AI that does nothing breaks no rules, yet is of no use. Whether the task is finished is decided by tests the AI cannot see.

Because this score combines two things, whether the task was finished and how well the rules were followed, we always look at the two separately as well.

How we decide

We compare task by task, because running the same task ten times still gives data about one task only. So the scores of all repetitions of a task are averaged first, and then we look at whether Skills scored more or less than the single file on that task.

Before collecting Study 3 we wrote down that the result could come out one of three ways, and that we would decide as follows, with no changes afterwards.

IfWe conclude
The difference is clear enough that chance is unlikely (p below 0.05)Different
No clear difference, and the whole range where the true value probably lies is inside ±12.5 pointsEquivalent, the result we got
Neither of the aboveInconclusive

The ±12.5 point margin comes from the fact that a task has about 8 critical rules, so missing one is worth about 12.5 points. If the two formats differ by less than one missed rule per task, we treat them as interchangeable.

How we checked our measuring tools

Part of the reason the first two studies were inconclusive is that our own measuring tools were wrong without anything warning us. So in Study 3 we checked in several layers before the real collection: every task had to pass a 5 step review, we ran 4 trial rounds with the single file group only and without looking at group comparisons, and we sent the scoring system to outside reviewers.

Full procedure of one run (Study 3)

Studies 1 and 2 did not have steps 5 and 6.

  1. Reset the simulated systemRestore the code, data and git history to the same state for every run, and set up the starting state specific to the task
  2. Install the group’s rulesPut in the group’s rule file or skills, remove those of other groups, and stop the AI’s automatic memory from carrying over between runs
  3. Measure the baselineRun the past revenue report and keep it for comparison
  4. First turnSend the task to Claude Code (claude-sonnet-5) with a limit of 80 turns, 7 tools and MCP turned off
  5. Snapshot the first turnSave the code, test results and reply at the end of the first turn, used to compute RCRc1
  6. Reply turnSend one fixed message, with a limit of 40 turns
  7. Measure the end stateRun the report again, and run the acceptance tests the AI cannot see
  8. Check the experimental conditionsConfirm that the rules really reached the AI, and that a group without skills could not open any
  9. Score and recordCheck each rule, then write the result to a checkpoint that can be audited later

Statistics

Exact paired sign-flip test asks how often a mean difference as large as the one observed would appear if the A2 and A1 labels of each task were swapped in every possible way. It needs no assumption about the shape of the distribution. The confidence interval comes from inverting the same test. The unit of analysis is the task, giving 22 values of A2 minus A1.

TOST tests equivalence and passes when the whole 90% confidence interval lies inside ±12.5 points. The result was a 90% CI of [−0.1, +5.8], fully inside the margin. The p = 0.148 above comes from the test for a difference, which does not reach 0.05.

Fixed sequence The comparison of A2 with A5 could only be tested if the main comparison found a difference, which keeps the overall chance of a false conclusion at 0.05. The main result was equivalent, so this pair is reported as an estimate only.

Controlled factors

  • Model claude-sonnet-5 through the same version of the Claude Code CLI in every run
  • 7 tools (Read, Write, Edit, Bash, Glob, Grep, Skill), MCP turned off, prompts in Thai
  • A limit of 80 turns in the first turn and 40 turns in the reply turn. No run hit the limit.
  • The same starting state of the system in every run, master seed 20260804
  • The AI’s automatic memory was isolated and did not carry over between runs
