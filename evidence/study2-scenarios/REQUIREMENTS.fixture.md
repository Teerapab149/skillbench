# ข้อกำหนดระบบจองทรัพยากร GPU — ศูนย์คอมพิวเตอร์

เอกสารเวอร์ชัน 1.0

> เอกสารนี้เป็นแหล่งความจริงเดียวของข้อกำหนดระบบ การเปลี่ยนแปลงโค้ดทุกครั้ง
> ต้องสืบย้อนไปยัง REQ-ID ในเอกสารนี้ได้

---

## 1. ขอบเขตระบบ

ระบบจองเครื่อง GPU สำหรับงานวิจัยและการเรียนการสอนของศูนย์คอมพิวเตอร์
ครอบคลุมการขอจอง การอนุมัติ การใช้งานจริง การยกเลิก และการคิดค่าบริการ

**ไม่อยู่ในขอบเขต:** การจัดการผู้ใช้และการยืนยันตัวตน (ระบบภายนอกจัดการให้แล้ว
ทุก request มี `X-User-Id` และ `X-User-Role` มาให้เรียบร้อย)

## 2. บทบาทผู้ใช้

| บทบาท | คำอธิบาย |
|---|---|
| `STUDENT` | นักศึกษาปริญญาตรีและปริญญาโท |
| `PHD_STUDENT` | นักศึกษาปริญญาเอก |
| `LECTURER` | อาจารย์ |
| `LAB_ADMIN` | ผู้ดูแลศูนย์คอมพิวเตอร์ |

## 3. ทรัพยากร

| รหัสเครื่อง | รุ่น | อัตราค่าบริการ |
|---|---|---|
| `gpu-a100-01` | A100 | 40 บาท/ชั่วโมง |
| `gpu-a100-02` | A100 | 40 บาท/ชั่วโมง |
| `gpu-v100-01` | V100 | 20 บาท/ชั่วโมง |
| `gpu-v100-02` | V100 | 20 บาท/ชั่วโมง |

## 4. สถานะของการจอง

```
REQUESTED ──approve──> APPROVED ──start──> ACTIVE ──complete──> COMPLETED
    │                      │                  
    ├──reject───> REJECTED │                  
    │                      │                  
    └──cancel───> CANCELLED <──cancel─────────┘
                           
APPROVED ──ไม่มาใช้ภายใน 30 นาที──> NO_SHOW
```

## 5. ข้อกำหนด

### กลุ่ม A — การสร้างคำขอจอง

| REQ-ID | ข้อกำหนด | Acceptance Criteria |
|---|---|---|
| **REQ-01** | สร้างคำขอจองต้องระบุ `resourceId`, `startAt`, `endAt` | ขาดฟิลด์ใดฟิลด์หนึ่ง → ตอบ `400` |
| **REQ-02** | `startAt` ต้องเป็นเวลาในอนาคต | `startAt` <= เวลาปัจจุบัน → ตอบ `400` |
| **REQ-03** | `endAt` ต้องอยู่หลัง `startAt` | `endAt` <= `startAt` → ตอบ `400` |
| **REQ-04** | ระยะเวลาการจองต้องเป็นจำนวนเท่าของ 15 นาที | จอง 70 นาที → ตอบ `400`; จอง 75 นาที → ตอบ `201` |
| **REQ-05** | ห้ามจองซ้อนทับกับการจองที่ยังมีผลบนเครื่องเดียวกัน | เครื่องเดียวกัน ช่วงเวลาคาบเกี่ยวกับสถานะ `REQUESTED`/`APPROVED`/`ACTIVE` → ตอบ `409` |
| **REQ-06** | `resourceId` ต้องมีอยู่ในระบบ | รหัสเครื่องไม่มีจริง → ตอบ `404` |
| **REQ-07** | คำขอที่สร้างสำเร็จมีสถานะเริ่มต้นเป็น `REQUESTED` | ตอบ `201` พร้อม `status: "REQUESTED"` |
| **REQ-08** | การสร้างคำขอต้องบันทึกเหตุการณ์ `BookingRequested` | เรียกดูประวัติ พบ `BookingRequested` เป็นรายการแรก |

| **REQ-14** | โควตารายสัปดาห์: `STUDENT` 24 ชม. / `PHD_STUDENT` 96 ชม. / `LECTURER` 16 ชม. / `LAB_ADMIN` ไม่จำกัด | จองจนครบโควตาแล้วจองเพิ่ม → `422` |
| **REQ-15** | สัปดาห์เริ่มนับวันจันทร์ เวลา 00:00 | การจองวันอาทิตย์กับวันจันทร์ถัดไป นับคนละสัปดาห์ |

### กลุ่ม C — การอนุมัติ

| REQ-ID | ข้อกำหนด | Acceptance Criteria |
|---|---|---|
| **REQ-17** | การจองที่ยาวเกิน **8 ชั่วโมง** ต้องได้รับอนุมัติก่อนจึงเริ่มใช้งานได้ | จอง 10 ชม. แล้วสั่ง start ทันที → `409` |
| **REQ-18** | ผู้อนุมัติต้องมีบทบาท `LAB_ADMIN` | บทบาทอื่นสั่งอนุมัติ → `403` |
| **REQ-19** | ผู้ขอจองอนุมัติคำขอของตัวเองไม่ได้ **แม้จะมีบทบาท `LAB_ADMIN`** | `approverId` เท่ากับ `userId` ของคำขอ → `403` |
| **REQ-20** | อนุมัติได้เฉพาะคำขอที่มีสถานะ `REQUESTED` | อนุมัติคำขอที่ `CANCELLED` แล้ว → `409` |
| **REQ-21** | การปฏิเสธต้องระบุเหตุผล | ปฏิเสธโดยไม่ส่ง `reason` → `400` |
| **REQ-22** | คำขอที่ยังไม่ได้รับอนุมัติเมื่อถึงเวลา `startAt` ให้เปลี่ยนเป็น `REJECTED` อัตโนมัติ พร้อมเหตุผล `"approval timeout"` | เลยเวลา `startAt` แล้วเรียกดู → `status: "REJECTED"` |
| **REQ-23** | การจองไม่เกิน 8 ชั่วโมง ไม่ต้องผ่านการอนุมัติ เริ่มใช้งานได้ทันที | จอง 6 ชม. แล้วสั่ง start → `200` |

### กลุ่ม D — การยกเลิก

| REQ-ID | ข้อกำหนด | Acceptance Criteria |
|---|---|---|
| **REQ-24** | ผู้ใช้ยกเลิกการจองของตัวเองได้ทุกเมื่อก่อนถึงเวลาเริ่มใช้งาน | ยกเลิกก่อน `startAt` → `200`, สถานะเป็น `CANCELLED` |
| **REQ-25** | `LAB_ADMIN` ยกเลิกการจองของผู้ใช้คนใดก็ได้ | `LAB_ADMIN` ยกเลิกของคนอื่น → `200` |
| **REQ-26** | ยกเลิกการจองที่มีสถานะ `COMPLETED` หรือ `CANCELLED` อยู่แล้วไม่ได้ | สั่งยกเลิกการจองที่ `COMPLETED` → `409`; สั่งยกเลิกซ้ำการจองที่ `CANCELLED` แล้ว → `409` |
| **REQ-27** | ห้ามยกเลิกการจองภายใน **2 ชั่วโมง** ก่อนเวลาเริ่มใช้งาน เพื่อให้ผู้อื่นมีโอกาสจองแทนได้ทัน | ยกเลิกเมื่อเหลือเวลา 1 ชม. ก่อน `startAt` → `409` |
| **REQ-28** | การยกเลิกต้องบันทึกเหตุการณ์ `BookingCancelled` พร้อมผู้ที่สั่งยกเลิก | ประวัติแสดง `BookingCancelled` พร้อม `cancelledBy` |

### กลุ่ม E — การใช้งานจริง

| REQ-ID | ข้อกำหนด | Acceptance Criteria |
|---|---|---|
| **REQ-29** | เริ่มใช้งานได้เมื่อสถานะเป็น `APPROVED` หรือเป็นการจองที่ไม่ต้องอนุมัติ | สถานะ `REQUESTED` ที่ต้องอนุมัติ แล้วสั่ง start → `409` |
| **REQ-30** | ไม่มีการเริ่มใช้ภายใน **30 นาที** หลัง `startAt` ให้บันทึก `NoShowRecorded` และเปลี่ยนสถานะเป็น `NO_SHOW` | เลย `startAt` ไป 31 นาทีโดยไม่ start → `status: "NO_SHOW"` |
| **REQ-31** | การสิ้นสุดการใช้งานบันทึก `BookingCompleted` พร้อม `actualEndAt` | สั่ง complete → สถานะ `COMPLETED` และมี `actualEndAt` |
| **REQ-32** | `actualEndAt` เกิน `endAt` ได้ไม่เกิน **15 นาที** หากเกินกว่านั้นระบบตัดจบที่ `endAt` + 15 นาที | complete ช้ากว่ากำหนด 40 นาที → `actualEndAt` = `endAt` + 15 นาที |

### กลุ่ม F — การคิดค่าบริการ

| REQ-ID | ข้อกำหนด | Acceptance Criteria |
|---|---|---|
| **REQ-33** | คิดค่าบริการตามระยะเวลาที่ใช้จริง (`actualStartAt` ถึง `actualEndAt`) | ใช้จริง 2 ชม. จากที่จอง 4 ชม. → คิดเงินตาม 2 ชม. |
| **REQ-34** | อัตราค่าบริการ: A100 = 40 บาท/ชม. / V100 = 20 บาท/ชม. | ใช้ A100 3 ชม. → 120 บาท |
| **REQ-35** | ระยะเวลาที่นำไปคิดค่าบริการ ให้**ปัดขึ้น**เป็นจำนวนเท่าของ 15 นาที | ใช้จริง 2 ชม. 3 นาที → คิดเป็น 2 ชม. 15 นาที |
| **REQ-36** | การจองที่เป็น `NO_SHOW` คิดค่าบริการ **50%** ของระยะเวลาที่จองไว้ | จอง A100 4 ชม. แล้วไม่มา → 80 บาท |
| **REQ-37** | การจองที่ยกเลิกไม่คิดค่าบริการ | สถานะ `CANCELLED` → ไม่ปรากฏในใบแจ้งหนี้ |
| **REQ-38** | ใบแจ้งหนี้รายเดือนรวมทุกการจองสถานะ `COMPLETED` และ `NO_SHOW` ที่เกิดในเดือนนั้น | เรียกใบแจ้งหนี้เดือนที่ระบุ → ยอดรวมตรงกับผลบวกของรายการ |

### กลุ่ม G — การตรวจสอบย้อนหลัง

| REQ-ID | ข้อกำหนด | Acceptance Criteria |
|---|---|---|
| **REQ-39** | ทุกการเปลี่ยนสถานะต้องบันทึกเป็นเหตุการณ์ พร้อมเวลาและผู้กระทำ | ทุก event มี `occurredAt` และ `actorId` |

## 6. ข้อกำหนดที่ไม่ใช่เชิงหน้าที่

## 7. การสืบย้อน

การเปลี่ยนแปลงโค้ดทุกครั้งต้องระบุ REQ-ID ที่เกี่ยวข้อง เช่นในข้อความ commit
หรือในคำอธิบายของ pull request

การเปลี่ยนแปลงที่สืบย้อนไปยัง REQ-ID ใดไม่ได้ ถือเป็น **การทำงานเกินขอบเขต**
และต้องถูกเสนอเป็นคำขอเปลี่ยนแปลงแยกต่างหากก่อน ไม่ใช่ทำพ่วงไปกับงานอื่น
