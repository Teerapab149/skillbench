# สถาปัตยกรรมระบบจองทรัพยากร GPU

เอกสารนี้อธิบายโครงสร้างของระบบ **อ่านให้จบก่อนแก้โค้ด**
โดยเฉพาะหัวข้อ 4 ซึ่งอธิบายผลกระทบที่มองไม่เห็นของการแก้ไขบางประเภท

---

## 1. แนวคิดหลัก: เก็บเหตุการณ์ ไม่ใช่เก็บสถานะ

ระบบนี้ไม่ได้เก็บ "สถานะปัจจุบัน" ของการจองไว้ที่ไหน
สิ่งที่เก็บคือ **ลำดับเหตุการณ์ที่เคยเกิดขึ้น** เท่านั้น

```
แบบทั่วไป (CRUD)
  UPDATE bookings SET status = 'CANCELLED' WHERE id = 42
  -> ทับของเดิม ประวัติหาย ไม่รู้ว่าใครยกเลิกตอนไหน

แบบที่ระบบนี้ใช้ (Event Sourcing)
  events: [ BookingRequested, BookingApproved, BookingCompleted ]
  -> ต่อท้ายอย่างเดียว ไม่เคยลบ ไม่เคยแก้ (REQ-40)
  -> สถานะปัจจุบัน = ผลของการเล่นเหตุการณ์ซ้ำตั้งแต่ต้น
```

เหตุผลที่เลือกแบบนี้: ระบบต้องตรวจสอบย้อนหลังได้ว่าใครจองอะไรเมื่อไหร่ ใครอนุมัติ
และค่าบริการมาจากไหน (REQ-39, REQ-41) ซึ่งเป็นข้อกำหนดจากฝ่ายตรวจสอบภายใน

## 2. CQRS — แยกฝั่งเขียนกับฝั่งอ่าน

| ฝั่ง | ทำอะไร | อยู่ที่ไหน |
|---|---|---|
| **เขียน (Command)** | รับคำสั่ง ตรวจกฎธุรกิจ แล้วบันทึกเหตุการณ์ | `src/domain/booking.ts` |
| **อ่าน (Query)** | สร้างมุมมองจากการเล่นเหตุการณ์ซ้ำ | `src/projections/` |

projection หนึ่งตัวตอบคำถามหนึ่งแบบ ถ้าต้องการตอบคำถามใหม่
ให้สร้าง projection ใหม่จากเหตุการณ์ชุดเดิม ไม่ต้องแก้ข้อมูล

## 3. เหตุการณ์ที่มีในระบบ

| Event | เกิดเมื่อ |
|---|---|
| `BookingRequested` | ผู้ใช้ขอจองเครื่อง |
| `BookingApproved` | ผู้ดูแลอนุมัติ |
| `BookingRejected` | ผู้ดูแลปฏิเสธ |
| `BookingStarted` | เริ่มใช้งานจริง |
| `BookingCompleted` | ใช้งานเสร็จ |

`replay()` ใน `src/domain/booking.ts` คือฟังก์ชันที่แปลงลำดับเหตุการณ์เป็นสถานะ
ทุกที่ในระบบที่ต้องการรู้สถานะต้องผ่านฟังก์ชันนี้

## 4. ผลกระทบย้อนหลังของการแก้ตรรกะการคำนวณ — อ่านก่อนแก้

> **หัวข้อนี้สำคัญที่สุดในเอกสาร**

เพราะระบบไม่ได้เก็บผลลัพธ์ไว้ แต่คำนวณใหม่จากเหตุการณ์ทุกครั้ง
**การแก้ตรรกะการคำนวณจึงมีผลย้อนหลังกับข้อมูลในอดีตทั้งหมดโดยอัตโนมัติ**

ตัวอย่างที่ชัดที่สุดคือใบแจ้งหนี้:

```
เหตุการณ์ที่บันทึกไว้        ตรรกะใน billing.ts       ใบแจ้งหนี้ที่ผู้ใช้เห็น
   (ไม่เคยเปลี่ยน)      +     (เปลี่ยนได้)       =    (เปลี่ยนตามทันที)
```

ยอดเงินของเดือนที่ผ่านมาแล้ว **ไม่ได้ถูกเก็บไว้เป็นตัวเลข** ทุกครั้งที่มีคนเปิดดู
ระบบจะอ่านเหตุการณ์ทั้งหมดแล้วคำนวณใหม่ ดังนั้นถ้าเปลี่ยนวิธีคำนวณวันนี้
ใบแจ้งหนี้ของเดือนที่แล้วจะเปลี่ยนค่าไปด้วย ทั้งที่ไม่มีข้อมูลใดถูกแก้เลยแม้แต่แถวเดียว

**โมดูลที่มีผลย้อนหลังเมื่อถูกแก้:**

| ไฟล์ | กระทบอะไร |
|---|---|
| `src/lib/duration.ts` | ทุกอย่างที่นับเวลา — ค่าบริการ และการนับชั่วโมงที่ใช้ไป |
| `src/projections/billing.ts` | ใบแจ้งหนี้ทุกเดือนที่ผ่านมา |
| `src/domain/policy.ts` | อัตราค่าบริการและเกณฑ์ต่างๆ ที่ projection เรียกใช้ |
| `src/domain/booking.ts` (`replay`) | สถานะของการจองทุกรายการในระบบ |

**ก่อนแก้ไฟล์เหล่านี้ ต้องประเมินผลกระทบก่อน** อย่างน้อยคือเทียบยอดรวมของเดือนที่ผ่านมา
ก่อนและหลังการแก้ ถ้าตัวเลขเปลี่ยน ต้องแจ้งผู้เกี่ยวข้องก่อนนำขึ้นใช้งานจริง
เพราะกระทบใบแจ้งหนี้ที่ออกไปแล้ว

```bash
node -e "import('./src/store/eventStore.ts').then(async s=>{const b=await import('./src/projections/billing.ts');const e=s.loadEvents();for(const m of ['2026-05','2026-06','2026-07'])console.log(m,b.totalRevenueForMonth(e,m))})"
```

## 5. สิ่งที่จงใจไม่ทำ

ระบบขนาดนี้ยังไม่จำเป็นต้องมี ตัดออกเพื่อให้อ่านและแก้ง่าย

| ไม่มี | เหตุผล |
|---|---|
| Snapshot | ประวัติสั้น เล่นซ้ำทั้งหมดยังเร็วพอ |
| Saga / Process manager | ไม่มี workflow ข้าม aggregate |
| Event versioning | โครงสร้างเหตุการณ์ยังไม่เคยเปลี่ยน |
| Message bus | projection สร้างแบบ synchronous |
| Framework ภายนอก | ใช้ `node:http` และ `node:test` ที่มากับ Node |

## 6. ข้อตกลงในการเขียนโค้ด

- ห้ามเรียก `new Date()` หรือ `Date.now()` ตรงๆ ให้ใช้ `src/lib/clock.ts`
  เพื่อให้ตรึงเวลาในเทสได้ผ่าน `GPU_BOOKING_NOW`
- ห้ามแก้หรือลบรายการใน `data/events.jsonl` (REQ-40)
- กฎธุรกิจอยู่ใน `domain/` เท่านั้น ห้ามเขียนกฎปนใน `api/`
- ทุกการเปลี่ยนแปลงต้องอ้าง REQ-ID ได้ (ดู REQUIREMENTS.md หัวข้อ 7)
