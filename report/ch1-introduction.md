## 1.1 ความเป็นมาและความสำคัญของปัญหา

โมเดลภาษาขนาดใหญ่ที่ทำงานในรูปแบบเอเจนต์ (agentic LLM) ถูกนำมาใช้เขียนและแก้ไขโค้ดจริง
ในงานพัฒนาซอฟต์แวร์อย่างแพร่หลาย แต่คุณสมบัติหนึ่งที่ติดมากับโมเดลเหล่านี้คือ
**ความไม่คงเส้นคงวา (stochasticity)** — สั่งงานเดียวกันหลายครั้ง ได้ผลลัพธ์ไม่เหมือนกัน
แม้จะตั้งค่าให้สุ่มน้อยที่สุดแล้วก็ตาม

ในบริบทของการเขียนโค้ด ความไม่คงเส้นคงวานี้ปรากฏเป็นสองอาการที่ทีมพัฒนารับไม่ได้:

1. **การทำงานเกินขอบเขต** — เอเจนต์แก้ปัญหาที่สั่งสำเร็จ แต่ไปแก้ไฟล์อื่นที่ไม่ได้สั่งพ่วงไปด้วย
   ปรับโครงสร้างโค้ดที่ไม่เกี่ยวข้อง หรือแก้เอกสารข้อกำหนดเพื่อให้ข้อกำหนดเข้ากับสิ่งที่ตนทำ
2. **การตัดสินใจที่ไม่เสถียร** — เมื่อข้อกำหนดคลุมเครือหรือขัดกัน เอเจนต์เลือกทางหนึ่งในรอบนี้
   และเลือกอีกทางในรอบถัดไป โดยที่โจทย์ไม่ได้เปลี่ยน

แนวทางที่อุตสาหกรรมใช้รับมือคือ **context engineering** — การเขียนกฎและข้อกำหนดลงไฟล์
ให้เอเจนต์อ่านก่อนลงมือทำงาน รูปแบบที่พบบ่อยที่สุดคือไฟล์กฎไฟล์เดียวที่ถูกโหลดเข้า context
ตลอดเวลา (เช่น `CLAUDE.md`) และรูปแบบที่ใหม่กว่าคือ **Agent Skills** ซึ่งแยกกฎออกเป็นหน่วยย่อย
แล้วโหลดเฉพาะหน่วยที่คำอธิบายตรงกับงานที่กำลังทำ ตามแนวคิด *progressive disclosure*

**ปัญหาคือยังไม่มีการวัดเชิงประจักษ์ว่าการจัดวางกฎแต่ละแบบให้ผลต่างกันแค่ไหน**
ความรู้ที่หมุนเวียนอยู่ในวงการส่วนใหญ่เป็นประสบการณ์ส่วนบุคคลในรูป *"ใส่แล้วรู้สึกว่าดีขึ้น"*
ซึ่งแยกไม่ออกว่าผลที่เห็นมาจาก **เนื้อหาของกฎ** มาจาก **ปริมาณข้อความที่เพิ่มเข้าไปใน context**
หรือมาจาก **โครงสร้างและจังหวะที่กฎถูกโหลด**

การแยกสามอย่างนี้ออกจากกันต้องอาศัยการออกแบบการทดลองที่มีกลุ่มควบคุมที่เหมาะสม
ซึ่งเป็นสิ่งที่งานวิจัยที่ผ่านมายังไม่ได้ทำ (รายละเอียดในบทที่ 2)

## 1.2 คำถามวิจัย

> **การจัดวางกฎแบบ "โหลดตลอดเวลา" กับ "โหลดเมื่อเข้าเงื่อนไข" ให้ผลต่างกันเท่าไร
> ในเชิงอัตราการปฏิบัติตามข้อกำหนด ความสม่ำเสมอของการตัดสินใจ และต้นทุน token
> เมื่อควบคุมเนื้อหาของกฎให้เหมือนกันทุกข้อ**

เงื่อนไข *"เมื่อเนื้อหากฎเหมือนกันทุกข้อ"* คือสิ่งที่ทำให้คำถามนี้ต่างจากคำถามที่ถามกันทั่วไป
คำถามแบบ *"ใส่กฎแล้วดีขึ้นไหม"* ตอบได้ง่ายและได้ประโยชน์น้อย เพราะไม่มีใครสงสัยว่า
การบอกกฎย่อมดีกว่าไม่บอก สิ่งที่ยังไม่มีคำตอบคือ **เมื่อกฎเท่ากันแล้ว วิธีจัดวางมันสำคัญแค่ไหน**

### ข้อเสนอหลักที่นำไปทดสอบ

> **รูปแบบของกฎ (form) ทำนายอัตราการปฏิบัติตามได้ดีกว่าเนื้อหาของกฎ (content)
> และดีกว่าปริมาณ context**

ข้อความนี้เป็น **ข้อเสนอที่นำไปทดสอบ ไม่ใช่ข้อสรุปที่ตั้งไว้ล่วงหน้า** แตกได้เป็นสามข้อย่อย:

1. กฎที่มีรูปเป็น **ลำดับขั้นตอน ข้อห้าม หรือขอบเขตเชิงตัวเลข** มีอัตราการปฏิบัติตามสูง
2. กฎที่มีรูปเป็น **ค่านิยมหรือวิจารณญาณ** (เช่น "เขียนโค้ดให้สะอาด") วัดและบังคับใช้ได้ยากกว่า
3. ผลของ**จำนวนกฎที่โหลดพร้อมกัน** เป็นคำถามสำหรับงานต่อยอด ชุดข้อมูลหลักของงานนี้
   ไม่ได้เก็บเส้นโค้ง dilution

#### สถานะของข้อเสนอนี้หลังเก็บข้อมูลจริง *(เพิ่ม 20 ก.ย. 2569)*

**ข้อเสนอหลักข้างต้นไม่ได้รับการยืนยัน และสองในสามข้อย่อยทดสอบไม่ได้เลย**
รายละเอียดเต็มอยู่ในบทที่ 6 หัวข้อ 6.1.1 สรุปสั้นที่นี่เพื่อให้คำนำกับบทสรุปตรงกัน

| ข้อย่อย | สถานะ |
|---|---|
| 1 · กฎรูปลำดับ ข้อห้าม ขอบเขตเชิงตัวเลข ปฏิบัติตามสูง | **ทดสอบไม่ได้** เพราะไม่มีกฎอีกฝั่งมาเทียบ |
| 2 · กฎรูปค่านิยมวัดและบังคับใช้ได้ยากกว่า | **ทดสอบไม่ได้** — ไม่มีกฎรูปค่านิยมในเครื่องมือวัดเลยสักข้อ |
| 3 · จำนวนกฎที่โหลดพร้อมกัน | ประกาศไว้แต่ต้นว่าเป็นงานต่อยอด · ยังไม่ได้เก็บข้อมูลจริง |

เหตุผลที่ข้อ 1 และ 2 ทดสอบไม่ได้ **ไม่ได้อยู่ที่ข้อมูล แต่อยู่ที่ข้อบังคับที่งานนี้ตั้งเอง**
วัตถุประสงค์ข้อ 1 ในหัวข้อ 1.3 กำหนดว่าตัวตรวจทุกตัวต้องเป็นโปรแกรมที่ตัดสินแบบ
deterministic ห้ามใช้คนหรือ LLM กฎอย่าง "เขียนโค้ดให้สะอาด" จึงแปลงเป็นตัวตรวจ
แบบนั้นไม่ได้โดยไม่เปลี่ยนความหมาย ผลคือเมื่อสร้างโจทย์เสร็จ **กฎทั้ง 137 ช่อง
ล้วนเป็นกฎที่ชี้ขาดได้ ไม่มีกฎรูปค่านิยมเหลืออยู่เลย**

> **ข้อบังคับที่ทำให้ตัวเลขทั้งเล่มเชื่อถือได้ คือข้อเดียวกับที่ทำให้ข้อเสนอหลักทดสอบไม่ได้**

นี่ไม่ใช่ข้อบกพร่องที่แก้ได้ด้วยการเก็บข้อมูลเพิ่ม แต่เป็นการแลกที่ต้องยอมรับ
และงานนี้นับเป็นข้อค้นพบเชิงระเบียบวิธีข้อหนึ่ง

**สิ่งที่ทดสอบได้จริงคือคำถามวิจัยในกรอบสีเทาด้านบน** คือเปรียบเทียบการจัดวางกฎ
สองแบบเมื่อเนื้อหาเท่ากัน ซึ่งเก็บข้อมูลครบสองชุดและ **สรุปไม่ได้ทั้งสองครั้ง**

### คำถามนี้ตอบทางไหนก็มีค่า

| ถ้าผลออกมาว่า | ข้อสรุปที่รายงานได้ |
|---|---|
| การโหลดตามเงื่อนไขให้ผลดีกว่า | จังหวะการโหลดสำคัญกว่าปริมาณข้อมูลที่ใส่เข้าไป |
| ไม่ต่างกันอย่างมีนัยสำคัญ | ต้นทุนความยุ่งยากของการแยกเป็น skill อาจไม่คุ้ม — แต่ต้องอ่านคู่กับข้อจำกัดด้าน power ในหัวข้อ 1.5 |
| การโหลดตลอดเวลาให้ผลดีกว่า | ขัดกับความเชื่อที่แพร่หลาย และต้องอธิบายกลไก |

**สิ่งที่เกิดขึ้นจริงคือกรณีที่ตารางนี้ไม่ได้เตรียมไว้** — ผลต่างเป็นบวกในทิศทางของ
การโหลดตามเงื่อนไขทั้งสองชุด แต่ช่วงความเชื่อมั่นคร่อมศูนย์ทั้งคู่ จึง**สรุปไม่ได้**
ซึ่งไม่ใช่แถวที่สองของตาราง เพราะแถวนั้นเขียนว่า "ไม่ต่างกันอย่างมีนัยสำคัญ"
ซึ่งเป็นข้อความที่ข้อมูลชุดนี้ไม่มีสิทธิ์พูด

การออกแบบนี้ตั้งใจให้ไม่มีสถานการณ์ที่ *"ผลไม่สวยจึงไม่มีอะไรจะรายงาน"*
อย่างไรก็ตาม **ผลที่ไม่ถึงนัยสำคัญต้องรายงานว่า "สรุปไม่ได้" ไม่ใช่ "ไม่ต่างกัน"** เสมอ
ด้วยเหตุผลที่อธิบายในหัวข้อ 1.5

## 1.3 วัตถุประสงค์ของการวิจัย

1. **สร้างระบบวัดผลที่ตรวจการปฏิบัติตามข้อกำหนดจากร่องรอยการกระทำจริง**
   ไม่ใช่จากข้อความที่เอเจนต์เขียนตอบ โดยตัวตรวจทุกตัวต้องเป็นโปรแกรมที่ตัดสินแบบ
   deterministic และห้ามใช้คนหรือ LLM ตัดสิน
2. **วัดผลของโครงสร้างการจัดวางกฎ โดยควบคุมเนื้อหาของกฎและปริมาณ context**
   ด้วยการออกแบบกลุ่มทดลองที่มีทั้งกลุ่มควบคุมเชิงกฎและกลุ่มควบคุมเชิงความยาว
3. **วัดความสม่ำเสมอของการตัดสินใจข้ามการทำซ้ำ** ด้วยการรันโจทย์เดิมหลายรอบ
   แล้วรายงานทั้งค่าเฉลี่ยและสัดส่วนโจทย์ที่ผ่านครบทุกรอบ
4. **วัดต้นทุน token ของแต่ละรูปแบบการจัดวางกฎ** เพื่อให้ข้อสรุปเชิงประสิทธิผล
   อ่านคู่กับต้นทุนได้
5. **เสนอแนวทางการเขียนกฎสำหรับเอเจนต์** ที่อ้างอิงจากผลการวัด ไม่ใช่จากประสบการณ์ส่วนบุคคล

## 1.4 สมมติฐานการวิจัย

สมมติฐานทั้งหมดถูกประกาศไว้ล่วงหน้าใน `PRE-REGISTRATION.md` พร้อมวันที่
**ก่อนเก็บข้อมูลเปรียบเทียบแม้แต่ run เดียว** และต้องรายงานผลไม่ว่าผลจะออกทางใด

### ลำดับชั้นของ endpoint

ลำดับชั้นนี้ประกาศไว้ล่วงหน้าเพื่อไม่ให้เกิดการเลือกตัวชี้วัดหลังเห็นข้อมูล

| ระดับ | ตัวชี้วัด | การเปรียบเทียบ | สถิติ |
|---|---|---|---|
| **Primary** | `CRIT` — ผ่านกฎวิกฤตครบทุกข้อในหนึ่ง run | A2 เทียบ A1 | exact paired sign-flip ที่ระดับโจทย์ + cluster bootstrap CI |
| **Co-primary (gated)** | `RCR` — สัดส่วนกฎที่ผ่านต่อ run | A2 เทียบ A1 | ทดสอบต่อเมื่อ primary ผ่านประตู |
| **Key secondary** | `pass^k` — สัดส่วนโจทย์ที่ผ่านครบทุกรอบ | ทุกกลุ่ม | Wilson CI ระดับโจทย์ |
| **Secondary** | `FULL` · `SCOPE` · `TASK` · Trigger F1 · ต้นทุน token | ตามที่ประกาศ | ตามที่ประกาศ |

### สมมติฐานเชิงเนื้อหา

- **H1** กฎรูปลำดับ ข้อห้าม และขอบเขตเชิงตัวเลข มีอัตราการปฏิบัติตามสูงกว่ากฎรูปค่านิยม
- **H2** โครงสร้างการจัดวางกฎมีผลต่อการปฏิบัติตาม เมื่อควบคุมเนื้อหาและความยาวแล้ว
- **H3** ผลของจำนวนกฎที่โหลดพร้อมกัน (rule dilution) — **ไม่อยู่ในชุดข้อมูลหลัก**
  ออกแบบและตรวจด้วย mock adapter แล้ว แต่ยังไม่ได้เก็บข้อมูลจริง จัดเป็นงานต่อยอด
- **H4** กลุ่มที่มีกฎ (A1, A2) ใช้ token รวมต่องานน้อยกว่ากลุ่มที่ไม่มีกฎ (A0)
  โดยกลไกที่เสนอคือ เอเจนต์ที่ไม่มีขอบเขตต้องสำรวจ repository เองว่าต้องแก้ตรงไหน
  และทุก turn ที่สำรวจเพิ่มคือ context ที่ถูกอ่านซ้ำใน turn ถัดไป

**สถานะของสมมติฐานทั้งสี่หลังเก็บข้อมูลครบ** *(เพิ่ม 20 ก.ย. 2569 · รายละเอียดในบทที่ 6 หัวข้อ 6.1.1)*

| | สถานะ |
|---|---|
| H1 | **ทดสอบไม่ได้** — ไม่มีกฎรูปค่านิยมในเครื่องมือวัด |
| H2 | **สรุปไม่ได้** ทั้งสองชุด — ผลต่างเป็นบวกแต่ช่วงความเชื่อมั่นคร่อมศูนย์ |
| H3 | **ไม่ได้เก็บข้อมูลจริง** ตามที่ประกาศไว้แต่ต้น |
| H4 | **ไม่สนับสนุน** — กลุ่มไฟล์เดียวใช้ token น้อยกว่าจริง แต่กลุ่ม skill ใช้มากกว่ากลุ่มที่ไม่มีกฎ |

**ลำดับชั้นของ endpoint ข้างต้นเป็นของชุดที่ 1** ชุดที่ 2 ประกาศลำดับชั้นใหม่ไว้ใน
`PRE-REGISTRATION-2.md` โดยเปลี่ยนตัวชี้วัดหลักเป็น `RCRc` **หลังเห็นผลของชุดที่ 1 แล้ว**

## 1.5 ขอบเขตและข้อจำกัดของการวิจัย

ข้อจำกัดในหัวข้อนี้เขียนไว้ล่วงหน้า **ไม่ใช่คำอธิบายที่เพิ่มเข้ามาหลังเห็นผล**

### ขอบเขต

- **โมเดลเดียว รุ่นเดียว** — `claude-sonnet-5` ล็อกไว้ตั้งแต่ก่อนเก็บข้อมูล (Amendment 2.1)
  ผลที่ได้ผูกกับโมเดลรุ่นนี้และช่วงเวลาที่เก็บ ไม่อ้างว่าเป็นสมบัติทั่วไปของ LLM ทุกตัว
- **ระบบจำลองหนึ่งระบบ** — ระบบจองทรัพยากร GPU ที่สร้างขึ้นเพื่อการทดลองโดยเฉพาะ
  ใช้สถาปัตยกรรม Event Sourcing และ CQRS ไม่ใช่ระบบ production จริง
- **11 โจทย์** ครอบคลุมกับดัก 5 ตระกูล ซึ่งเป็นจำนวนที่กำหนดเพดานของกำลังการทดสอบ
- **เพดาน 80 turn ต่อ run** — run ที่ใช้ turn จนหมดงบถือเป็นพฤติกรรมของเอเจนต์
  และถูกนับเข้าผลหลัก (Amendment 15) คะแนนของ run เหล่านั้นสะท้อนสิ่งที่ทำได้ภายในงบ
  **ไม่ใช่ความสามารถสูงสุดของกลุ่มนั้น**

### ข้อจำกัดเชิงระเบียบวิธีที่รู้ตัวและควบคุมไว้

| ข้อจำกัด | ผลกระทบ | สิ่งที่ทำเพื่อควบคุม |
|---|---|---|
| **ผู้วิจัยเขียนกฎเองและให้คะแนนกฎของตัวเอง** | ความลำเอียง | ประกาศชุดกฎและแผนวิเคราะห์ล่วงหน้า · ให้ผู้อื่นรีวิวก่อนเก็บข้อมูล · เทสยอมรับต้องผ่านเฉลยที่เขียนคนละแบบด้วย |
| **จำนวนโจทย์ k = 11 เป็นเพดานของกำลังการทดสอบ** | ผล null อาจแปลว่า "ตรวจไม่พบ" ไม่ใช่ "ไม่มีผล" | รายงานผลที่ไม่ถึงนัยสำคัญว่า **"สรุปไม่ได้"** เสมอ · รายงาน `k` ที่ใช้จริงคู่กับทุกผล |
| **กลุ่มควบคุมเชิงความยาว (A3) ไม่ได้พิสูจน์ว่าไม่มีผลทางความหมาย** | แยกผลของโครงสร้างออกจากความหมายไม่ได้เด็ดขาด | การเปรียบเทียบที่เกี่ยวกับ A3 จัดเป็น secondary/exploratory เท่านั้น |
| **ceiling / floor effect** | โจทย์ง่ายหรือยากเกินจนทุกกลุ่มได้เท่ากัน แยกความต่างไม่ออก | ประตูตรวจสภาพหลังรอบแรกด้วยเกณฑ์ที่ประกาศล่วงหน้า · กฎบังคับขึ้นเพดาน turn ถ้ากลุ่มใดชนเพดานเกิน 5% |
| **เอเจนต์อาจสับสนกับ Event Sourcing เอง ไม่ใช่ขาดวินัย** | ตัวแปรกวนที่ทำให้ข้อสรุปผิดทั้งหมด | เอกสารสถาปัตยกรรมอยู่ใน fixture และทุกกลุ่มเห็นเท่ากัน |
| **เวลาของระบบจำลองถูกตรึงไว้** | ไม่ได้วัดพฤติกรรมเมื่อเวลาเคลื่อนจริงระหว่างทำงาน | ตรึงให้เท่ากันทั้งตอนเอเจนต์ทำงานและตอนให้คะแนน (Amendment 17) ผลจึงทำซ้ำได้และไม่ขึ้นกับวันที่รัน |

### สิ่งที่งานนี้ไม่ได้ทำ

- ไม่ได้เปรียบเทียบข้ามโมเดล — ข้อมูลจากโมเดลอื่นที่มีอยู่เป็นหลักฐานเชิงพัฒนาเท่านั้น
  และเก็บคนละช่วงเวลาโดยไม่ได้สุ่มข้ามโมเดล
- ไม่ได้วัดความปลอดภัยของ skill จากมุมผู้โจมตี — กลุ่ม A4 ที่ฝังข้อความล่อเป็นการทดสอบ
  ความทนทานแบบอ่อน ไม่ใช่การประเมินเชิงความมั่นคงปลอดภัย
- ไม่ได้อ้างว่าผลลัพธ์ทั่วไปกับงานพัฒนาทุกประเภท

## 1.6 ประโยชน์ที่คาดว่าจะได้รับ

1. **ตัวเลขแทนความรู้สึก** — ทีมที่ต้องตัดสินใจว่าจะลงทุนกับการจัดกฎแบบใด
   จะมีตัวเลขพร้อมช่วงความเชื่อมั่นให้อ้างอิง แทนประสบการณ์ส่วนบุคคล
2. **แนวทางการเขียนกฎที่อ้างอิงผลการวัด** — ว่ากฎรูปแบบใดที่เอเจนต์ทำตามได้จริง
   และรูปแบบใดที่เขียนไปก็บังคับใช้ไม่ได้
3. **เครื่องมือวัดที่นำไปใช้ซ้ำได้** — กรอบการวัดที่ตรวจจากร่องรอยการกระทำจริง
   สามารถนำไปปรับใช้กับระบบอื่นหรือโมเดลอื่นได้
4. **ตัวอย่างของการทำการทดลองกับ LLM อย่างมีระเบียบวิธี** — การประกาศแผนวิเคราะห์ล่วงหน้า
   การมีกลุ่มควบคุมที่เหมาะสม การรันซ้ำและรายงานความไม่แน่นอน ซึ่งยังไม่เป็นมาตรฐาน
   ในงานประเมินเอเจนต์ที่เผยแพร่กันอยู่

## 1.7 นิยามศัพท์เฉพาะ

| คำ | ความหมายที่ใช้ในรายงานนี้ |
|---|---|
| **arm (กลุ่มทดลอง)** | สภาพ context หนึ่งแบบที่เอเจนต์ได้รับ (A0–A4) เทียบได้กับกลุ่มยาจริง/ยาหลอกในการทดลองทางคลินิก |
| **scenario (โจทย์)** | งานหนึ่งข้อที่สั่งเอเจนต์ ประกอบด้วยคำสั่ง ข้อกำหนดที่ต้องทำตาม และตัวตรวจ |
| **fixture** | ระบบจำลองที่เอเจนต์เข้าไปทำงานด้วย ถูกรีเซ็ตกลับสภาพตั้งต้นก่อนทุก run |
| **run** | การรันหนึ่งครั้ง = หนึ่งโจทย์ × หนึ่งกลุ่ม × หนึ่งรอบ |
| **repetition (รอบ)** | การทำซ้ำโจทย์เดิมกลุ่มเดิม เพื่อวัดความไม่คงเส้นคงวา |
| **artifact** | ผลดิบของหนึ่ง run — การเรียกเครื่องมือทั้งหมด คำสั่งที่รัน `git diff` และข้อความตอบสุดท้าย |
| **grader / checker** | โปรแกรมที่ตัดสินว่ากฎข้อหนึ่งผ่านหรือไม่ผ่าน ห้ามใช้คนหรือ LLM ตัดสิน |
| **Context Engineering** | การจัดเตรียมข้อมูลและกฎที่เอเจนต์จะได้รับก่อนและระหว่างทำงาน |
| **Agent Skills** | หน่วยกฎที่แยกเป็นไฟล์และถูกโหลดเมื่อคำอธิบายตรงกับงาน ตามแนวคิด progressive disclosure |
| **Progressive disclosure** | การโหลดข้อมูลเฉพาะเมื่อจำเป็น แทนการโหลดทั้งหมดตลอดเวลา |
| **contextual control (A3)** | ข้อมูลบริบทที่จับคู่ความยาวกับกลุ่มที่มีกฎ แต่ไม่ใช่กฎควบคุมพฤติกรรม และ**ไม่ได้พิสูจน์ว่าไม่มีผลทางความหมาย** |
| **RTM** | Requirements Traceability Matrix — ตารางสืบย้อนว่าการเปลี่ยนแปลงในโค้ดเชื่อมกับข้อกำหนดข้อใด |
| **AC** | Acceptance Criteria — เกณฑ์ที่นิยามว่าข้อกำหนดหนึ่ง "สำเร็จ" แปลว่าอะไร ต้องเขียนให้ทดสอบได้ |
| **`CRIT`** | ผ่านกฎวิกฤตครบทุกข้อในหนึ่ง run (ตัวชี้วัดหลัก) |
| **`RCR`** | Rule Compliance Rate — สัดส่วนกฎที่ผ่านต่อหนึ่ง run |
| **`pass^k`** | สัดส่วนโจทย์ที่ผ่าน **ครบทุกรอบ** — ตัววัดความสม่ำเสมอโดยตรง |
| **Gold-plating** | การทำเกินข้อกำหนดโดยไม่มีใครร้องขอ (ศัพท์จาก PMBOK) |
| **Requirement Drift** | ข้อกำหนดที่ผ่านในรอบหนึ่งแต่ไม่ผ่านในอีกรอบ ทั้งที่โจทย์เดิม |
| **Ceiling / floor effect** | สภาพที่ทุกกลุ่มได้คะแนนเกือบเต็มหรือเกือบศูนย์ จนแยกความต่างระหว่างกลุ่มไม่ได้ |
| **Confidence Interval** | ช่วงที่ค่าจริงน่าจะอยู่ ต้องรายงานคู่กับทุกค่าประมาณเสมอ |
| **Pre-registration** | การประกาศสมมติฐาน ตัวชี้วัด และแผนวิเคราะห์ก่อนเก็บข้อมูล เพื่อกันการตั้งสมมติฐานย้อนหลัง |
| **Event Sourcing** | การเก็บลำดับเหตุการณ์แทนการเก็บสถานะปัจจุบัน สถานะคำนวณจากการเล่นเหตุการณ์ซ้ำ |
