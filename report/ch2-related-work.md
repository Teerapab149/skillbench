## 2.1 Context Engineering และ Agent Skills

### แนวคิดพื้นฐาน

*Context engineering* หมายถึงการจัดเตรียมข้อมูลที่โมเดลจะได้รับก่อนและระหว่างทำงาน
ให้เอเจนต์ทำงานตามที่ต้องการ ในทางปฏิบัติของงานพัฒนาซอฟต์แวร์ รูปแบบที่ใช้กันมีสองแบบหลัก

**แบบที่หนึ่ง — ไฟล์กฎที่โหลดตลอดเวลา** เขียนกฎทั้งหมดไว้ในไฟล์เดียว
ซึ่งถูกใส่เข้า context ทุกครั้งที่เอเจนต์เริ่มทำงาน ข้อดีคือเรียบง่ายและแน่นอนว่าเอเจนต์เห็นกฎครบ
ข้อเสียคือทุกกฎกินพื้นที่ context ตลอดเวลาไม่ว่าจะเกี่ยวข้องกับงานตรงหน้าหรือไม่

**แบบที่สอง — Agent Skills** แยกกฎออกเป็นหน่วยย่อย แต่ละหน่วยมีคำอธิบายสั้นว่าใช้เมื่อใด
ระบบจะโหลดเนื้อหาเต็มของหน่วยนั้นเมื่อคำอธิบายตรงกับงานที่กำลังทำ

### Progressive disclosure

เอกสารทางการของ Agent Skills อธิบายกลไกการโหลดเป็นสามชั้น: ชั้นค้นพบซึ่งโหลดเฉพาะชื่อ
และคำอธิบายของแต่ละ skill ชั้นเรียกใช้ซึ่งโหลดเนื้อหาเต็มเมื่อ skill ถูกเลือก
และชั้นทำงานซึ่งโหลดไฟล์อ้างอิงเพิ่มเมื่อจำเป็น

แนวคิดนี้ตั้งอยู่บนสมมติฐานโดยนัยว่า **การไม่ใส่ข้อมูลที่ไม่เกี่ยวข้องเข้า context
ช่วยให้เอเจนต์ทำตามข้อมูลที่เกี่ยวข้องได้ดีขึ้น** สมมติฐานนี้ฟังดูสมเหตุสมผล
และมีงานด้าน context ยาวที่สนับสนุนโดยอ้อม (หัวข้อ 2.4)
**แต่ยังไม่มีการวัดโดยตรงว่าได้ผลจริงแค่ไหนเมื่อควบคุมเนื้อหาของกฎให้เท่ากัน**

ช่องว่างนี้คือจุดตั้งต้นของงานวิจัยนี้

## 2.2 การประเมินความสามารถของ LLM ในงานพัฒนาซอฟต์แวร์

### เกณฑ์มาตรฐานที่ใช้กันแพร่หลาย

**SWE-bench** (Jimenez et al., 2023) เป็นเกณฑ์มาตรฐานที่ใช้อ้างอิงมากที่สุดสำหรับเอเจนต์เขียนโค้ด
ประกอบด้วยปัญหาจริงจาก GitHub issue จำนวน 2,294 ข้อ ใน 12 repository ภาษา Python
เกณฑ์ตัดสินคือแพตช์ที่เอเจนต์สร้างขึ้นทำให้ชุดทดสอบของ repository นั้นผ่านหรือไม่

**SWE-bench+** (Aleithan et al., 2024) ตรวจสอบคุณภาพข้อมูลของ SWE-bench
แล้วรายงานว่าแพตช์ที่ผ่านจำนวนหนึ่งมาจากการที่เฉลยปรากฏอยู่ใน issue หรือคอมเมนต์ตั้งแต่แรก
ซึ่งชี้ว่าการวัดด้วยผลของชุดทดสอบเพียงอย่างเดียวมีจุดอ่อน

### ช่องว่างที่สำคัญต่องานนี้

เกณฑ์มาตรฐานกลุ่มนี้วัด **ความสามารถในการแก้ปัญหา** คำถามที่มันตอบคือ
*"เอเจนต์แก้ปัญหาได้หรือไม่"* ไม่ใช่ *"เอเจนต์แก้ปัญหาโดยไม่ทำสิ่งอื่นที่ไม่ได้สั่งหรือไม่"*

เอเจนต์ที่แก้ปัญหาสำเร็จแต่แก้ไฟล์อื่นพ่วงไปอีกสิบกว่าไฟล์ จะได้คะแนนเต็มภายใต้เกณฑ์นี้
ทั้งที่ในการทำงานจริงเป็นพฤติกรรมที่ทีมพัฒนารับไม่ได้ **ช่องว่างนี้คือสิ่งที่งานวิจัยนี้เติม**

## 2.3 การวัดการปฏิบัติตามคำสั่ง

**IFEval** (Zhou et al., 2023) เสนอแนวคิด *verifiable instructions* — คำสั่งที่ตรวจสอบได้
ด้วยโปรแกรมโดยไม่ต้องใช้คนหรือ LLM ตัดสิน เช่น "เขียนให้เกินสี่ร้อยคำ"
หรือ "กล่าวถึงคำที่กำหนดอย่างน้อยสามครั้ง" ชุดข้อมูลประกอบด้วยคำสั่งที่ตรวจได้ 25 ชนิด
จาก prompt จำนวน 541 รายการ

หลักการนี้เป็นรากฐานของกฎเหล็กข้อหนึ่งในงานวิจัยนี้:
**ถ้าเขียนตัวตรวจเป็นโปรแกรมไม่ได้ แปลว่ากฎข้อนั้นกำกวมเกินกว่าจะนำมาวัด**

**ช่องว่าง:** IFEval ตรวจสอบ *ข้อความที่โมเดลผลิตออกมา* งานวิจัยนี้ยกหลักการเดียวกัน
จากระดับข้อความไปสู่ **ระดับการกระทำต่อระบบจริง** — ตรวจจากผลต่างของโค้ด (`git diff`)
ลำดับการเรียกเครื่องมือ คำสั่งที่รันจริง และผลกระทบต่อข้อมูลย้อนหลัง

## 2.4 ลำดับชั้นของคำสั่ง ความยาว context และความสุ่ม

สามกลุ่มงานต่อไปนี้เป็นรากฐานทางทฤษฎีของสมมติฐานหลักและของระเบียบวิธีในงานนี้

### 2.4.1 ลำดับชั้นของคำสั่งไม่มั่นคงอย่างที่คาด

**The Instruction Hierarchy** (Wallace et al., 2024) เสนอให้ฝึกโมเดลให้จัดลำดับความสำคัญ
ของคำสั่งตามแหล่งที่มา คือ system message เหนือ user message เหนือเนื้อหาจากบุคคลที่สาม
เพื่อให้ทนต่อคำสั่งที่แฝงมากับข้อมูล

**Control Illusion** (Geng et al.) ทดสอบโมเดลชั้นนำหกตัวแล้วรายงานว่า
การแยก system กับ user prompt **ไม่ได้สร้างลำดับชั้นที่เชื่อถือได้จริง**
และโมเดลมีความลำเอียงโดยธรรมชาติต่อข้อจำกัดบางชนิด โดยกรอบเชิงสังคมของคำสั่ง
มีอิทธิพลต่อพฤติกรรมมากกว่าการแยกแหล่งที่มาอย่างเป็นทางการ

ข้อค้นพบหลังนี้เป็น **รากฐานทางทฤษฎีของสมมติฐานหลักของงานนี้** ที่ว่า
*รูปแบบของกฎทำนายการปฏิบัติตามได้ดีกว่าเนื้อหาของกฎ* และเป็นเหตุผลที่ออกแบบโจทย์
ตระกูลที่ข้อกำหนดขัดกับสามัญสำนึกไว้ในชุดทดลอง

**SkillMutator** (Kim et al.) ศึกษาช่องโหว่ของ Agent Skills โดยเฉพาะ
รายงานว่าผู้ไม่หวังดีสามารถฝังคำสั่งอันตรายไว้ในส่วนคำอธิบายภาษาธรรมชาติของ skill
ขณะที่โค้ดยังดูปกติ และเครื่องมือตรวจจับที่มีอยู่จับได้เพียงส่วนน้อย

งานชิ้นนี้มองความปลอดภัยของ skill จากมุม **ผู้โจมตี** ส่วนงานวิจัยนี้มองจากมุม
**ผู้ใช้สุจริตที่เขียน skill เอง** แล้วถามว่ามันควบคุมพฤติกรรมได้จริงแค่ไหน
เป็นคนละคำถามบนวัตถุเดียวกัน กลุ่มทดลอง A4 ที่ฝังข้อความล่อไว้ในไฟล์โค้ด
เป็นการทดสอบความทนทานแบบอ่อนเมื่อเทียบกับงานกลุ่มนี้

### 2.4.2 ตำแหน่งของข้อมูลใน context มีผลต่อการถูกนำไปใช้

**Lost in the Middle** (Liu et al., 2023) รายงานว่าประสิทธิภาพของโมเดลสูงที่สุด
เมื่อข้อมูลที่เกี่ยวข้องอยู่ต้นหรือท้าย context และลดลงอย่างมีนัยสำคัญเมื่อข้อมูลอยู่ตรงกลาง
แม้ในโมเดลที่ออกแบบมาสำหรับ context ยาวโดยเฉพาะ

ข้อค้นพบนี้เป็นเหตุผลเชิงกลไกที่อธิบายว่าเหตุใดกฎที่อยู่กลางไฟล์ยาวจึงอาจถูกละเลย
และเป็นแรงจูงใจของแนวคิด progressive disclosure

**ช่องว่าง:** งานชิ้นนี้วัดที่งานค้นคืนข้อมูล ไม่ใช่งานที่ต้องปฏิบัติตามกฎ
และวัดตามตำแหน่งในเอกสาร ไม่ใช่ตามจำนวนกฎที่โหลดพร้อมกัน

### 2.4.3 ความสุ่มของโมเดลเป็นข้อเท็จจริงที่ต้องออกแบบรองรับ

งานศึกษาเชิงประจักษ์เกี่ยวกับความไม่คงเส้นคงวาของโมเดลในงานสร้างโค้ด
วิเคราะห์โจทย์จำนวนมากจากชุดข้อมูลมาตรฐานหลายชุด แล้วรายงานว่า
**การตั้งค่าให้สุ่มน้อยที่สุดไม่รับประกันว่าจะได้ผลเหมือนเดิม** และเสนอว่างานวิจัยควรรายงาน
ค่าเฉลี่ย ความแปรปรวน หรือการกระจายจากการเรียกหลายครั้ง แทนผลจากการรันครั้งเดียว

งานอีกชิ้นในทิศทางเดียวกันโต้ว่าการประเมิน LLM ไม่ควรมองข้ามความไม่แน่นอน
และการรายงานผลจากการรันครั้งเดียวทำให้เข้าใจผิดได้

สองงานนี้เป็น **เหตุผลของระเบียบวิธีทั้งหมดในงานนี้** — การรันซ้ำหลายรอบต่อโจทย์
การรายงานช่วงความเชื่อมั่นคู่กับทุกค่าประมาณ และการใช้ตัวชี้วัดที่วัดความสม่ำเสมอโดยตรง
แทนการดูค่าเฉลี่ยอย่างเดียว

**ช่องว่าง:** งานเหล่านี้วัดความสุ่มของ *โค้ดที่ผลิตออกมา* งานวิจัยนี้วัดความสุ่มของ
*การตัดสินใจเชิงข้อกำหนด* — เมื่อข้อกำหนดขัดกัน เอเจนต์เลือกทางเดิมทุกรอบหรือไม่
ซึ่งนิยามไว้ในงานนี้ว่า **Requirement Drift**

## 2.5 Requirements Traceability Matrix ในบทบาทเครื่องมือวัดพฤติกรรม

### สาขาเดิมและคำถามเดิม

การกู้คืนความเชื่อมโยงระหว่างข้อกำหนดกับโค้ด (*traceability link recovery*)
เป็นสาขาที่มีมานานในวิศวกรรมซอฟต์แวร์ แบ่งได้เป็นสามยุคตามเทคนิคที่ใช้:
วิธีเชิงการค้นคืนสารสนเทศ วิธีเชิงการเรียนรู้ของเครื่อง และวิธีที่ใช้ LLM ร่วมกับการค้นคืน

คำถามที่งานทั้งหมดในสาขานี้ถามคือ
*"จะกู้คืนความเชื่อมโยงจากสิ่งที่มนุษย์เขียนไว้แล้วได้อย่างไร"*

### คำถามกลับด้านของงานนี้

งานวิจัยนี้ถามคำถามในทิศทางตรงกันข้าม:

> *เมื่อ **เอเจนต์** เป็นผู้เขียนโค้ด การเปลี่ยนแปลงที่มันทำ **สืบย้อนกลับไปยังข้อกำหนดได้กี่ส่วน***

RTM ในงานนี้จึงไม่ได้ทำหน้าที่เป็นเครื่องมือช่วยจัดการเอกสาร แต่ถูกใช้เป็น
**เครื่องมือวัดพฤติกรรม** การเปลี่ยนแปลงที่สืบย้อนกลับไปยังข้อกำหนดไม่ได้
คือการทำงานนอกขอบเขต ซึ่งวัดเป็นตัวเลขได้

### การเชื่อมกับศัพท์ทางการจัดการโครงการ

แนวคิด *gold-plating* ในมาตรฐานการบริหารโครงการ (PMBOK) หมายถึงการส่งมอบเกิน
สิ่งที่ข้อกำหนดระบุโดยไม่มีผู้ร้องขอ ซึ่งถือเป็นความเสี่ยงไม่ใช่คุณค่า
งานวิจัยนี้นำแนวคิดดังกล่าวมาทำให้วัดได้ด้วยตัวชี้วัดที่คำนวณจากร่องรอยการกระทำจริง

เท่าที่ค้นพบ **ยังไม่มีงานวิจัยที่ใช้ RTM ในบทบาทของเครื่องมือวัดพฤติกรรมของเอเจนต์**

## 2.6 การออกแบบการทดลองแบบมีกลุ่มควบคุม

### ปัญหาของการเทียบแบบ "มี" กับ "ไม่มี"

หากเปรียบเทียบเพียงเอเจนต์ที่ไม่มีกฎกับเอเจนต์ที่มี skill คำถามที่ตอบไม่ได้ทันทีคือ

> *ผลที่ดีขึ้นมาจากกฎ หรือมาจากการที่ใส่ข้อความเพิ่มเข้าไปใน context เฉย ๆ*

การออกแบบของงานนี้จึงมีกลุ่มควบคุมสองชนิดที่ทำหน้าที่ต่างกัน:

| ชนิด | บทบาท | ควบคุมอะไร |
|---|---|---|
| **active control** | กฎเนื้อหาเดียวกัน แต่จัดวางแบบไฟล์เดียวโหลดตลอด | แยกผลของ *โครงสร้าง* ออกจากผลของ *เนื้อหา* |
| **contextual control** | ข้อความยาวใกล้เคียงกัน แต่เป็นข้อมูลบริบท ไม่ใช่กฎควบคุมพฤติกรรม | แยกผลของ *กฎ* ออกจากผลของ *ปริมาณ context* |

### ข้อจำกัดที่ต้องระบุอย่างตรงไปตรงมา

กลุ่มควบคุมเชิงความยาว **ไม่ใช่ยาหลอกที่พิสูจน์แล้วว่าไม่มีผลทางความหมาย**
ข้อมูลบริบทอาจช่วยหรือรบกวนเอเจนต์ก็ได้ ดังนั้น

- ผลที่ว่ากลุ่มควบคุมทั้งสองไม่ต่างกัน **ไม่ได้พิสูจน์ว่ากฎไม่มีผล**
- ผลที่ว่ากลุ่มทดลองดีกว่ากลุ่มควบคุมเชิงความยาว **ไม่ได้แยกผลของโครงสร้างออกจาก
  ความยาวหรือความหมายของข้อความได้เด็ดขาด**

การเปรียบเทียบที่เกี่ยวข้องกับกลุ่มควบคุมเชิงความยาวจึงถูกจัดเป็น secondary
หรือ exploratory เท่านั้น และประกาศไว้เช่นนั้นล่วงหน้า

### การประกาศแผนวิเคราะห์ล่วงหน้า

งานนี้ใช้แนวปฏิบัติการประกาศสมมติฐาน ตัวชี้วัด ลำดับชั้นของ endpoint และแผนวิเคราะห์
ไว้ล่วงหน้าก่อนเก็บข้อมูลเปรียบเทียบ พร้อมบันทึกวันที่ การเปลี่ยนแปลงใด ๆ หลังจากนั้น
ต้องบันทึกเป็น amendment พร้อมเหตุผลและวันที่ และต้องรายงานทั้งฉบับเดิมและฉบับแก้ในเล่ม

แนวปฏิบัตินี้มีเป้าหมายเพื่อกันการตั้งสมมติฐานย้อนหลังหลังเห็นข้อมูล
ซึ่งเป็นความเสี่ยงที่สูงเป็นพิเศษเมื่อผู้วิจัยเป็นผู้ออกแบบทั้งกฎและตัวตรวจเอง

## 2.7 สรุปช่องว่างของงานวิจัยที่ผ่านมา

งานประเมินเอเจนต์เขียนโค้ดที่มีอยู่วัด **ความสามารถในการแก้ปัญหา** โดยใช้ผลของชุดทดสอบ
เป็นเกณฑ์ ซึ่งไม่ลงโทษเอเจนต์ที่แก้ปัญหาสำเร็จแต่ทำงานเกินขอบเขตหรือสร้างผลกระทบ
ที่ไม่ได้ตั้งใจ ในอีกด้านหนึ่ง งานด้านการวัดการปฏิบัติตามคำสั่งเสนอแนวคิดคำสั่ง
ที่ตรวจสอบได้ด้วยโปรแกรม แต่จำกัดอยู่ที่ระดับข้อความที่โมเดลผลิต ไม่ใช่ระดับการกระทำ
ต่อระบบจริง ส่วนงานด้าน context ยาวและลำดับชั้นของคำสั่งชี้ว่าตำแหน่งและรูปแบบของคำสั่ง
มีผลต่อการปฏิบัติตาม แต่ยังไม่มีการวัดในบริบทของงานพัฒนาระบบที่มีเครื่องมือจริง

งานวิจัยนี้เติมช่องว่างดังกล่าวด้วยการเสนอกรอบการวัดที่

1. **ตรวจการปฏิบัติตามข้อกำหนดจากร่องรอยการกระทำจริง** — ผลต่างของโค้ด
   ลำดับการเรียกเครื่องมือ คำสั่งที่รัน และผลกระทบต่อข้อมูลย้อนหลัง
2. **ใช้ RTM เป็นตัวชี้วัดพฤติกรรม** โดยนำแนวคิด gold-plating จากมาตรฐานการบริหารโครงการ
   มาทำให้วัดเป็นตัวเลขได้
3. **แยกผลของโครงสร้างการจัดวางกฎออกจากผลของปริมาณ context** ด้วยกลุ่มควบคุม
   ที่จับคู่ความยาวแต่ไม่มีกฎ ซึ่งเป็นการควบคุมที่งานก่อนหน้ายังไม่มี
