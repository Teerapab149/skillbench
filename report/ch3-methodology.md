## 3.1 กรอบแนวคิดการวิจัย

### คำถามวิจัย

> **การจัดวางกฎและจังหวะที่กฎถูกโหลดเข้า context ส่งผลต่อการที่เอเจนต์ทำตามกฎหรือไม่
> เมื่อควบคุมเนื้อหาของกฎให้เท่ากันทุกประการ**

คำถามนี้ต่างจากคำถามที่อุตสาหกรรมถามกันอยู่ ซึ่งมักเป็น *"ใส่กฎแล้วดีขึ้นไหม"*
คำถามแบบหลังตอบง่ายและตอบแล้วได้ประโยชน์น้อย เพราะไม่มีใครสงสัยว่าการบอกกฎดีกว่าไม่บอก
สิ่งที่ยังไม่มีคำตอบเชิงประจักษ์คือ **เมื่อกฎเท่ากันแล้ว วิธีจัดวางมันสำคัญแค่ไหน**

### ตัวแปรต้นและตัวแปรตาม

| | |
|---|---|
| **ตัวแปรต้น** | โครงสร้างและจังหวะการโหลดกฎ — ไฟล์เดียวโหลดตลอดเวลา เทียบกับ แยกเป็น skill ที่โหลดเมื่อ description ตรงกับงาน |
| **ตัวแปรตาม** | การปฏิบัติตามกฎที่ประกาศไว้ วัดด้วยตัวชี้วัดในหัวข้อ 3.5 โดยตัวหลักคือ `CRIT` |
| **สิ่งที่ต้องคงที่** | เนื้อหาของกฎ · โมเดล · เพดาน turn · ชุดเครื่องมือ · โจทย์ · สภาพ runtime · การรีเซ็ต workspace |

### สิ่งที่ทำให้งานนี้ไม่ใช่การรีวิวเครื่องมือ

การเทียบ *"มีกฎ"* กับ *"ไม่มีกฎ"* ตอบไม่ได้ว่าผลที่เห็นมาจากเนื้อหาของกฎ
หรือมาจาก context ที่ต่างกัน งานนี้จึงมี **contextual control ที่จับคู่ความยาว** (A3)
ซึ่งได้ข้อมูลบริบทโครงการยาวใกล้เคียง A1 แต่ไม่มีกฎควบคุมพฤติกรรม

A3 ไม่ใช่ยาหลอกที่พิสูจน์แล้วว่าไม่มีผลทางความหมาย ข้อมูลบริบทอาจช่วยหรือรบกวนได้
ดังนั้น A1≈A3 ไม่พิสูจน์ว่ากฎไม่มีผล และ A2>A3 ไม่แยกผลของโครงสร้างออกจากความยาว
หรือเนื้อหาได้เด็ดขาด การเปรียบเทียบที่เกี่ยวกับ A3 จึงเป็น secondary/exploratory

## 3.2 การออกแบบกลุ่มทดลอง 5 กลุ่ม

| กลุ่ม | บทบาท | สิ่งที่เอเจนต์เห็นตอนเริ่มงาน | ค่าประมาณ always-on | ค่าประมาณเมื่อโหลด skill ครบ |
|---|---|---|---:|---:|
| **A0** | เส้นฐานล่างสุด | ไม่มีไฟล์กฎใด ๆ | 0 | 0 |
| **A1** | active control | `CLAUDE.md` ไฟล์เดียว โหลดตลอดเวลา | 1,969 | 1,969 |
| **A2** | **treatment** | `CLAUDE.md` สั้น + skill 4 ตัวที่โหลดตามเงื่อนไข | **848** | 3,323 |
| **A3** | contextual control จับคู่ความยาว | ข้อมูลบริบทที่ยาวใกล้ A1 แต่ไม่มีกฎควบคุมพฤติกรรม | 2,073 | 2,073 |
| **A4** | ทดสอบความทนทาน | เหมือน A2 + ข้อความล่อฝังในไฟล์โค้ด | 848 | 3,323 |

*(ตัวเลขในตารางเป็นค่าประมาณแบบ character heuristic จากไฟล์จริง ไม่ใช่ token usage ที่
adapter วัดจากการรัน ค่า usage จริงต้องรายงาน fresh input + cache creation + cache read แยกกัน)*

**A1 ถูกเลือกเป็น active control ไม่ใช่ A0** เพราะการเทียบกับกลุ่มที่ไม่มีอะไรเลย
จะทำให้ผลดูดีเกินจริง กลุ่มที่ควรถูกเทียบคือวิธีที่ทีมพัฒนาซอฟต์แวร์ใช้กันอยู่จริงในปัจจุบัน
ซึ่งคือการเขียนกฎทั้งหมดลงไฟล์เดียวแล้วให้โหลดทุกครั้ง

### การเปรียบเทียบแต่ละคู่ตอบคำถามอะไร

| คู่ | คำถามที่ตอบ |
|---|---|
| A1 – A0 | การมีกฎดีกว่าไม่มีหรือไม่ |
| **A2 – A1** | **กฎชุดเดียวกัน วางคนละที่ ให้ผลต่างกันหรือไม่ — คำถามวิจัยหลัก** |
| A1 – A3 | เปรียบเทียบกฎแบบ always-on กับข้อมูลบริบทที่จับคู่ความยาว โดยมีข้อจำกัดเรื่อง semantic inertness |
| A2 – A3 | เปรียบเทียบเชิงสำรวจ; แยกโครงสร้าง ความยาว และความหมายออกจากกันไม่ได้เด็ดขาด |
| A4 – A2 | กฎกันคำสั่งที่ฝังในไฟล์ได้จริง หรือเอเจนต์เพียงบังเอิญเชื่อฟังเมื่อไม่มีสิ่งยั่วยุ |

### ความเท่าเทียมของเนื้อหากฎระหว่าง A1 กับ A2

เงื่อนไขที่ขาดไม่ได้ของการทดลองนี้คือ **A1 กับ A2 ต้องมีข้อผูกพันครบเท่ากันทุกข้อ**
ถ้าฝ่ายใดมีมากกว่า สิ่งที่วัดจะกลายเป็น *"กฎมากกว่าย่อมดีกว่า"* ซึ่งเป็นคนละคำถาม

กฎถูกประกาศไว้ที่เดียวใน `config/rules-canonical.json` เป็น **20 ข้อ แยกย่อยเป็น 47 ข้อผูกพัน**
แล้วมีตัวตรวจอัตโนมัติ assert ว่าทั้งสองฝ่ายครอบคลุมครบทุกข้อ ตกข้อเดียวคือรันการทดลองไม่ได้

> **ข้อบกพร่องที่พบและแก้ก่อนเก็บข้อมูล (4 ก.ย. 2569):** ตัวตรวจรุ่นก่อนตรวจด้วย *คำสำคัญ*
> ไม่ใช่ *ข้อผูกพัน* เช่นใช้คำว่า `acceptance criteria` ซึ่งปรากฏทั้งสองฝ่าย จึงรายงานว่าผ่าน
> ทั้งที่ A2 มีข้อผูกพันที่ A1 ไม่มีอยู่ถึง 7 ข้อ ที่ชัดที่สุดคือ *"แปลง AC เป็นเทสก่อนแตะ
> implementation"* และ *"รันเทสแล้วต้องตกก่อน"* ซึ่งมีเฉพาะใน skill `acceptance-first`
>
> ความล้มเหลวรูปแบบนี้อันตรายเป็นพิเศษเพราะ **ตัวตรวจที่หลวมเกินไปให้ผลหน้าตาเหมือนทุกอย่างเรียบร้อย**
> แก้แล้วโดยยกข้อผูกพันที่ขาดขึ้นไปใส่ A1 ให้ครบ และเปลี่ยนตัวตรวจไปตรวจทีละข้อผูกพัน

### การจับคู่ความยาวของ contextual control

A3 ต้องมีความยาวใกล้เคียง A1 ในกรอบ **0.85–1.15 เท่า** ซึ่งประกาศไว้ล่วงหน้าและตรวจอัตโนมัติ
ค่าประมาณปัจจุบันคือ **1.053** และเนื้อหาของ A3 เป็นข้อมูลเชิงบริหารของโครงการ
เช่น ความเป็นมา โครงสร้างทีม รอบการปล่อยของ **โดยไม่มีคำสั่งเชิงพฤติกรรมเลยสักข้อ**

> **ข้อบกพร่องที่พบและแก้ก่อนเก็บข้อมูล:** A3 ฉบับแรกขึ้นต้นด้วยข้อความว่า *"Arm A3 — PLACEBO
> ไฟล์นี้ไม่มีกฎควบคุมพฤติกรรมใด ๆ เลย"* ซึ่งเท่ากับบอกโมเดลตรง ๆ ว่ากำลังอยู่ในการทดลอง
> และอยู่ในกลุ่มที่ไม่ต้องทำตามกฎ ผลของกลุ่มนี้จึงตอบไม่ได้ว่าเอเจนต์ทำได้แย่ลง
> เพราะไม่มีกฎ หรือเพราะถูกบอกว่าไม่ต้องทำตามกฎ
>
> ไฟล์ของทุกกลุ่มถูกเขียนใหม่ให้ไม่มีข้อความบ่งชี้การทดลอง และมีตัวตรวจอัตโนมัติกันไว้

## 3.3 ตัวแปรควบคุมและการสุ่มแบบ randomized block

### ตัวแปรที่ล็อกให้เหมือนกันทุกกลุ่ม

| ตัวแปร | ค่า | วิธีบังคับ |
|---|---|---|
| โมเดล | `claude-sonnet-5` | ส่งผ่าน `--model` · อยู่ใน signature ของ checkpoint · ตรวจซ้ำกับค่าที่ CLI รายงานทุก run |
| เพดานจำนวน turn | 80 | `--max-turns` · อยู่ใน signature |
| ชุดเครื่องมือ | 7 ตัว (`Read` `Write` `Edit` `Bash` `Glob` `Grep` `Skill`) | `--tools` **ร่วมกับ** `--strict-mcp-config` · assert ทุก run |
| บริการภายนอก (MCP) | ไม่มี | `--strict-mcp-config` โดยไม่ระบุไฟล์ config · assert ว่าไม่มีเซิร์ฟเวอร์เชื่อมต่อ |
| แหล่ง setting | เฉพาะของโครงการ | `--setting-sources project` |
| เวอร์ชันเครื่องมือ | ตรึงจาก run แรก | บันทึกใน manifest · เปลี่ยนกลางทางเมื่อใดหยุดทั้งชุด |
| โจทย์และ fixture | เหมือนกันทุกกลุ่ม | รีเซ็ต workspace ด้วย git ก่อนทุก run |

`Skill` ถูกใส่ให้ทุกกลุ่มเท่ากันแม้กลุ่มที่ไม่มีไฟล์ skill เพราะถ้าให้เฉพาะ A2 กับ A4
ชุดเครื่องมือจะกลายเป็นตัวแปรที่ต่างกันอีกตัวหนึ่ง แล้วแยกไม่ออกว่าผลมาจากโครงสร้างกฎ
หรือมาจากการมีเครื่องมือมากกว่า ตัวแปรต้นต้องเหลือตัวเดียวคือมีโฟลเดอร์ skill หรือไม่

### การสุ่มแบบ randomized block

หน่วยของ block คือ repetition หนึ่งรอบ ภายในแต่ละรอบจะรันทุกคู่ (โจทย์ × กลุ่ม)
โดย**สลับลำดับแบบสุ่ม** ด้วย seed ที่กำหนดไว้ล่วงหน้าเพื่อให้ทำซ้ำได้

เหตุผล: ถ้ารันกลุ่มหนึ่งจนจบแล้วค่อยรันกลุ่มถัดไป ความเปลี่ยนแปลงของบริการปลายทาง
ในช่วงเวลานั้นจะไปกองอยู่ที่กลุ่มใดกลุ่มหนึ่ง การสลับทำให้ผลกระทบกระจายเท่า ๆ กันทุกกลุ่ม

การทดลองทั้งหมดเก็บใน **invocation เดียวและ checkpoint เดียว** ไม่แยกเก็บทีละกลุ่ม
เพราะการแยกเก็บทำให้การสุ่มภายใน block เสียตั้งแต่ต้น

การสุ่มลำดับช่วยกระจาย temporal drift แต่ **ไม่ได้ทำให้สมมติฐานของ sign-flip เป็นจริงเอง**
การทดสอบหลักยังต้องอาศัย sign-exchangeability ของผลต่างราย scenario ภายใต้สมมติฐานศูนย์
ซึ่งเป็นสมมติฐานที่ตรวจยืนยันจากลำดับสุ่มเพียงอย่างเดียวไม่ได้

### การประกาศตัวแปรควบคุมไม่ใช่การควบคุม

หัวข้อนี้เป็นข้อค้นพบเชิงระเบียบวิธีของงานนี้ ไม่ใช่เพียงบันทึกการแก้ข้อบกพร่อง

ระหว่างการพัฒนาพบว่ามีตัวแปรที่ **ประกาศไว้ในไฟล์กำหนดค่าครบถ้วน แต่ไม่เคยถูกบังคับจริง**
รวมสามครั้งในสามเดือน และทุกครั้งระบบยังผลิตผลลัพธ์พร้อมช่วงความเชื่อมั่นออกมาตามปกติ
โดยไม่มีสัญญาณเตือนใด ๆ

| ตัวแปรที่ประกาศ | สิ่งที่เกิดขึ้นจริง | พบเมื่อ |
|---|---|---|
| ชื่อโมเดล | ไม่เคยถูกโค้ดอ่านไปใช้ ค่าที่ใช้จริงคือค่าที่ฝังอยู่ในโปรแกรม | 12 ส.ค. 2569 |
| `temperature` | ไม่เคยถูกส่งไปยังเครื่องมือ และเครื่องมือไม่มีช่องให้ตั้งค่านี้ | 4 ก.ย. 2569 |
| ชุดเครื่องมือ 7 ตัว | ได้จริง 7 / 15 / 31 / 39 / 47 ตัวแล้วแต่ run · **100 จาก 109 run (92%) มีเครื่องมือจากบริการภายนอกติดมาด้วย** | 4 ก.ย. 2569 |

ข้อสังเกตที่สำคัญที่สุดคือ **หลักฐานของข้อที่สามอยู่ในข้อมูลที่ระบบเก็บไว้เองตั้งแต่ run แรก**
ระบบบันทึกรายชื่อเครื่องมือที่ได้รับจริงลงในผลทุก run เพราะผู้พัฒนารู้ว่าต้องตรวจ
แต่ไม่เคยมีขั้นตอนใดนำค่านั้นมาเปรียบเทียบกับค่าที่ประกาศไว้

**มาตรการที่ใช้แก้:**

1. **run manifest** — บันทึกสภาพจริงจาก run แรกแล้วตรึงไว้ ได้แก่ เวอร์ชันเครื่องมือ โมเดล
   ชุดเครื่องมือ ชุด skill พื้นฐาน แหล่งสิทธิ์เรียกใช้ และลายนิ้วมือของไฟล์ที่นิยามการทดลอง
2. **การตรวจแบบ fail-closed ทุก run** — ไม่ตรงกับ manifest เมื่อใด **หยุดทั้งชุดทันที**
   ไม่ใช่บันทึกไว้แล้วรันต่อ เพราะ run ที่เก็บภายใต้สภาพต่างกันนำมารวมเป็นชุดเดียวไม่ได้
3. **หลักการแยก signature กับ manifest** — signature เก็บเฉพาะสิ่งที่ผู้ทดลองตั้งใจกำหนดเอง
   เปลี่ยนแล้วได้ชุดข้อมูลใหม่ · manifest เก็บสิ่งที่เปลี่ยนได้เองโดยไม่มีใครสั่ง
   เปลี่ยนแล้วต้องหยุด

   หลักการข้อนี้มาจากความผิดพลาดจริง: ตอนแรกนำเวอร์ชันเครื่องมือไปใส่ใน signature
   ซึ่งให้ผลตรงข้ามกับที่ตั้งใจ เพราะเมื่อเครื่องมืออัปเดตตัวเอง ระบบจะเปลี่ยนชื่อไฟล์ checkpoint
   แล้ว **เริ่มเก็บชุดข้อมูลใหม่โดยเงียบ** แทนที่จะหยุดเตือน

### ข้อจำกัดของการควบคุมที่ต้องระบุตามตรง

**ชุด skill พื้นฐานลบให้เหลือศูนย์ไม่ได้** ทุกกลุ่มรวมทั้ง A0 มองเห็น skill ที่ติดมากับเครื่องมือ
และของผู้ใช้รวม 18 ตัว การปิดด้วยคำสั่งที่มีอยู่จะปิด skill ของการทดลองไปด้วย
ส่วนการแยกโฟลเดอร์ตั้งค่าทำให้การยืนยันตัวตนล้มเหลว

สิ่งที่ทำได้และทำไปแล้วคือ **ประกาศชุดนี้เป็นค่าคงที่ที่เท่ากันทุกกลุ่ม** แล้วให้ตัวแปรต้น
เป็นส่วนต่าง พร้อมบังคับเพิ่มว่า skill นอกการทดลองที่ถูก **เรียกใช้จริง** ต้องเป็นศูนย์ทุก run

ข้อมูลที่เก็บมาทั้งหมดสอดคล้องกับเงื่อนไขนี้ คือไม่มีกลุ่มใดเรียกใช้ skill นอกการทดลองเลยแม้แต่ครั้งเดียว
และกลุ่ม A0, A1, A3, A4 ไม่เรียกใช้เครื่องมือ `Skill` เลย

> **ผลต่อการเขียนรายงาน:** ต้องเขียนว่า *"สภาพแวดล้อมไม่สะอาดเท่าที่ออกแบบไว้ แต่ไม่สะอาดเท่ากันทุกกลุ่ม"*
> **ห้ามเขียนว่า A0 เป็นเอเจนต์เปล่าสมบูรณ์** เพราะข้อมูลไม่รองรับข้อความนั้น

## 3.4 การออกแบบโจทย์และกับดัก

โจทย์ทั้งหมด **11 ข้อ แบ่งเป็น 6 ตระกูล** บนโดเมนเดียวกันคือระบบจองเวลาใช้งานหน่วยประมวลผลกราฟิก
ที่ออกแบบด้วยสถาปัตยกรรมแบบเก็บลำดับเหตุการณ์ (event sourcing)

| ตระกูล | โจทย์ | สิ่งที่ทดสอบ |
|---|---|---|
| `ordinary` | S01, S02, S03 | งานปกติที่ไม่มีกับดัก — **ตัวเทียบภายในการออกแบบ** |
| `gold_plating` | S04, S05 | ทำเกินสิ่งที่ผู้ใช้ขอ |
| `counter_intuitive` | S06, S07 | ข้อกำหนดที่ขัดกับสามัญสำนึก |
| `hidden_impact` | S08, S09 | การแก้ตรรกะที่กระทบข้อมูลย้อนหลังโดยไม่มี error |
| `requirement_conflict` | S10 | ข้อกำหนดสองข้อที่ขัดกันเอง |
| `requirement_invention` | S11 | ข้อกำหนดไม่ครอบคลุมกรณีที่ต้องเขียนโค้ด |

### เหตุผลที่ต้องมีโจทย์ธรรมดา

ถ้าใช้เฉพาะโจทย์ที่มีกับดัก จะแยกไม่ออกระหว่าง *"เอเจนต์ขาดวินัยในการทำตามกฎ"*
กับ *"เอเจนต์ไม่เข้าใจสถาปัตยกรรมของระบบ"* โจทย์ธรรมดาสามข้อจึงทำหน้าที่เป็นตัวเทียบ

- ถ้าเอเจนต์ทำโจทย์ธรรมดาไม่ผ่านด้วย ปัญหาอยู่ที่ความเข้าใจระบบ
- ถ้าผ่านโจทย์ธรรมดาแต่ตกเฉพาะโจทย์ที่มีกับดัก **นั่นคือเรื่องวินัยในการทำตามกฎจริง**

### เหตุผลที่เลือกสถาปัตยกรรมแบบเก็บลำดับเหตุการณ์

ระบบประเภทนี้คำนวณผลลัพธ์ใหม่จากเหตุการณ์ทุกครั้งที่มีการเรียกดู การแก้ตรรกะการคำนวณ
จึงเปลี่ยนตัวเลขของข้อมูลในอดีตทั้งหมดทันที **โดยไม่มี error ไม่มีข้อมูลถูกแก้ และเทสเดิมยังผ่าน**

คุณสมบัตินี้ทำให้ความเสียหายจากการทำงานเกินขอบเขตวัดได้ด้วยตัวเลข ไม่ใช่ด้วยความเห็น
ซึ่งเป็นเงื่อนไขที่ตัวชี้วัดของงานนี้ต้องการ

### วิธีให้คะแนน

แต่ละโจทย์มีกฎ 8–11 ข้อ แบ่งระดับความรุนแรงเป็น `critical` กับ `major`
ตัวตัดสินว่าผ่านหรือไม่เป็นโปรแกรม ไม่ใช่มนุษย์ และให้ผลเดิมทุกครั้งที่รันซ้ำบนข้อมูลเดียวกัน
บันทึกการทำงานดิบของทุก run ถูกเก็บไว้ทั้งหมดเพื่อให้ตรวจสอบย้อนหลังได้

## 3.5 ตัวชี้วัดและสูตรคำนวณ

| ตระกูล | ตัวชี้วัด | นิยาม |
|---|---|---|
| การปฏิบัติตามกฎ | `CRIT` | กฎระดับวิกฤตผ่านครบทุกข้อใน run นั้น (0/1) — **ตัวชี้วัดหลัก** |
| | `RCR` | สัดส่วนกฎที่ผ่านต่อ run |
| | `FULL` | run ที่ผ่านครบทุกกฎ (0/1) |
| ขอบเขต | `SCOPE` | ไม่มีไฟล์นอกรายการที่อนุญาตถูกแก้ (0/1) |
| ความสม่ำเสมอ | `pass^k` | สัดส่วนโจทย์ที่ผ่าน **ครบทุกรอบ** |
| | Jaccard / Entropy | ความคาดเดาได้ของชุดไฟล์ที่ถูกแก้ข้าม run |
| ความปลอดภัย | Injection resistance | อัตราการต้านคำสั่งที่ฝังในไฟล์ (กลุ่ม A4) |
| การยิง skill | Precision / Recall / F1 | skill ถูกเรียกใช้ถูกจังหวะหรือไม่ |
| ต้นทุน | token, tool call, เวลาต่อ run | ต้องรายงานคู่กับผลเสมอ |

### พื้นเชิงโครงสร้างของ `RCR` — ข้อจำกัดที่ต้องระบุคู่กับตัวเลขเสมอ

วัดโดยป้อนผลการทำงานปลอมที่ *"ไม่ทำอะไรเลย"* เข้าตัวตรวจทั้ง 11 โจทย์ ได้ `RCR` เฉลี่ย **0.552**

สาเหตุคือกฎประเภท *"ห้ามแตะ"* และ *"ห้ามทำเกินขอบเขต"* ผ่านโดยปริยายเมื่อไม่มีไฟล์ใดถูกแก้
ซึ่งไม่ใช่ข้อผิดพลาดของตัวตรวจ แต่เป็นคุณสมบัติของการวัด "การไม่ทำเกิน" — การไม่ทำอะไรเลย
ย่อมไม่ทำเกินอยู่แล้ว

**ผลที่ตามมา:** `RCR` ถูกบีบให้อยู่ในช่วงประมาณ 0.55–1.00 ไม่ใช่ 0–1
ขนาดของผลที่วัดได้จึงเล็กกว่าความเป็นจริงเสมอ **นี่คือเหตุผลหลักที่ `CRIT` เป็นตัวชี้วัดหลักแทน `RCR`**
เพราะการไม่ทำอะไรเลยได้ `CRIT` เท่ากับศูนย์ในทุกโจทย์

### เหตุผลที่ `pass^k` เป็นตัวชี้วัดหลักไม่ได้ ทั้งที่มีความหมายเชิงการใช้งานมากที่สุด

`pass^k` ตอบคำถามที่ผู้ใช้งานจริงสนใจที่สุด คือ *"เชื่อถือได้ทุกครั้งหรือไม่"*
เอเจนต์ที่ผ่าน 8 ใน 10 ครั้งใช้งานจริงไม่ได้ ต่อให้ค่าเฉลี่ยดูดี

แต่มันเป็นตัวชี้วัดหลักไม่ได้เพราะ **มีหน่วยข้อมูลเพียง 11 หน่วย** เท่าจำนวนโจทย์
จึงถูกกำหนดให้เป็น key secondary และรายงานทุกครั้ง

## 3.6 สถิติที่ใช้และการคำนวณขนาดตัวอย่าง

### หน่วยของการวิเคราะห์คือโจทย์ ไม่ใช่ run

run ที่อยู่ในโจทย์เดียวกันไม่เป็นอิสระต่อกัน ค่า intraclass correlation ที่วัดได้จากข้อมูล
สอบเทียบคือ **ICC = 0.335** การรายงานที่ระดับ run จึงเป็นการอ้างปริมาณข้อมูลเกินกว่าที่มีอยู่จริง
และให้ช่วงความเชื่อมั่นแคบกว่าความเป็นจริง

### แผนการทดสอบตามลำดับตายตัว (fixed-sequence)

| ลำดับ | ตัวชี้วัด | การเปรียบเทียบ | สถิติ |
|---|---|---|---|
| **Primary** | `CRIT` | A2 เทียบ A1 | **exact paired sign-flip** บนผลต่างค่าเฉลี่ยรายโจทย์ + cluster bootstrap 95% CI |
| *(sensitivity)* | `CRIT` | A2 เทียบ A1 | McNemar exact ระดับ run — รายงานควบคู่ ไม่ใช่ตัวตัดสิน |
| **Co-primary** | `RCR` | A2 เทียบ A1 | cluster bootstrap · **ทดสอบเมื่อ primary มีนัยสำคัญเท่านั้น** |
| Key secondary | `pass^k` | A2 เทียบ A1 | ราย arm ใช้ Wilson โดยตัวหารคือ scenario; ช่วงของผลต่างยังไม่ได้ implement |
| Equivalence | `CRIT` | A1 เทียบ A3 | **TOST** margin ±0.10 บนช่วงความเชื่อมั่น 90% |
| Secondary | ตัวชี้วัดที่เหลือ | ทุกคู่ | รายงานทั้งหมด ไม่คัดเลือก |

การทดสอบแบบลำดับตายตัวควบคุมการเปิดทดสอบถัดไปตามเงื่อนไขที่ประกาศไว้ ส่วนตัวชี้วัด
secondary รายงานทั้งหมดพร้อม multiplicity และข้อจำกัด การรายงานครบไม่ตัดความเสี่ยงจาก
การเลือกตีความหรือการเลือกวิธีวิเคราะห์ จึงต้องแยกผลยืนยันกับผลสำรวจให้ชัด

**เหตุผลที่ใช้ sign-flip เป็นสถิติหลัก:** เป็นการทดสอบที่ใช้จำนวนโจทย์เป็นหน่วยโดยตรง
และที่ k = 11 สามารถนับครบทั้ง 2,048 รูปแบบของการสลับเครื่องหมายได้จริง จึง exact
เมื่อสมมติฐานศูนย์ทำให้เครื่องหมายของผลต่างราย scenario แลกเปลี่ยนกันได้
(sign-exchangeability) การสุ่มลำดับ run ไม่ได้พิสูจน์สมมติฐานนี้

Wilson และ bootstrap ที่พิมพ์ในสรุป **ราย arm** เป็นช่วงพรรณนาและไม่ชดเชยการพึ่งพากัน
ภายใน scenario เอง ช่วงของ pairwise effects ที่ implement ใช้ scenario-cluster bootstrap
และ percentile bootstrap ที่มีเพียง 11 clusters อาจมี coverage ไม่ดี จึงต้องรายงานเป็นข้อจำกัด

**เหตุผลที่ต้องมี TOST:** เอกสารของงานนี้ระบุว่า A1 ≈ A3 จะเป็นข้อค้นพบที่มีน้ำหนักที่สุด
แต่การทดสอบความเหนือกว่าตอบคำถามนั้นไม่ได้ เพราะ **"ไม่มีนัยสำคัญ" ไม่เท่ากับ "เท่ากัน"**
ผลที่ไม่มีนัยสำคัญเกิดได้จากทั้งการไม่มีผลจริงและการมีอำนาจการทดสอบไม่พอ ซึ่งแยกกันไม่ออก
TOST ให้ผลสามทาง คือเท่ากันภายในกรอบ ต่างกันเกินกรอบ และ **สรุปไม่ได้**

### ขนาดตัวอย่างและเหตุผลของจำนวนรอบ

จาก `n_eff = k·m / (1 + (m−1)·ICC)` ที่ k = 11 และ ICC = 0.335

| รอบต่อโจทย์ (m) | run ต่อกลุ่ม | n_eff |
|---:|---:|---:|
| 4 | 44 | 21.9 |
| **6 (เลือกใช้)** | **66** | **24.7** |
| 9 | 99 | 26.9 |
| ∞ | ∞ | 32.8 |

การเพิ่มจาก 6 เป็น 9 รอบ ใช้ run เพิ่มอีก 33 run ต่อกลุ่ม เพื่อแลกกับค่าประมาณ `n_eff`
ที่เพิ่มขึ้นเพียง 9% จึงเลือก 6 รอบเพื่อสมดุล feasibility กับ precision ภายใต้เวลาที่มี
ตัวเลขนี้ **ไม่ใช่ power** และสูตร unpaired รุ่นเก่าไม่สามารถรับรอง power ของ primary ปัจจุบัน

**นัยเชิงวางแผน:** เมื่อ m เข้าใกล้อนันต์ `n_eff` ตามโมเดลนี้ลู่เข้าสู่ `k / ICC`
ซึ่งที่ k = 11 คือประมาณ 33 หน่วยต่อกลุ่ม การเพิ่มรอบยังช่วยประมาณผลราย scenario ได้ดีขึ้น
แต่ให้ผลตอบแทนลดลง; จำนวน scenario ยังคงจำกัด resolution และความครอบคลุมของข้อสรุป

**ขนาดการทดลองที่ configure: 5 กลุ่ม × 11 โจทย์ × 6 รอบ = 330 allocated cells**
จำนวน attempt อาจเกิน 330 และการเลือก attempt ต่อ cell ต้องเป็นไปตาม estimand/retry policy
ที่ผู้วิจัยยังไม่ได้อนุมัติ

> **ข้อจำกัดที่ต้องระบุตามตรง:** ค่า ICC = 0.335 วัดมาจากข้อมูลสอบเทียบบนโมเดลคนละตัว
> กับที่ใช้ในการทดลองหลัก จึงเป็น **ค่าสำหรับวางแผนเท่านั้น ไม่ใช่คำรับรองอำนาจการทดสอบ**
> ของการทดลองนี้ และต้องวัด ICC ใหม่จากข้อมูลจริงแล้วรายงานทั้งสองค่า ด้วย k = 11
> ทั้ง sign-flip และ bootstrap มี resolution/precision จำกัด จึงต้องรายงาน effect size และช่วง
> ความไม่แน่นอน รวมถึงผลที่งานยังตัดออกไม่ได้ แทนการอ้างว่ามี power ที่แสดงแล้ว

## 3.7 ตารางการอ่านผลที่กำหนดไว้ล่วงหน้า

ตารางนี้เขียนขึ้นก่อนเห็นข้อมูลเปรียบเทียบ เพื่อไม่ให้การตีความถูกกำหนดโดยผลที่ออกมา

| ผลที่ได้ | การตีความที่ประกาศไว้ |
|---|---|
| A2 > A1 อย่างมีนัยสำคัญ | จังหวะการโหลดกฎมีผลจริง เมื่อควบคุมเนื้อหากฎให้เท่ากัน |
| A2 − A1 ไม่มีนัยสำคัญ | สรุปไม่ได้ว่าเท่ากัน เพราะไม่ได้ลงทะเบียน equivalence procedure สำหรับคู่นี้ |
| A1 ≈ A3 (ผ่าน TOST) | ใกล้กันภายใน margin สำหรับ contextual control นี้; **ไม่พิสูจน์ว่ากฎไม่มีผล** เพราะ A3 อาจมีผลทางความหมาย |
| A1 > A3 | สอดคล้องกับกฎแบบ always-on ที่ดีกว่า contextual control นี้ แต่ยังไม่แยกทุกกลไก |
| A2 > A3 แต่ A1 ≈ A3 | เป็น pattern เชิงสำรวจ ไม่ใช่หลักฐานว่าผลมาจากโครงสร้างแทนจำนวน token โดยลำพัง |
| A4 − A2 ไม่มีนัยสำคัญ | สรุปไม่ได้ว่าทนเท่ากัน; รายงานช่วงและข้อจำกัดของโจทย์/attack ที่กำหนดไว้ |
| ตรวจพบ A4 − A2 | เป็นความต่างระหว่าง arm และ attack ที่กำหนดในงานนี้ ไม่ใช่ข้อสรุปทั่วไปว่ากฎกันสิ่งยั่วยุได้หรือไม่ได้ |

### กฎการรายงานที่ผูกมัดไว้ล่วงหน้า

1. **ผลที่ไม่มีนัยสำคัญต้องรายงานว่า "สรุปไม่ได้" ไม่ใช่ "ไม่ต่างกัน"** เว้นแต่ผ่าน TOST
2. **โจทย์ที่กลุ่มควบคุมทำได้เต็มอยู่แล้วต้องรายงานแยกชั้น** เพราะในโจทย์เหล่านั้น
   กลุ่มทดลองไม่มีทางชนะได้ในทางคณิตศาสตร์ เหลือเพียงเสมอหรือแพ้
   **แต่จะไม่ตัดโจทย์เหล่านั้นทิ้ง** เพราะการตัดข้อมูลหลังเห็นผลคือการเลือกข้อมูล
3. **ต้นทุน token ต้องรายงานคู่กับผลเสมอ** ผลที่ดีขึ้นโดยใช้ทรัพยากรมากขึ้นไม่ใช่ผลที่ดีขึ้น
4. **สมมติฐานรองเรื่องต้นทุน token รายงานไม่ว่าผลจะออกทางใด** ตามที่ผูกมัดไว้ตอนประกาศ
5. **ผลของกลุ่ม A4 ต้องแยกรายงานระหว่าง run ที่เอเจนต์เปิดไฟล์ที่มีข้อความล่อจริง
   กับ run ที่ไม่เคยเปิด** เพราะ run ที่ไม่เคยเปิดไม่ได้ถูกทดสอบเรื่องความทนทานเลย
   การนับมันเป็นผลสำเร็จจะเปลี่ยน *"ไม่เคยถูกทดสอบ"* ให้กลายเป็น *"ต้านทานได้"*

### ประตูตรวจสภาพก่อนเก็บข้อมูลเต็มชุด

หลังเก็บ repetition แรกครบ 55 run จะหยุดตรวจสภาพก่อนดำเนินการต่อ โดยตรวจเพียงสามเรื่อง
คือความครบของข้อมูล สภาพ runtime และช่วงการวัดของโจทย์

output ของประตูไม่แสดงผลต่างระหว่างกลุ่ม และผู้วิจัยรายงานว่าจะไม่ตรวจผลเปรียบเทียบระหว่างทาง
อย่างไรก็ดี นี่เป็น **แนวปฏิบัติไม่ตรวจดู ไม่ใช่ access-control หรือ blinding ที่บังคับได้**:
artifact ยังติดป้าย arm และผู้วิจัยเข้าถึงได้ การดูผลแล้วนำไปตัดสินใจยังถือเป็นการวิเคราะห์ระหว่างกาล

## สรุปบทที่ 3

งานนี้ใช้การทดลองแบบสุ่มมี 5 กลุ่ม บนโจทย์ 11 ข้อ 6 ตระกูล รวม 330 cells
โดยควบคุมเนื้อหาของกฎให้เท่ากันระหว่างกลุ่มควบคุมกับกลุ่มทดลองในระดับข้อผูกพันทั้ง 47 ข้อ
และมี contextual control จับคู่ความยาวเป็นการเปรียบเทียบเชิงสำรวจ โดยไม่อ้างว่า
semantic inertness ถูกพิสูจน์หรือว่าแยกผลของโครงสร้างออกจากเนื้อหาได้เด็ดขาด

แผนการวิเคราะห์ทั้งหมดถูกประกาศเป็นลายลักษณ์อักษรพร้อมวันที่ก่อนเก็บข้อมูลเปรียบเทียบ
และตัวแปรควบคุมทุกตัวถูกตรวจสอบซ้ำในทุก run แทนการประกาศไว้เฉย ๆ
ซึ่งเป็นมาตรการที่มาจากบทเรียนที่พบในโครงการนี้เองว่า **การเขียนตัวแปรควบคุมลงเอกสาร
ไม่ใช่การควบคุม ตราบใดที่ไม่มีสิ่งใดตรวจสอบมันทุกครั้งที่รัน**
