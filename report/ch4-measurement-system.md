## 4.1 สถาปัตยกรรมของระบบวัดผล

ระบบแบ่งเป็นห้าส่วนที่แยกความรับผิดชอบชัดเจน และไม่มีส่วนใดรู้จักรายละเอียดภายในของอีกส่วน

| ส่วน | หน้าที่ | ไฟล์ |
|---|---|---|
| **Adapter** | เรียกเอเจนต์จริงและแปลงผลให้เป็นรูปแบบกลาง | `src/adapters/claude-cli.mjs` |
| **Runner** | คุมการสุ่มลำดับ ติดตั้งบริบท เก็บผล ตรวจสภาพ และทำต่อเมื่อถูกขัดจังหวะ | `src/runner.mjs` |
| **Grader** | ให้คะแนนผลการทำงานตามกฎของแต่ละโจทย์ | `src/graders.mjs` |
| **Stats** | สูตรสถิติทั้งหมด แยกจากการนำเสนอ | `src/stats.mjs` |
| **Analyze** | ประกอบรายงานจากผลที่ให้คะแนนแล้ว | `src/analyze.mjs` |

### ลำดับการทำงานของหนึ่ง run

```
รีเซ็ต workspace กลับ baseline
  → ติดตั้งบริบทของกลุ่มทดลอง
  → วัดค่าตั้งต้นด้วยคำสั่ง probe
  → เรียกเอเจนต์พร้อมโจทย์
  → เก็บ tool call / คำสั่ง / diff / ข้อความตอบ / การใช้ token
  → วัดค่าปลายทางด้วยคำสั่ง probe เดิม
  → ตรวจสภาพ runtime เทียบกับ manifest
  → ให้คะแนน แล้วบันทึกลง checkpoint
```

การบันทึกเกิดขึ้น **ทุก run ไม่ใช่ตอนจบ** เพราะการเก็บข้อมูลชุดนี้ใช้เวลาหลายสิบชั่วโมง
และจะถูกขัดจังหวะแน่นอน ไม่ใช่อาจจะ — ทั้งจากโควตาที่หมด เครือข่ายที่หลุด และเครื่องที่หลับ

### เหตุผลที่แยกชั้น adapter ออกมา

หัวข้อของงานอ้างว่าวิธีการนี้ใช้กับเครื่องมือพัฒนาตัวใดก็ได้ ข้ออ้างนั้นจะน่าเชื่อ
ก็ต่อเมื่อการเปลี่ยนเครื่องมือทำได้โดยไม่ต้องแตะโจทย์ ตัวตรวจ หรือสถิติเลย
โครงสร้างจึงถูกออกแบบให้ทุกอย่างนอก adapter ทำงานกับ **รูปแบบผลลัพธ์กลาง** เท่านั้น

> **ข้อจำกัดที่ต้องระบุตามตรง:** งานนี้ยังไม่ได้พัฒนา adapter ตัวที่สอง
> ข้ออ้างเรื่องการนำไปใช้กับเครื่องมืออื่นจึงเป็น **ข้ออ้างเชิงโครงสร้าง ไม่ใช่ข้ออ้างที่พิสูจน์แล้ว**
> การทำ adapter ตัวที่สองคือหลักฐานที่ขาดอยู่ และถูกระบุไว้เป็นงานต่อในบทที่ 7

### การทำซ้ำได้

ระบบทั้งหมดเขียนด้วย JavaScript บน Node โดย **ไม่มีไลบรารีภายนอกแม้แต่ตัวเดียว**
ผู้ที่ต้องการทำซ้ำจึงต้องการเพียง Node กับเครื่องมือเอเจนต์ ไม่ต้องติดตั้งอะไรเพิ่ม
การสุ่มทุกจุดผูกกับ seed ที่กำหนดไว้ล่วงหน้า และผลดิบของทุก run ถูกเก็บไว้ทั้งหมด

## 4.2 ระบบจำลองที่ใช้เป็นสนามทดสอบ

สนามทดสอบคือระบบจองเวลาใช้งานหน่วยประมวลผลกราฟิกของศูนย์วิจัย ที่เขียนขึ้นใหม่ทั้งหมด
ด้วยสถาปัตยกรรมแบบเก็บลำดับเหตุการณ์ (event sourcing) ร่วมกับการแยกฝั่งอ่านและฝั่งเขียน (CQRS)

| ส่วน | บทบาทในการทดลอง |
|---|---|
| `data/events.jsonl` | บันทึกเหตุการณ์แบบต่อท้ายอย่างเดียว — เป็นแหล่งความจริงเดียวของระบบ |
| `src/domain/` | กฎธุรกิจและการเล่นเหตุการณ์ซ้ำเพื่อสร้างสถานะปัจจุบัน |
| `src/projections/` | มุมมองที่คำนวณใหม่จากเหตุการณ์ เช่น ตารางว่างและใบแจ้งหนี้ |
| `tools/revenue-report.ts` | คำสั่งที่ใช้วัดผลกระทบย้อนหลัง — เป็นหัวใจของการวัดกับดักตระกูล `hidden_impact` |

### เหตุผลที่ต้องเป็นสถาปัตยกรรมแบบนี้

ระบบที่เก็บผลลัพธ์ไว้ตรง ๆ จะแสดงความเสียหายจากการแก้ผิดออกมาเป็น error หรือ test แดง
แต่ระบบที่คำนวณใหม่ทุกครั้งจะไม่แสดงอะไรเลย — **การแก้ตรรกะการคำนวณเปลี่ยนตัวเลขของข้อมูล
ในอดีตทั้งหมดทันที โดยไม่มี error ไม่มีข้อมูลถูกแก้ และเทสเดิมยังผ่านครบ**

ใบแจ้งหนี้ที่ออกให้ผู้ใช้ไปแล้วเมื่อเดือนก่อน จะเปลี่ยนค่าเมื่อมีคนเปิดดูครั้งถัดไป

คุณสมบัตินี้ทำให้วัด "ความเสียหายที่มองไม่เห็น" ได้ด้วยตัวเลข โดยรันคำสั่งเดียวกัน
ก่อนและหลังการทำงานของเอเจนต์แล้วเทียบผล ซึ่งเป็นเงื่อนไขที่ตัวชี้วัดของงานนี้ต้องการ
และเป็นเหตุผลที่เลือกโดเมนนี้แทนโดเมนที่คุ้นเคยกว่าอย่างระบบ CRUD ทั่วไป

### ข้อกำหนดและเอกสารประกอบ

fixture มาพร้อมเอกสารข้อกำหนด 43 ข้อพร้อม acceptance criteria สัญญา API
และเอกสารสถาปัตยกรรมที่อธิบายเรื่องผลกระทบย้อนหลังไว้อย่างชัดเจน
เอกสารเหล่านี้เป็นสิ่งที่กฎของกลุ่มทดลองอ้างถึง และเป็นสิ่งที่เอเจนต์ต้องอ่านก่อนแก้

**เอกสารเหล่านี้เหมือนกันทุกกลุ่ม** ความต่างระหว่างกลุ่มอยู่ที่กฎการทำงาน ไม่ใช่ข้อมูลของระบบ

## 4.3 การติดตั้งบริบทของแต่ละกลุ่มทดลอง

ตัวแปรต้นทั้งหมดของการทดลองถูกส่งเข้าไปด้วยการวางไฟล์ลงใน workspace ก่อนเอเจนต์เริ่มทำงาน

| กลุ่ม | ไฟล์ที่ถูกวาง |
|---|---|
| A0 | ไม่มี |
| A1 | `CLAUDE.md` |
| A2 | `CLAUDE.md` + `.claude/skills/*/SKILL.md` จำนวน 4 ไฟล์ |
| A3 | `CLAUDE.md` (เนื้อหาไม่มีกฎ) |
| A4 | เหมือน A2 + แก้ไฟล์ในโค้ดของ fixture เพื่อฝังข้อความล่อ |

### กลไกรีเซ็ตและติดตั้ง

ทุก run เริ่มด้วยการรีเซ็ต fixture กลับสู่สถานะ baseline ที่ตรึงไว้ด้วย git tag
จากนั้นจึงติดตั้งไฟล์ของกลุ่ม แล้ว **commit ทับลงไปทันที**

การ commit ทับเป็นรายละเอียดที่ดูเล็กแต่จำเป็น เพราะถ้าไม่ทำ ไฟล์ของกลุ่มทดลอง
จะปรากฏใน `git status` และถูกนับเป็นไฟล์ที่เอเจนต์สร้างขึ้น ซึ่งจะทำให้
**ตัวชี้วัดการทำงานเกินขอบเขตเป็นบวกปลอมทุก run ทุกกลุ่ม**

หลังจบ run ไฟล์ของกลุ่มจะถูกถอนออก และ workspace ถูกรีเซ็ตอีกครั้งก่อน run ถัดไป

### หลักฐานว่าบริบทถูกติดตั้งจริง

ผลของทุก run บันทึกสถานะการติดตั้งไว้ด้วย ได้แก่ มีไฟล์ `CLAUDE.md` หรือไม่
มีไฟล์ skill กี่ไฟล์ และ `git status` สะอาดหลังติดตั้งหรือไม่

เหตุผลที่ต้องบันทึก: ในระยะแรกของการพัฒนาเคยเกิดกรณีที่ไฟล์กำหนดค่าประกาศบริบทของทุกกลุ่มไว้ครบ
แต่ไม่มีโค้ดส่วนใดอ่านไปใช้ ทุกกลุ่มจึงเจอ workspace เหมือนกันหมด
**และการทดลองยังให้ผลออกมาครบถ้วน มีช่วงความเชื่อมั่น มีค่า p เหมือนเดิมทุกประการ**
โดยไม่มีสิ่งใดเตือน — รายละเอียดของความล้มเหลวประเภทนี้อยู่ในหัวข้อ 4.5

## 4.4 ตัวตรวจกฎแบบกำหนดผลได้แน่นอน

### หลักการที่ห้ามละเมิด

> **ตัวตัดสินว่าผ่านหรือไม่ผ่านต้องเป็นโปรแกรม ไม่ใช่มนุษย์
> และต้องให้ผลเดิมทุกครั้งที่รันซ้ำบนข้อมูลเดียวกัน**

ถ้าใช้มนุษย์หรือใช้โมเดลภาษาเป็นผู้ตัดสิน ผลจะขึ้นกับผู้ตัดสิน และการทำซ้ำจะเป็นไปไม่ได้
ข้อกำหนดข้อนี้บังคับให้กฎทุกข้อต้องเขียนในรูปที่ตรวจด้วยโปรแกรมได้ ซึ่งจำกัดประเภทของกฎ
ที่งานนี้ศึกษาได้ และเป็นข้อจำกัดที่ต้องระบุในบทที่ 6

### ชนิดของตัวตรวจ

โจทย์ทั้ง 11 ข้อมีกฎรวม **105 ข้อ** ใช้ตัวตรวจ **17 ชนิด** แบ่งได้เป็นห้ากลุ่ม

| กลุ่ม | ชนิดตัวตรวจ | ตรวจอะไร |
|---|---|---|
| การเปลี่ยนแปลงโค้ด | `diff_matches` · `diff_not_matches` · `max_diff_lines` | เนื้อหาของ diff และขนาดของการเปลี่ยนแปลง |
| ขอบเขตไฟล์ | `files_within` · `files_not_touch` · `files_include` · `max_files_changed` | แตะไฟล์ไหนบ้าง และแตะเกินหรือไม่ |
| ผลกระทบที่มองไม่เห็น | `probe_unchanged` · `tests_pass` | ตัวเลขย้อนหลังเปลี่ยนหรือไม่ · ชุดทดสอบยังผ่านหรือไม่ |
| พฤติกรรมและการรายงาน | `text_matches` · `any_req_cited` · `all_reqs_cited` · `no_unrequested_feature` | อ้าง REQ-ID หรือไม่ · แจ้งข้อสังเกตหรือไม่ · เพิ่มฟีเจอร์ที่ไม่มีใครขอหรือไม่ |
| การใช้เครื่องมือ | `tool_called` · `tool_order` · `command_run` · `any_of` | เรียกเครื่องมือถูกจังหวะหรือไม่ · รันคำสั่งที่ห้ามหรือไม่ |

กฎแต่ละข้อมีระดับความรุนแรงเป็น `critical` หรือ `major` โดย `CRIT` คือการผ่านกฎ `critical` ครบทุกข้อ

### ตัวตรวจต้องเป็นฟังก์ชันบริสุทธิ์

ตัวตรวจทุกตัวรับผลดิบเข้าไปแล้วคืนค่าออกมา โดยไม่พึ่งเวลาปัจจุบัน ค่าสุ่ม หรือสถานะภายนอก
ข้อกำหนดนี้ทำให้เกิดความสามารถที่สำคัญมากข้อหนึ่ง คือ **การให้คะแนนซ้ำ** ในหัวข้อ 4.5

พร้อมกันนั้น ผลดิบของทุก run — รวมถึงบันทึกการทำงานทั้งหมดของเอเจนต์ — ถูกเก็บไว้ครบ
เงื่อนไขสองข้อนี้ต้องตัดสินใจ **ก่อน** เก็บข้อมูล เพิ่มทีหลังไม่ได้

## 4.5 กลไกตรวจสอบความถูกต้องของเครื่องมือวัด

หัวข้อนี้เป็นส่วนที่ใช้เวลาพัฒนามากที่สุด และเป็นส่วนที่นำไปใช้กับงานอื่นได้มากที่สุด

### ทำไมระบบวัดเอเจนต์จึงล้มเหลวแบบเงียบเป็นพิเศษ

ในระบบซอฟต์แวร์ทั่วไป ความผิดพลาดมักแสดงตัวออกมา โปรแกรมหยุดทำงาน ค่าเป็นค่าว่าง
หรือชุดทดสอบไม่ผ่าน แต่ในระบบที่ **สิ่งที่ถูกวัดคือเอเจนต์ซึ่งมีความสุ่มโดยธรรมชาติ**
กลไกนี้ใช้ไม่ได้ เพราะพฤติกรรมต่อไปนี้ล้วนเป็นพฤติกรรมปกติของเอเจนต์ที่ทำงานถูกต้อง

| สิ่งที่สังเกตเห็น | เมื่อเอเจนต์ทำงานปกติ | เมื่อเครื่องมือวัดพัง |
|---|---|---|
| ไม่แก้ไฟล์เลย | ตัดสินว่างานอยู่นอกขอบเขต | ไม่เคยได้รับโจทย์ |
| ตอบว่าโจทย์ไม่ชัดเจน | ขอคำยืนยันตามกฎ | ข้อความโจทย์ถูกตัดขาด |
| ข้อความตอบว่างเปล่า | — | โปรเซสถูกฆ่า |
| กฎข้อหนึ่งตกทุกครั้ง | โจทย์ยากจริง | รูปแบบการตรวจคอมไพล์ไม่ผ่าน |
| **ทุกกลุ่มได้ผลเท่ากัน** | **บริบทไม่มีผล — ข้อค้นพบ** | **ไม่เคยติดตั้งบริบทเลย** |

คอลัมน์กลางกับคอลัมน์ขวา **แยกจากกันไม่ได้เลยหากดูจากผลลัพธ์เพียงอย่างเดียว**
และคอลัมน์กลางคือสิ่งที่งานนี้ตั้งใจวัด ความกำกวมจึงไม่ใช่อุบัติเหตุ แต่เป็นคุณสมบัติของปัญหา

**แถวสุดท้ายคือแถวที่อันตรายที่สุด** เพราะผลลัพธ์ที่งานนี้ประเมินว่ามีน้ำหนักที่สุด
คือการที่กลุ่มที่มีกฎยาว ๆ ไม่ต่างจากกลุ่มยาหลอก ซึ่ง **มีหน้าตาเหมือนเครื่องมือวัดที่พังทุกประการ**
ถ้าไม่มีกลไกยืนยันว่าบริบทถูกติดตั้งจริง ผู้วิจัยจะไม่มีทางรู้ว่ากำลังรายงานข้อค้นพบ
หรือกำลังรายงานความล้มเหลวของเครื่องมือตัวเอง

### หลักการรับมือ: ป้อนข้อมูลที่รู้คำตอบล่วงหน้า

ข้อบกพร่องที่พบทั้งหมดในโครงการนี้ — **23 จุดที่บันทึกไว้ถึง 10 สิงหาคม และอีก 15 จุด
ที่พบในรอบตรวจวันที่ 4 กันยายน** — แทบไม่มีจุดใดที่การอ่านโค้ดจะจับได้
สิ่งที่จับได้จริงคือการป้อนข้อมูลที่รู้คำตอบอยู่แล้วเข้าไป แล้วตรวจว่าผลออกมาตรงหรือไม่

**ด่านตรวจที่รันได้โดยไม่ต้องเรียกใช้เอเจนต์และไม่มีค่าใช้จ่าย:**

| ด่าน | ป้อนอะไรที่รู้คำตอบ | จับอะไรได้ |
|---|---|---|
| `check-arms` | ติดตั้งบริบทของทุกกลุ่มลง fixture จริงแล้วล้างทิ้ง | ตัวแปรต้นไม่ถูกใส่ · รูปแบบตรวจที่คอมไพล์ไม่ผ่าน · ไฟล์ของกลุ่มปนเข้าผลวัด · ข้อผูกพันที่ขาดหายไปฝั่งใดฝั่งหนึ่ง |
| `check-spawn` | ส่งข้อความที่มีช่องว่าง เครื่องหมายคำพูด และอักขระพิเศษ ไปยังโปรแกรมที่พิมพ์สิ่งที่ได้รับออกมา | ข้อมูลนำเข้าไม่ถึงปลายทาง |
| `check-spec` | สแกนหาเฉลยของกับดักใน fixture | ข้อมูลรั่วจนการทดลองเป็นโมฆะ |
| `gate-analysis` | ชุดข้อมูลจำลอง วิ่งผ่านท่อวิเคราะห์ทั้งเส้น | ท่อวิเคราะห์พัง · รายงานไม่ตรงกับแผนที่ประกาศไว้ · ยอมรับข้อมูลที่ไม่ครบ |
| `regrade` | ให้คะแนนผลชุดเดิมซ้ำด้วยตัวตรวจฉบับปัจจุบัน | เกณฑ์การให้คะแนนเปลี่ยนกลางทางโดยไม่รู้ตัว |

**การทดสอบด้วยเอเจนต์ที่ไม่ทำอะไรเลย** เป็นข้อมูลสังเคราะห์ที่รู้คำตอบแน่นอน
ถ้าผลที่ไม่มีการเปลี่ยนแปลงใด ๆ ได้คะแนนสูง แปลว่าเกณฑ์การให้คะแนนมีปัญหา
วิธีนี้เปิดโปงพื้นเชิงโครงสร้างของ `RCR` ที่ค่า 0.552 ซึ่งไม่มีทางพบได้จากการอ่านโค้ด

### การให้คะแนนซ้ำ: แยก "เครื่องมือเปลี่ยน" ออกจาก "เอเจนต์เปลี่ยน"

หลักฐานที่สะอาดที่สุดที่พบในงานนี้มาจากการให้คะแนนผลชุดเดิมซ้ำหลังแก้ตัวตรวจ

กฎข้อหนึ่งของโจทย์ S07 วัดว่าเอเจนต์สังเกตความผิดปกติของโควตาหรือไม่
หลังแก้รูปแบบการตรวจ ผลเปลี่ยนจาก **ผ่าน 3 จาก 3 run เป็นตก 3 จาก 3 run**
โดยที่ **ข้อมูลดิบไม่เปลี่ยนแม้แต่ไบต์เดียว** เพราะไม่มีการเรียกเอเจนต์ใหม่เลย

เมื่อข้อมูลนำเข้าคงที่ ผลที่เปลี่ยนย่อมมาจากเครื่องมือวัดเท่านั้น
เป็นการพิสูจน์ว่ารูปแบบเดิมวัดผิดและรูปแบบใหม่วัดสิ่งที่ตั้งใจ โดยไม่มีค่าใช้จ่ายเพิ่ม

### การบังคับตัวแปรควบคุมในระดับ run

หลังพบว่าตัวแปรควบคุมสามตัวถูกประกาศไว้แต่ไม่เคยถูกบังคับจริง (รายละเอียดในบทที่ 3)
ระบบจึงเพิ่มกลไกสองชั้น

**ชั้นที่หนึ่ง — run manifest** บันทึกสภาพจริงจาก run แรกแล้วตรึงไว้
ได้แก่เวอร์ชันเครื่องมือ โมเดล ชุดเครื่องมือ ชุด skill พื้นฐาน แหล่งสิทธิ์เรียกใช้
และลายนิ้วมือของไฟล์ทุกไฟล์ที่นิยามการทดลอง

**ชั้นที่สอง — การตรวจแบบ fail-closed ทุก run** เทียบสภาพจริงกับ manifest
ไม่ตรงเมื่อใด **หยุดทั้งชุดทันทีพร้อมระบุว่าอะไรเปลี่ยน** ไม่ใช่บันทึกไว้แล้วรันต่อ

หลักการที่ได้จากการออกแบบส่วนนี้:

> **signature เก็บสิ่งที่ผู้ทดลองตั้งใจกำหนดเอง เปลี่ยนแล้วได้ชุดข้อมูลใหม่
> · manifest เก็บสิ่งที่เปลี่ยนได้เองโดยไม่มีใครสั่ง เปลี่ยนแล้วต้องหยุด**

หลักการข้อนี้มาจากความผิดพลาดจริงในการออกแบบรอบแรก ที่นำเวอร์ชันเครื่องมือไปใส่ใน signature
ซึ่งให้ผลตรงข้ามกับที่ตั้งใจ เพราะเมื่อเครื่องมืออัปเดตตัวเองระหว่างการเก็บข้อมูล
ระบบจะเปลี่ยนชื่อไฟล์บันทึกความคืบหน้าแล้ว **เริ่มเก็บชุดข้อมูลใหม่โดยเงียบ**
แทนที่จะหยุดเตือน ด่านที่เขียนไว้จึงไม่มีทางได้ทำงานเลยแม้แต่ครั้งเดียว

### การป้องกันการวิเคราะห์ที่อ่านผลผิด

ระบบวิเคราะห์มีด่านที่ปฏิเสธการทำงานในสามกรณี

1. **ข้อมูลไม่ครบทุกช่อง** ตรวจที่ระดับ (โจทย์ × กลุ่ม × รอบ) ว่ามีหนึ่งรายการพอดี
   ไม่ใช่ตรวจยอดรวม เพราะชุดข้อมูลที่มีช่องหนึ่งซ้ำและอีกช่องหายให้ยอดรวมเท่าเดิมพอดี
   แล้วการจับคู่จะทับกันเงียบ ๆ · ต้องระบุเจตนาอย่างชัดแจ้งจึงจะวิเคราะห์ข้อมูลไม่ครบได้
   และรายงานที่ได้จะถูกประทับหัวว่าห้ามนำไปอ้างเป็นผล
2. **ช่องข้อมูลซ้ำหรืออยู่นอกเมทริกซ์ที่ประกาศ** ปฏิเสธเสมอ ข้ามไม่ได้ทุกกรณี
   เพราะเป็นข้อมูลผิดรูป ไม่ใช่เพียงเก็บไม่ครบ
3. **ประตูตรวจสภาพหลังรอบแรก** ตรวจเพียงความครบ สภาพ runtime และช่วงการวัดของโจทย์
   **โดยไม่คำนวณคะแนนแยกกลุ่มเลย** ข้อห้ามนี้บังคับด้วยโปรแกรม ไม่ใช่ด้วยวินัย
   คือสคริปต์ไม่มีความสามารถในการพิมพ์ผลเปรียบเทียบออกมา และมีการทดสอบที่อ่านซอร์สโค้ด
   ของตัวเองเพื่อรักษาเงื่อนไขนี้ไว้

### สรุปหลักการที่นำไปใช้กับงานอื่นได้

1. **การทดสอบว่าระบบรันผ่านไม่เพียงพอ** ต้องทดสอบว่าข้อมูลเดินทางถึงปลายทางครบ
   และตัวตรวจให้คะแนนสิ่งที่ตั้งใจวัดจริง
2. **การประกาศตัวแปรควบคุมในไฟล์กำหนดค่าไม่ใช่การควบคุม** ตราบใดที่ไม่มีสิ่งใดตรวจสอบมันทุกครั้งที่รัน
3. **ด่านตรวจที่ผ่านได้เสมอแย่กว่าไม่มีด่าน** เพราะมันสร้างความมั่นใจที่ไม่มีอะไรรองรับ
   ตัวอย่างในงานนี้คือด่านที่ตรวจเพียงว่ารายงานยาวเกินจำนวนอักขระที่กำหนด
   ซึ่งผ่านได้แม้ระบบวิเคราะห์จะขัดกับแผนที่ประกาศไว้
4. **เก็บผลดิบทุก run และทำให้ตัวตรวจเป็นฟังก์ชันบริสุทธิ์** สองข้อนี้ตัดสินใจก่อนเก็บข้อมูลเท่านั้น
   เพิ่มทีหลังไม่ได้ และเป็นเงื่อนไขของการให้คะแนนซ้ำซึ่งเป็นเครื่องมือที่มีค่าที่สุดในการตรวจสอบตัวเอง

## 4.6 ส่วนขยายของระบบวัดผลสำหรับชุดที่ 2

หัวข้อนี้บรรยายสิ่งที่เพิ่มหรือแก้หลังชุดที่ 1 เสร็จ ทุกข้อมาจากข้อบกพร่องที่พบจริง
ไม่ใช่การปรับปรุงเชิงคาดเดา และแต่ละข้อระบุไว้ว่าพบได้อย่างไร

### 4.6.1 การติดป้าย "เข้าเงื่อนไข" ให้กฎแต่ละข้อ

ตัวให้คะแนนติดป้ายทุกกฎว่า **มีโอกาสตกได้จริงหรือไม่** ในการรันครั้งนั้น
กฎห้ามที่เกี่ยวกับการแก้ไฟล์ต้องมีไฟล์ถูกแก้อย่างน้อยหนึ่งไฟล์ · กฎห้ามเรื่องคำสั่ง
ต้องมีคำสั่งถูกรัน · กฎเชิงบวกเข้าเงื่อนไขเสมอเพราะการไม่ทำคือการตกจริง

สองรายละเอียดที่มาจากการรีวิวภายใน และทั้งคู่จำเป็น:

- **กฎที่ตกจริง ถือว่าเข้าเงื่อนไขเสมอ** ตามนิยาม มิฉะนั้นการละเมิดที่เกิดขึ้นจริง
  เช่นการ commit เปล่าซึ่งไม่มีไฟล์เปลี่ยน จะถูกตัดออกจากตัวชี้วัด = ให้รางวัลกับการละเมิด
- **กฎประกอบแบบ "หรือ" เข้าเงื่อนไขก็ต่อเมื่อข้อย่อยทุกข้อเข้าเงื่อนไข** เพราะการ "หรือ"
  จะตกได้ก็ต่อเมื่อข้อย่อยทุกข้อตก ถ้าใช้เกณฑ์ "ข้อใดข้อหนึ่ง" ข้อย่อยที่ผ่านแบบไม่มีอะไร
  ให้ตรวจจะลากทั้งกฎกลับไปเป็น "ผ่าน" ซึ่งเป็นข้อบกพร่องเดิมที่ย้ายมาซ่อนในตัวประกอบ

### 4.6.2 ด่านพื้นของตัวชี้วัด — ออกแบบให้ล้มได้

`scripts/check-rcra-floor.mjs` ป้อน artifact สังเคราะห์สามแบบเข้าตัวตรวจทุกโจทย์
แล้วบังคับเกณฑ์ที่ประกาศไว้ล่วงหน้า รันอยู่ใน `npm run gate`

| เคส | สิ่งที่มันพิสูจน์ | เกณฑ์ |
|---|---|---|
| ไม่ทำอะไรเลย | กฎที่ผ่านเพราะไม่มีอะไรให้ตรวจ | `RCRc` ≤ 0.05 ทุกโจทย์ |
| ขี้เกียจแต่ไม่นิ่ง — แก้ไฟล์เดียว รันคำสั่ง ตอบข้อความน่าเชื่อ งานไม่สำเร็จ | ตัวชี้วัดให้รางวัลกับการลงมือทำหรือไม่ | `RCRc` ≤ 0.05 ทุกโจทย์ |
| ป่าเถื่อนแต่ทำงานสำเร็จ — ผ่านเทสยอมรับ แต่ละเมิดกฎห้ามทุกข้อ | ตัวชี้วัดตอบสนองต่อเนื้อหาของกฎหรือไม่ | `RCRc` ≤ 0.50 **และต้อง > 0 อย่างน้อยหนึ่งโจทย์** |

เคสที่สามถูกเพิ่มหลังผู้รีวิวชี้ว่าด่านที่มีแต่สองเคสแรก **เป็นการพิสูจน์ตัวเองโดยเลขคณิต**:
ทั้งคู่สร้างจาก "งานไม่สำเร็จ" และ `RCRc` คูณด้วยความสำเร็จของงาน artifact ทุกตัว
ในตระกูลนั้นจึงได้ 0.000 เสมอไม่ว่าเนื้อในจะเป็นอะไร

เพดาน 0.50 ของเคสที่สามมาจากหลักการ "ละเมิดกฎห้ามทุกข้อแล้วต้องตกกฎวิกฤตเกินครึ่ง"
ครั้งแรกตั้งไว้ที่ 0.35 แล้ววัดได้สูงสุด 0.444 — **การขยับเพดานให้พอดีกับตัวเลขที่เพิ่งเห็น
คือการตั้งเกณฑ์หลังเห็นข้อมูล** จึงเปลี่ยนไปตั้งจากหลักการที่พูดเป็นประโยคได้แทน
และบันทึกไว้ในโค้ดว่าเคยตั้งผิดมาก่อน

ด่านยังบังคับด้วยว่า **ทุกโจทย์ต้องมีนิยามของ "งานหลักสำเร็จ"** มิฉะนั้นจำนวนโจทย์
ที่เข้าตัวชี้วัดหลักจะลดลงเงียบ ๆ ซึ่ง `k` คือเพดานของกำลังการทดสอบทั้งการทดลอง

### 4.6.3 แยก "เรียก skill" ออกจาก "skill เข้าบริบท"

เดิมระบบนับทุกครั้งที่เอเจนต์เรียกเครื่องมือ `Skill` ว่าโหลดสำเร็จ ซึ่งผิดเมื่อการเรียกล้มเหลว

ของจริงที่พบตอนเริ่มเก็บชุดที่ 2: A5 ไม่มี skill ติดตั้งไว้เลย แต่เรียก `Skill` สองครั้ง
แล้วได้ `Unknown skill` กลับมาทั้งคู่ **ไม่มีอะไรเข้าบริบทเลย** แต่ artifact บันทึกว่า
โหลดไปสองตัว ทำให้ด่านตรวจการปนเปื้อนหยุดการทดลองทั้งชุดเพราะสิ่งที่ไม่เคยเกิดขึ้น
และจะทำให้ตัวชี้วัด Trigger F1 นับการเรียกที่ล้มเหลวเป็นการโหลดด้วย

ตอนนี้ `loadedSkills` แปลว่า **เรียกแล้วผลลัพธ์ไม่ใช่ error** (ไม่มีผลลัพธ์จับคู่ = ถือว่าไม่สำเร็จ)
และเก็บ `skillInvocations` แยกไว้รายงานเจตนา ส่วน skill นอกการทดลองยังจับที่การเรียก
เหมือนเดิม เพราะแค่พยายามเรียกก็ผิดแล้ว

**ตรวจย้อนหลังก่อนสรุปว่ากระทบตัวเลขเดิมหรือไม่:** ชุดที่ 1 เรียก `Skill` รวม 225 ครั้ง
ล้มเหลว 0 ครั้ง **ตัวเลข Trigger F1 ที่รายงานไว้จึงไม่กระทบ**

### 4.6.4 แผนการวิเคราะห์ที่โค้ดทำตามจริง

ก่อนแก้ ตัวชี้วัดหลักและตัวชี้วัดร่วมถูกเขียนตายไว้ในโปรแกรมวิเคราะห์เป็นตัวอักษร
ผลคือต่อให้ประกาศแผนของชุดที่ 2 ไว้อย่างไร รายงานก็จะพิมพ์ลำดับชั้นของชุดที่ 1 ออกมา
**แผนที่ประกาศไว้แล้วไม่มีโค้ดตัวไหนทำตาม คือวิธีที่ pre-registration กลายเป็น
"คำนวณเองทีหลัง" ได้เนียนที่สุด**

ตอนนี้ลำดับชั้นของ endpoint หัวข้อในรายงาน ชื่อคอลัมน์ และชื่อเอกสารประกาศแผน
ล้วนอ่านจากไฟล์นิยามการทดลองที่ `--config` ชี้ และการเปรียบเทียบแบบจับคู่ตัดค่า
ที่วัดไม่ได้ (null) ออกแทนที่จะแปลงเป็นศูนย์หรือกลายเป็น NaN เงียบ ๆ

### 4.6.5 การแยกชุดข้อมูลสองชุดออกจากกัน

นิยามการทดลองของชุดที่ 2 อยู่ใน `config/arms-study2.json` และผลอยู่ใน `results-study2/`
เพราะ `configPath` เป็นส่วนหนึ่งของลายเซ็นของ checkpoint ทั้งสองชุดจึงได้ checkpoint
และ manifest คนละก้อนโดยอัตโนมัติ ชุดที่ 1 วิเคราะห์ซ้ำได้จากไฟล์เดิมเสมอ

ไฟล์นิยามการทดลองของ **ทั้งสองชุด** อยู่ใน digest ที่ตรวจทุก run — ถ้ารายการนี้
ไม่ตามไปด้วย ไฟล์ที่นิยามชุดที่ 2 จะอยู่นอก digest และแก้ระหว่างเก็บข้อมูลได้
โดยไม่มีอะไรหยุด ซึ่งเป็นช่องเดียวกับที่กลไกนี้ถูกสร้างมาเพื่อปิด

การลดชั้นกฎในชุดที่ 2 แก้ไฟล์โจทย์โดยตรง ชุดโจทย์ที่ใช้ตอนเก็บชุดที่ 1 จึงถูกคัดลอก
ไว้ที่ `evidence/study1-scenarios/` และเครื่องมือให้คะแนนใหม่ **ปฏิเสธการทำงาน**
เมื่อชุดโจทย์ที่เลือกไม่ตรงกับ digest ที่ตรึงไว้ใน manifest — กฎที่ไม่มีกลไกบังคับ
คือกฎที่จะถูกลืมในวันที่เหนื่อย

### 4.6.6 บทเรียนร่วมของข้อบกพร่องชุดนี้

ข้อบกพร่องที่พบในรอบนี้สี่ข้อมีรูปแบบเดียวกันทั้งหมด — **ด่านตรวจที่เล็งผิดที่**

| ด่าน | เล็งไปที่ | ควรเล็งไปที่ |
|---|---|---|
| ตรวจความพร้อมก่อนรัน | `results/` เสมอ | โฟลเดอร์ของชุดที่กำลังจะรัน |
| กันไม่ให้เครื่องมืออื่นแตะ fixture ระหว่างเก็บข้อมูล | checkpoint ใน `results/` เท่านั้น | ทุกโฟลเดอร์ผลลัพธ์ |
| ตรวจความเท่าเทียมของเนื้อหา arm | A1 กับ A2 | ทุก arm ที่อ้างว่าบรรจุกฎชุดเดียวกัน รวม A5 |
| ตรวจการปนเปื้อนของ skill | การเรียก | การเข้าบริบทจริง |

**ด่านที่เล็งผิดที่อันตรายกว่าไม่มีด่านเลย เพราะมันตอบว่าปลอดภัย** ข้อนี้เป็นบทเรียน
เชิงระเบียบวิธีที่ใช้ได้นอกเหนือจากงานนี้ และควรอ่านคู่กับหัวข้อ 4.5 ซึ่งบอกว่า
ระบบวัดเอเจนต์ล้มเหลวแบบเงียบเป็นพิเศษ

## สรุปบทที่ 4

ระบบวัดผลถูกออกแบบให้ทุกส่วนแยกความรับผิดชอบ ตัวตัดสินเป็นโปรแกรมที่ให้ผลเดิมทุกครั้ง
และผลดิบถูกเก็บไว้ครบเพื่อให้ตรวจสอบย้อนหลังได้

ข้อบกพร่องที่พบระหว่างเตรียมชุดที่ 2 ทั้งสี่ข้อมีรูปแบบเดียวกัน คือ **ด่านตรวจที่เล็งผิดที่**
ซึ่งรายงานว่าปลอดภัยทั้งที่ไม่ได้มองสิ่งที่ควรมอง — อันตรายกว่าการไม่มีด่านเลย

ส่วนที่ใช้เวลาพัฒนามากที่สุดไม่ใช่การเรียกเอเจนต์หรือการคำนวณสถิติ
แต่เป็น **กลไกที่ทำให้เชื่อได้ว่าเครื่องมือวัดเองไม่ได้พัง** ซึ่งเป็นปัญหาที่รุนแรงเป็นพิเศษ
ในการวัดสิ่งที่มีความสุ่มโดยธรรมชาติ เพราะความล้มเหลวของเครื่องมือกับปรากฏการณ์ที่น่าสนใจ
ให้ตัวเลขที่มีหน้าตาเหมือนกันทุกประการ
