## 6.1 อภิปรายผล

หัวข้อนี้ตอบสมมติฐานที่ประกาศไว้ในบทที่ 1 แล้วอภิปรายว่าผลทั้งสองชุดบอกอะไร
**ตัวเลขทุกตัวอ้างจากบทที่ 5 ของชุดนั้น ๆ ไม่มีการคำนวณใหม่ในบทนี้**

### 6.1.1 คำตอบต่อสมมติฐาน H1–H4

| | สมมติฐาน | คำตอบ |
|---|---|---|
| **H1** | กฎรูปลำดับ ข้อห้าม และขอบเขตเชิงตัวเลข มีอัตราการปฏิบัติตามสูงกว่ากฎรูปค่านิยม | **ทดสอบไม่ได้** — ไม่มีกฎรูปค่านิยมอยู่ในเครื่องมือวัดเลยแม้แต่ข้อเดียว |
| **H2** | โครงสร้างการจัดวางกฎมีผลต่อการปฏิบัติตาม เมื่อควบคุมเนื้อหาและความยาวแล้ว | **สรุปไม่ได้** ทั้งสองชุด |
| **H3** | ผลของจำนวนกฎที่โหลดพร้อมกัน (rule dilution) | **ไม่ได้เก็บข้อมูลจริง** ประกาศไว้ตั้งแต่ต้นว่าเป็นงานต่อยอด |
| **H4** | กลุ่มที่มีกฎใช้ token ต่องานน้อยกว่ากลุ่มที่ไม่มีกฎ | **ไม่สนับสนุน** และผลไปคนละทางกับที่ทำนาย |

**สมมติฐานสี่ข้อ ตอบได้จริงเพียงสองข้อ และทั้งสองข้อไม่ได้ผลอย่างที่คาด**
นี่คือข้อเท็จจริงที่ต้องเขียนไว้ตรง ๆ ก่อนอภิปรายรายละเอียด

#### H1 — ทดสอบไม่ได้ และเหตุผลอยู่ที่การออกแบบเครื่องมือ ไม่ใช่ที่ข้อมูล

H1 เปรียบเทียบกฎสองรูปแบบ แต่เมื่อไล่ตรวจกฎทั้ง 137 ช่องในโจทย์ 11 ข้อ
**ไม่มีกฎรูปค่านิยมอยู่เลยแม้แต่ข้อเดียว** ตัวตรวจทั้ง 20 ชนิดที่ใช้จริง
ล้วนตรวจสิ่งที่ชี้ขาดได้ เช่น ไฟล์ใดถูกแก้ · มีข้อความใดในบรรทัดที่เพิ่ม ·
เทสยอมรับผ่านหรือไม่ · มีคำสั่งใดถูกรัน

เหตุผลไม่ใช่ความบังเอิญ แต่เป็นผลโดยตรงจากข้อบังคับที่งานนี้ตั้งไว้เองว่า
**ตัวตรวจทุกตัวต้องเป็นโปรแกรมที่ให้ผลเดิมทุกครั้ง ห้ามใช้คนหรือ LLM ตัดสิน**
กฎอย่าง "เขียนโค้ดให้สะอาด" ไม่มีทางแปลงเป็นตัวตรวจแบบนั้นได้โดยไม่เปลี่ยน
ความหมายของมันไปเป็นอย่างอื่น

> **ข้อบังคับที่ทำให้ตัวเลขทั้งเล่มเชื่อถือได้ คือข้อเดียวกับที่ทำให้ H1 ทดสอบไม่ได้**

นี่ไม่ใช่ข้อบกพร่องที่ซ่อมได้ด้วยการเก็บข้อมูลเพิ่ม แต่เป็นการแลกที่ต้องยอมรับ
และควรนับเป็นข้อค้นพบเชิงระเบียบวิธี: **การยืนกรานว่าตัวตรวจต้องกำหนดผลได้แน่นอน
จำกัดขอบเขตของคำถามที่ถามได้ไปด้วย** ใครที่จะศึกษากฎรูปค่านิยมต้องยอมรับ
ผู้ตัดสินที่เป็นมนุษย์หรือ LLM พร้อมกับปัญหาความน่าเชื่อถือที่ตามมา

#### H2 — สรุปไม่ได้ทั้งสองชุด และนี่คือผลหลักของงาน

H2 คือคำถามวิจัยหลักโดยตรง ผลของทั้งสองชุดเป็นบวกในทิศทางของ skill
แต่ช่วงความเชื่อมั่นคร่อมศูนย์ทั้งคู่

| | ผลต่าง | 95% CI | p |
|---|---:|---|---:|
| ชุดที่ 1 (`CRIT`) | +9.1 จุด | [−6.8%, +27.3%] | 0.500 |
| ชุดที่ 2 (`RCRc`) | +11.0 จุด | [−2.1%, +27.5%] | 0.250 |

**ทั้งสองชุดสรุปไม่ได้ด้วยเหตุผลเดียวกัน คือจำนวนโจทย์ที่ให้ข้อมูลน้อยเกินไป**
ทั้งสองชุดเหลือโจทย์ที่ผลต่างไม่เป็นศูนย์ `m` = 5 ข้อจาก 11 เท่ากันพอดี (ชนะ 3 แพ้ 2 เสมอ 6)
ค่า p ต่ำสุดที่การออกแบบมีทางได้จึงเท่ากับ `2^(1−5)` = 0.0625 **เท่ากันทั้งสองชุด**
ซึ่งสูงกว่าเกณฑ์ 0.05 **นัยสำคัญจึงเป็นไปไม่ได้ทางคณิตศาสตร์ในทั้งสองชุด**
**ตั้งแต่ก่อนเห็นข้อมูล** ไม่ว่าขนาดของผลจริงจะใหญ่เพียงใด

สิ่งที่การซ่อมตัวชี้วัดทำได้จริงคือทำให้**ค่าประมาณคมขึ้น** ค่า p ที่สังเกตได้ลดจาก
0.500 เหลือ 0.250 และขอบล่างของช่วงความเชื่อมั่นขยับจาก −6.8% เป็น −2.1%
**แต่ไม่ได้ขยับเพดาน** เพราะเพดานขึ้นกับ `m` เท่านั้น และ `m` ไม่เปลี่ยน
PRE-REGISTRATION-2 §7 คาดไว้ล่วงหน้าว่า `m` จะอยู่ราว 6 และเขียนไว้ตรง ๆ ว่า
**ถ้า `m` จริงต่ำกว่า 6 นัยสำคัญจะเป็นไปไม่ได้** ซึ่งเป็นสิ่งที่เกิดขึ้นจริง

> **บันทึกการแก้ไข · 21 กันยายน 2569** — ฉบับก่อนหน้าของหัวข้อนี้เขียนว่าชุดที่ 1
> มีเพดาน p เท่ากับ 0.063 และชุดที่ 2 ลดเหลือ 0.0625 จึง "เป็นไปได้จริงแล้ว"
> **ข้อความนั้นผิด** 0.063 กับ 0.0625 คือเลขตัวเดียวกันที่ปัดคนละแบบ
> ทั้งสองชุดมี `m` = 5 เท่ากัน เพดานจึงไม่เคยขยับ ข้อความเดิมถูกแทนที่ด้วย
> ข้อความข้างบนนี้ ส่วนตัวเลขผลการทดลองไม่มีข้อใดเปลี่ยน

H2 ยังระบุเงื่อนไข **"เมื่อควบคุมเนื้อหาและความยาวแล้ว"** ซึ่งชุดที่ 2 พยายามตอบด้วย
กลุ่ม A5 ที่ถือข้อความชุดเดียวกับ A2 แต่โหลดตลอดเวลา ผลของคู่นี้
**ไม่ถูกทดสอบตามลำดับที่ประกาศไว้** เพราะผลหลักไม่ผ่านประตู
ค่าที่รายงานเชิงพรรณนาคือ A5 ได้ 52.7% เทียบ A2 ที่ 61.5%

#### H3 — ไม่ได้เก็บข้อมูล และห้ามอ้างตัวเลขที่มี

บทที่ 1 ประกาศไว้ตั้งแต่ต้นว่า H3 ไม่อยู่ในชุดข้อมูลหลัก ออกแบบและตรวจด้วย
mock adapter แล้วเท่านั้น **ตัวเลขที่มีอยู่ทั้งหมดมาจากข้อมูลจำลอง ห้ามอ้าง
ในเล่มและบนสไลด์** ตามที่ระบุไว้ในหัวข้อข้อมูลที่ถูกกันออกโดยเจตนา

การที่ H3 ยังไม่ถูกทดสอบเป็นเรื่องของงบเวลาและโควตา ไม่ใช่เรื่องของการออกแบบ
จึงเป็นงานต่อยอดที่ทำได้จริงด้วยเครื่องมือชุดนี้โดยไม่ต้องสร้างอะไรใหม่

#### H4 — ไม่สนับสนุน และผลไปคนละทางกับที่ทำนาย

H4 ทำนายว่ากลุ่มที่มีกฎจะใช้ token ต่องานน้อยกว่ากลุ่มที่ไม่มีกฎ
โดยกลไกที่เสนอคือเอเจนต์ที่ไม่มีขอบเขตต้องสำรวจ repository เองมากกว่า

**ผลจริง ทั้งสองชุดไปทางเดียวกัน และไม่ตรงกับที่ทำนาย**

| ชุดที่ 2 | A0 ไม่มีกฎ | A1 ไฟล์เดียว | A2 skill |
|---|---:|---:|---:|
| token ขาเข้าเฉลี่ยต่อ run | 932,247 | **792,793** | 938,864 |
| จำนวน tool call เฉลี่ย | 24.0 | **21.1** | 23.4 |
| ต้นทุนเทียบเท่าต่อ run | **0.6749** | 0.6949 | 0.6966 |

- **A1 ใช้ token น้อยกว่า A0 จริงตามที่ทำนาย** และเรียก tool น้อยกว่าด้วย
  ซึ่งสอดคล้องกับกลไกที่เสนอไว้ว่าขอบเขตช่วยลดการสำรวจ
- **แต่ A2 ใช้ token มากกว่า A0** ทั้งที่มีกฎเนื้อหาเดียวกับ A1
- **ต้นทุนรวมต่อ run ของทั้ง A1 และ A2 สูงกว่า A0** ทั้งคู่

ชุดที่ 1 ให้รูปแบบเดียวกัน: A0 ใช้ 974,136 token ขณะที่ A1 ใช้ 911,912 (น้อยกว่า)
และ A2 ใช้ 1,015,939 (มากกว่า) ส่วนต้นทุนต่อ run ของ A0 ต่ำที่สุดเช่นกัน

**การตีความ:** ถ้ากลไกที่ H4 เสนอถูกต้อง มันควรได้ผลกับทุกกลุ่มที่มีกฎ ไม่ใช่เฉพาะ A1
การที่ A2 สวนทางทั้งที่มีกฎเนื้อหาเดียวกัน ชี้ว่าสิ่งที่กำหนดต้นทุนไม่ใช่
"มีขอบเขตหรือไม่มี" อย่างเดียว แต่มีอย่างอื่นที่ยังไม่รู้ร่วมอยู่ด้วย
**ทั้งหมดนี้เป็นการรายงานเชิงพรรณนา ไม่ได้ทดสอบทางสถิติ** เพราะ H4
ถูกประกาศไว้เป็น secondary ที่รายงานอย่างเดียว ไม่ได้อยู่ในลำดับที่อ้างนัยสำคัญได้

### 6.1.2 ผลหลักสองชุดบอกอะไรเมื่ออ่านคู่กัน

**สิ่งที่พูดได้:** ภายใต้เงื่อนไขของงานนี้ การจัดวางกฎแบบ skill ให้ผลเป็นบวก
เมื่อเทียบกับไฟล์เดียวทั้งสองครั้ง ขนาดผลที่ประมาณได้อยู่ราว 9–11 จุด

**สิ่งที่พูดไม่ได้:** ว่าผลนั้นต่างจากศูนย์ — ช่วงความเชื่อมั่นคร่อมศูนย์ทั้งคู่
และต้องเขียนว่า **"สรุปไม่ได้" ไม่ใช่ "ไม่ต่างกัน"** เพราะการออกแบบ
ไม่มีกำลังพอจะแยกสองอย่างนี้ออกจากกัน

**สิ่งที่การทำสองชุดเพิ่มเข้ามาจริง ๆ** คือการแยกสาเหตุของผล null ออกได้
ผล null ครั้งเดียวตีความไม่ได้ว่ามาจากเครื่องมือหรือมาจากปรากฏการณ์
การซ่อมเครื่องมือแล้วทำซ้ำทำให้ตอบได้ว่า **อุปสรรคย้ายจาก "เป็นไปไม่ได้"
มาเป็น "ไม่พอ"** ซึ่งเปลี่ยนคำแนะนำสำหรับงานถัดไปจาก "ซ่อมเครื่องมือวัด"
เป็น "เพิ่มจำนวนโจทย์"

### 6.1.3 ข้อสังเกตที่สำคัญที่สุดจากข้อมูล — กฎแลกความสำเร็จกับความสอดคล้อง

ตัวชี้วัดของชุดที่ 2 แยกออกเป็นสองส่วนได้ และสองส่วนจัดอันดับกลุ่มไม่เหมือนกัน

| กลุ่ม | ทำงานสำเร็จ | ตามกฎเมื่อทำสำเร็จ |
|---|---:|---:|
| A0 ไม่มีกฎ | **75.0%** | 0.895 |
| A1 ไฟล์เดียว | 52.3% | **0.967** |
| A2 skill | 63.6% | **0.967** |
| A5 ข้อความเดียวกับ A2 | 54.5% | **0.967** |

**กลุ่มที่มีกฎทุกกลุ่มตามกฎได้ดีกว่า และได้เท่ากันหมดที่ 0.967
ขณะที่กลุ่มที่ไม่มีกฎทำงานสำเร็จมากที่สุด**

ถ้ารูปแบบนี้เป็นจริง มันตอบคำถามที่คนใช้งานถามจริงมากกว่าคำถามว่ากลไกไหนดีกว่า:
**กฎไม่ได้ทำให้เอเจนต์เก่งขึ้น แต่ทำให้มันอยู่ในกรอบมากขึ้น โดยแลกกับ
การทำงานให้เสร็จ** ซึ่งเป็นการแลกที่ผู้ใช้ควรรู้ตัวว่ากำลังทำอยู่

**ข้อจำกัดที่ต้องอ่านคู่กันเสมอ สามข้อ**

1. **ไม่ได้ทดสอบทางสถิติ** และการทดสอบแต่ละส่วนแยกกัน**ไม่ได้ประกาศไว้ล่วงหน้า
   จึงเพิ่มทีหลังไม่ได้** ตัวเลขข้างบนเป็นค่าเชิงพรรณนาล้วน
2. **A0 ถูกประกาศไว้ว่าเป็นกลุ่มเชิงพรรณนา** ไม่ใช่คู่เปรียบเทียบที่อ้างนัยสำคัญได้
3. กำลังการทดสอบที่ไม่พอสำหรับตัวชี้วัดหลัก ก็ไม่พอสำหรับส่วนย่อยของมันเช่นกัน

**จึงเป็นสมมติฐานที่ข้อมูลชี้ทาง ไม่ใช่ข้อสรุป** และควรเป็นสมมติฐานหลัก
ของการทดลองชุดถัดไป โดยประกาศให้สองส่วนเป็น endpoint คนละตัวตั้งแต่ต้น

### 6.1.4 กลไกทำงาน แต่ผลปลายทางไม่ขยับ — ตีความอย่างไร

ความแม่นของการยิง skill ในชุดที่ 2 อยู่ในระดับสูง `trace-to-requirement` = 1.000 ·
`acceptance-first` = 0.842 · `impact-analysis` = 0.872 **skill ถูกโหลดตรงจังหวะที่ควรโหลด**

เมื่ออ่านคู่กับผลหลักที่สรุปไม่ได้ ข้อความที่ได้คือ **ปัญหาไม่ได้อยู่ที่การส่งกฎ
ถึงเอเจนต์** กลไก progressive disclosure ทำงานตามที่โฆษณาไว้ในระดับที่วัดได้

คำอธิบายที่เป็นไปได้สามทาง ซึ่งข้อมูลชุดนี้แยกออกจากกันไม่ได้:

1. **ผลจริงมีแต่เล็กเกินกว่าโจทย์ 11 ข้อจะจับได้** — เข้ากันได้กับทิศทางบวกทั้งสองชุด
2. **ผลจริงเล็กมากหรือไม่มี** — การได้กฎถึงมือไม่ได้แปลว่าเอเจนต์ทำตาม
3. **ตัวชี้วัดกลบผล** — ตามที่หัวข้อ 6.1.3 แสดงว่าสองส่วนเดินคนละทางและหักล้างกัน

ข้อ 3 เป็นคำอธิบายที่ข้อมูลสนับสนุนมากที่สุดในตอนนี้ และเป็นเหตุผลที่
ข้อเสนอแนะหลักของบทที่ 7 คือให้แยก endpoint ออกเป็นสองตัวตั้งแต่ต้น

### 6.1.5 สิ่งที่ผลนี้บอกกับคนที่ต้องเขียนกฎให้เอเจนต์จริง

งานนี้ตอบคำถามว่า "skill หรือ context ดีกว่ากัน" ไม่ได้ แต่มีสามข้อที่พูดได้
จากสิ่งที่วัดมา และทั้งสามข้อมาพร้อมขอบเขตของมันเอง

1. **ถ้าเป้าหมายคือให้เอเจนต์อยู่ในกรอบ กฎช่วยได้จริง** ทุกกลุ่มที่มีกฎ
   ตามกฎได้ดีกว่ากลุ่มที่ไม่มีอย่างเห็นได้ชัด และได้เท่ากันไม่ว่าจะจัดวางแบบใด
2. **แต่ต้องรู้ว่ากำลังแลกอะไร** กลุ่มที่ไม่มีกฎทำงานสำเร็จบ่อยกว่าอย่างมีนัยเชิงปฏิบัติ
   ในข้อมูลชุดนี้ · *(ข้อ 1 และ 2 เป็นค่าเชิงพรรณนา ไม่ได้ทดสอบทางสถิติ)*
3. **การเลือกวิธีจัดวางกฎอาจไม่ใช่ตัวแปรที่คุ้มกับเวลาที่ใช้ถกเถียง** —
   ความต่างระหว่าง skill กับไฟล์เดียวเล็กเกินกว่าจะวัดได้ด้วยการทดลองขนาดนี้
   ขณะที่ความต่างระหว่าง "มีกฎ" กับ "ไม่มีกฎ" เห็นได้ชัดกว่ามาก

**สิ่งที่งานนี้บอกไม่ได้เลย** คือกฎชุดอื่น โจทย์ประเภทอื่น โมเดลอื่น
หรือเครื่องมืออื่นจะให้ผลแบบเดียวกันหรือไม่

## 6.2 ข้อจำกัดของการวิจัย

> เลขหัวข้อย่อยในส่วนนี้คงไว้เป็น `6.x.N` ตามเดิมโดยเจตนา เพราะบทที่ 3 4 และ 7
> อ้างถึงด้วยเลขเหล่านี้อยู่แล้ว การเปลี่ยนเลขจะทำให้การอ้างอิงข้ามบททั้งเล่มผิด

### 6.x.1 ข้อจำกัดเชิงกำลังการทดสอบ — ข้อที่หนักที่สุด

**จำนวนโจทย์เป็นเพดาน ไม่ใช่จำนวนรอบ**

การทดสอบหลักเป็น exact sign-flip permutation ที่ระดับโจทย์ หน่วยข้อมูลจึงเป็น **โจทย์**
ไม่ใช่ run การเพิ่มจำนวนรอบต่อโจทย์ช่วยให้ค่าประมาณของแต่ละโจทย์แม่นขึ้น
แต่ไม่ได้เพิ่มจำนวนหน่วยอิสระ ซึ่งคงที่อยู่ที่ 11

ผลที่ตามมาเป็นเรื่องเลขคณิตล้วน ๆ: หากโจทย์ที่ทุกกลุ่มได้คะแนนเท่ากันมีค่าผลต่างเป็นศูนย์
การสลับเครื่องหมายของศูนย์ไม่เปลี่ยนค่าสถิติ โจทย์นั้นจึงไม่ให้ข้อมูล
ถ้าเหลือโจทย์ที่ผลต่างไม่เป็นศูนย์จำนวน `m` ข้อ ค่า p ต่ำที่สุดที่เป็นไปได้คือ `2^(1−m)`

| `m` | p ต่ำสุดที่เป็นไปได้ | ถึงระดับ 0.05 ได้หรือไม่ |
|---:|---|---|
| 4 | 0.125 | **ไม่ได้** |
| 5 | 0.0625 | **ไม่ได้** |
| 6 | 0.031 | ได้ |
| 7 | 0.016 | ได้ |

**ต่ำกว่า 6 แปลว่านัยสำคัญเป็นไปไม่ได้ทางคณิตศาสตร์ ไม่ว่าขนาดของผลจะใหญ่เพียงใด**

**ค่า `m` ที่ได้จริงในการทดลองนี้คือ 5** (จาก 11 โจทย์ ผลต่างเป็นบวก 3 ข้อ เป็นลบ 2 ข้อ
และเป็นศูนย์ 6 ข้อ) ค่า p ต่ำที่สุดที่การออกแบบนี้มีทางได้จึงเท่ากับ 0.0625
**นัยสำคัญที่ระดับ 0.05 เป็นไปไม่ได้ตั้งแต่ก่อนเห็นข้อมูล** ไม่ว่าผลจะออกทางใด
ค่า p ที่ได้จริงคือ 0.50

**ข้อจำกัดนี้หนักขึ้นจากการใช้กฎสำรอง** — การเก็บข้อมูลถูกปิดที่ 4 รอบแทน 6 รอบ
ตามกฎที่ประกาศไว้ล่วงหน้า (ดู 6.x.12) จำนวน run ต่อกลุ่มจึงเป็น 44 แทนที่จะเป็น 66
การตัดรอบไม่กระทบ `m` โดยตรงเพราะ `m` นับจากจำนวนโจทย์ ไม่ใช่จำนวน run
แต่ทำให้ค่าเฉลี่ยรายโจทย์แต่ละค่ามีความผันผวนมากขึ้น จึงมีโอกาสเกิดผลต่างเป็นศูนย์
หรือกลับทิศได้ง่ายขึ้น ซึ่งลด `m` ลงได้ทางอ้อม

**ข้อสรุปที่ต้องเขียนตามนี้เสมอ:** ผลที่ไม่ถึงนัยสำคัญต้องรายงานว่า **"สรุปไม่ได้"**
ไม่ใช่ **"ไม่ต่างกัน"** เพราะการออกแบบไม่มีกำลังพอจะแยกสองอย่างนี้ออกจากกันตั้งแต่ต้น

### 6.x.2 ผลกระทบจากพื้นและเพดานของโจทย์

**สิ่งที่ประกาศรับความเสี่ยงไว้ล่วงหน้า**

เอกสารประกาศแผนวิเคราะห์ล่วงหน้าระบุไว้ในหัวข้อความเสี่ยงที่ยอมรับได้ว่า
โมเดลที่เลือกใช้ *อาจชนพื้นแทนที่จะชนเพดาน* และหากโจทย์ตกไปกองที่ศูนย์มากกว่าที่โมเดล
ที่ใช้ calibration ชนเพดาน เกณฑ์การเลือกโมเดลจะเลือกอีกโมเดลหนึ่ง

กระบวนการเลือกโมเดลนั้นถูกยกเลิกไปด้วยเหตุผลด้านงบเวลา (Amendment 2.1)
และล็อกโมเดลที่ใช้โดยไม่ได้วัดเทียบ **ความเสี่ยงที่ประกาศรับไว้จึงยังคงอยู่**

**สิ่งที่วัดได้จริงจากรอบแรก**

| ชุดข้อมูล | โจทย์ที่แยกแยะได้ | ชนเพดาน | ชนพื้น |
|---|---:|---:|---:|
| calibration บนโมเดลเดิม (53 run ที่ใช้ได้) | 7 | 4 | **0** |
| รอบแรกของชุดนี้ (55 run) | 4 | 2 | **5** |

ประตูตรวจสภาพหลังรอบแรกให้ผลผ่าน เพราะเกณฑ์ที่ประกาศไว้ล่วงหน้าคือ NO-GO
เมื่อโจทย์ที่ได้เต็มหรือศูนย์รวมกันตั้งแต่ 9 ข้อขึ้นไป ผลที่ได้คือ 7 ข้อ
**ผ่านเกณฑ์ แต่ผ่านโดยไม่เหลือระยะห่างมากนัก**

ข้อจำกัดนี้ต้องอ่านคู่กับ 6.x.1 เสมอ เพราะโจทย์ที่ทุกกลุ่มได้เท่ากันคือโจทย์ที่ไม่เข้าสู่การทดสอบ

**ข้อควรระวังในการตีความ:** ข้อมูลรอบแรกมีเพียงหนึ่ง run ต่อกลุ่มต่อโจทย์
จึงแยกไม่ออกระหว่าง *อัตราจริงเป็นศูนย์* กับ *รอบเดียวบังเอิญพลาดทั้งหมด*
ตัวเลขในตารางข้างต้นจึงเป็นสัญญาณเตือน ไม่ใช่ข้อสรุป — ค่าที่ใช้สรุปได้อยู่ในบทที่ 5

### 6.x.3 ตัวชี้วัดหลักเป็นการ "และ" กันของกฎหลายข้อ

`CRIT` นับว่าผ่านก็ต่อเมื่อกฎวิกฤต **ทุกข้อ** ในโจทย์นั้นผ่านพร้อมกัน
ซึ่งมีจำนวน 9–10 ข้อต่อโจทย์ การพลาดกฎข้อเดียวทำให้ทั้ง run ได้ศูนย์

การออกแบบเช่นนี้ตั้งใจให้ตัวชี้วัดเข้มงวด แต่มีผลข้างเคียงสองอย่างที่ต้องระบุ:

1. **ค่าที่ได้จะต่ำและกระจายไปที่ปลายทั้งสอง** ทำให้เกิดสภาพพื้นได้ง่ายกว่าตัวชี้วัดแบบสัดส่วน
2. **ค่า `CRIT` ที่เป็นศูนย์ไม่ได้แปลว่าเอเจนต์ไม่ได้ทำอะไร** — จากการวินิจฉัยรอบแรกพบว่า
   มีโจทย์ที่เอเจนต์ทำงานหลักสำเร็จทุกกลุ่ม รวมถึงผ่านเทสยอมรับที่เอเจนต์มองไม่เห็น
   แต่ `CRIT` เป็นศูนย์เพราะไปตกกฎขอบเขต

ด้วยเหตุนี้ รายงานจึงต้องเสนอ `RCR` ซึ่งเป็นสัดส่วนกฎที่ผ่าน ควบคู่กับ `CRIT` เสมอ
และการอภิปรายต้องอ้างอิงผลระดับกฎ ไม่ใช่ระดับ `CRIT` เพียงอย่างเดียว

*(หลักฐานประกอบ: `evidence/rep0-assay-diagnostics.md`)*

### 6.x.4 ผู้วิจัยเป็นผู้ออกแบบทั้งกฎ โจทย์ และตัวตรวจ

นี่คือข้อจำกัดเชิงโครงสร้างที่ไม่สามารถกำจัดได้ในงานขนาดนี้ สิ่งที่ทำได้คือลดทอนและเปิดเผย

**สิ่งที่ทำเพื่อลดทอน**

- ประกาศชุดกฎ ตัวชี้วัด และแผนวิเคราะห์ล่วงหน้าพร้อมวันที่ ก่อนเก็บข้อมูลเปรียบเทียบ
- ตัวตรวจทุกตัวเป็นโปรแกรมที่ตัดสินแบบ deterministic ห้ามใช้คนหรือ LLM ตัดสิน
- เทสยอมรับต้อง **แดงบนสภาพตั้งต้น** ทุกข้อ มิฉะนั้นวัดอะไรไม่ได้
- เทสยอมรับต้อง **ผ่านเฉลยอ้างอิง** และต้อง **ผ่านเฉลยที่เขียนคนละแบบ** ด้วย
  เพื่อพิสูจน์ว่าเทสวัดพฤติกรรม ไม่ได้วัดความเหมือนกับวิธีเขียนของผู้วิจัย
- เทสยอมรับต้อง **ตกกับเฉลยที่ผิด** เพื่อพิสูจน์ว่าไม่ได้หลวมเกินไป

**สิ่งที่ยังเหลืออยู่**

ความสัมพันธ์ระหว่างกฎกับตัวตรวจยังมาจากผู้เขียนคนเดียวกัน สมมติฐานที่ผิดร่วมกัน
ระหว่างสองสิ่งนี้จะไม่ถูกจับโดยกลไกข้างต้น การให้ผู้อื่นรีวิวชุดกฎก่อนเก็บข้อมูลช่วยได้บางส่วน
แต่ไม่ได้แทนที่การมีผู้ออกแบบตัวตรวจที่เป็นอิสระจากผู้ออกแบบกฎ

### 6.x.5 กลุ่มควบคุมเชิงความยาวไม่ใช่ยาหลอกที่พิสูจน์แล้ว

กลุ่มควบคุมที่จับคู่ความยาว (A3) ได้รับข้อความบริบทโครงการที่ยาวใกล้เคียงกับกลุ่มที่มีกฎ
แต่ไม่มีกฎควบคุมพฤติกรรม **ข้อความดังกล่าวไม่ได้รับการพิสูจน์ว่าไม่มีผลทางความหมาย**
ข้อมูลบริบทอาจช่วยหรือรบกวนเอเจนต์ก็ได้

ผลที่ตามมา:

- ผลที่ว่ากลุ่มที่มีกฎกับกลุ่มควบคุมเชิงความยาวไม่ต่างกัน **ไม่ได้พิสูจน์ว่ากฎไม่มีผล**
- ผลที่ว่ากลุ่มทดลองดีกว่ากลุ่มควบคุมเชิงความยาว **ไม่ได้แยกผลของโครงสร้าง
  ออกจากความยาวหรือความหมายของข้อความได้เด็ดขาด**

การเปรียบเทียบทุกคู่ที่เกี่ยวข้องกับกลุ่มนี้จึงประกาศไว้ล่วงหน้าว่าเป็น secondary
หรือ exploratory และต้องไม่ถูกยกขึ้นเป็นข้อสรุปหลักในภายหลัง

### 6.x.6 ทุกกลุ่มเห็น skill ของเครื่องมือจำนวนหนึ่งเท่ากัน

การตรวจสภาพ runtime ก่อนเก็บข้อมูลพบว่า เครื่องมือบรรทัดคำสั่งที่ใช้รันการทดลอง
มี skill ติดตั้งมาในตัวจำนวน 17 รายการ ซึ่งปรากฏใน available set ของ **ทุกกลุ่ม**
รวมถึงกลุ่มที่นิยามว่าไม่มี skill

รายการเหล่านี้ไม่ใช่การปนเปื้อนจากเครื่องของผู้วิจัย — ยืนยันโดยการย้ายโฟลเดอร์ skill
ส่วนตัวออกทั้งหมดแล้วตรวจซ้ำ ผลไม่เปลี่ยน และแฟล็กที่ระบบใช้อยู่กันดังกล่าวออกได้ครบอยู่แล้ว

**สิ่งที่ต้องระบุในการตีความ:**

> contrast ที่วัดได้จริงคือ **"skill ของการทดลอง 4 ตัว เทียบกับไม่มี บนพื้นเดียวกัน"**
> ไม่ใช่ **"มี skill เทียบกับไม่มี skill เลย"** ซึ่งเป็นคนละข้อความ

การควบคุมที่ทำได้คือชุดนี้ต้องเท่ากันทุก run ซึ่งบังคับด้วยการตรึงไว้ใน runtime manifest
และตรวจซ้ำทุก run หากเปลี่ยนระหว่างเก็บข้อมูล การรันจะหยุดทันที

**ข้อค้นพบระหว่างเก็บข้อมูล: ชุด skill ของเครื่องมือไม่คงที่ตามเวลา**

ระหว่างการเก็บข้อมูลจริง การตรวจสภาพ runtime หยุดการรันหนึ่งครั้งด้วยเหตุผลว่า
baseline skill set เปลี่ยนจาก 18 รายการเหลือ 15 รายการ และเมื่อตรวจซ้ำในเวลาต่อมา
ก็กลับมาเป็น 18 รายการเท่าเดิม

การตรวจย้อนหลังพบว่าชุดนี้เคยเปลี่ยนองค์ประกอบมาก่อนแล้วด้วย — การตรวจสภาพก่อนเริ่มเก็บข้อมูล
เห็นรายการหนึ่งที่ไม่ปรากฏในชุดที่ถูกตรึงไว้ และไม่เห็นอีกสองรายการที่ปรากฏในชุดที่ถูกตรึง
ทั้งหมดนี้เกิดขึ้นโดยที่ผู้วิจัยไม่ได้ติดตั้งหรือถอน skill ใด ๆ

ชุด skill ที่ติดมากับเครื่องมือจึงอยู่ภายใต้การควบคุมของผู้ให้บริการ ไม่ใช่ของผู้วิจัย
และอาจเปลี่ยนตามสถานะบัญชีหรือช่วงเวลา การเปลี่ยนแปลงครั้งที่ตรวจพบเกิดขึ้นหลังจาก
ชนขีดจำกัดการใช้งานรายรอบ ซึ่งเป็นความสัมพันธ์ที่สังเกตได้แต่ยังไม่ได้พิสูจน์กลไก

**ผลต่อความถูกต้องของข้อมูล**

run ที่พบสภาพไม่ตรงกับที่ตรึงไว้ **ถูกปฏิเสธและไม่ถูกบันทึกลงชุดข้อมูล**
ทุก run ที่อยู่ในชุดข้อมูลสุดท้ายจึงเห็น baseline ชุดเดียวกันทั้งหมด ชุดข้อมูลสอดคล้องกันภายใน
สิ่งที่สูญเสียคือเวลาในการเก็บข้อมูล ไม่ใช่ความถูกต้อง ซึ่งเป็นการแลกที่กลไกนี้ออกแบบมาให้เป็น

**สิ่งที่กลไกนี้ยังตรวจไม่ได้**

การตรวจเปรียบเทียบทำได้เฉพาะสิ่งที่ปรากฏใน metadata ของเครื่องมือ คือหมายเลขรุ่น
ชุด tool และชุด skill หากผู้ให้บริการเปลี่ยนพฤติกรรมของโมเดลโดยไม่เปลี่ยนสิ่งเหล่านี้
การทดลองจะตรวจไม่พบ ข้อจำกัดนี้ต้องอ่านคู่กับหัวข้อเรื่องเหตุการณ์ระหว่างเก็บข้อมูล

### 6.x.7 เวลาของระบบจำลองถูกตรึงไว้

ระบบจำลองที่ใช้ทดลองอ่านเวลาปัจจุบันจากตัวแปรสภาพแวดล้อมที่ตรึงไว้ที่วันเวลาเดียว
ทั้งตอนเอเจนต์ทำงานและตอนให้คะแนน (Amendment 17)

**ข้อดี:** ผลทำซ้ำได้และไม่ขึ้นกับวันที่รัน ซึ่งสำคัญเพราะการเก็บข้อมูลกินเวลาหลายวัน
หากไม่ตรึง วันที่รันจะกลายเป็นตัวแปรที่การทดลองไม่ได้ตั้งใจให้มี และโจทย์ที่ไวต่อเวลา
จะให้คำตอบต่างกันโดยไม่เกี่ยวกับตัวแปรต้น

**ข้อจำกัด:** งานนี้จึงไม่ได้วัดพฤติกรรมของเอเจนต์เมื่อเวลาเคลื่อนไปจริงระหว่างทำงาน
ซึ่งเป็นคำถามคนละข้อและอยู่นอกขอบเขต

### 6.x.8 นิยามของ run ที่ใช้ turn จนหมดงบ

run ที่เอเจนต์ใช้ turn จนครบเพดานถือเป็น **พฤติกรรมของเอเจนต์** และถูกนับเข้าผลหลัก
(Amendment 15) ไม่ใช่ความล้มเหลวของเครื่องมือวัด รายงานแสดงผลชุดที่ตัด run เหล่านั้นออก
ควบคู่กันเสมอเพื่อให้เห็นว่าข้อสรุปไวต่อการเลือกเกณฑ์ข้อนี้เพียงใด

**สิ่งที่ต้องระบุ:** คะแนนของ run ที่ชนเพดานสะท้อนงานที่ทำได้ภายในงบ turn ที่ประกาศไว้
**ไม่ใช่ความสามารถสูงสุดของกลุ่มนั้น** ตัวเลขผลหลักจึงเป็นค่าที่ผูกกับเพดาน turn ที่กำหนด

นอกจากนี้ กฎที่ประกาศไว้เองระบุว่าหากกลุ่มใดชนเพดานเกินร้อยละ 5 ให้ถือว่าเพดานยัง binding
และต้องขึ้นเพดานอีก ผลชุดนั้นจะตีความเป็นผลสุดท้ายไม่ได้
**อัตราการชนเพดานที่วัดได้จริงคือ 0 จาก 220 run (ร้อยละ 0) และเป็นศูนย์ในทุกกลุ่ม**
เพดาน turn ที่ 80 จึงไม่ binding สำหรับข้อมูลชุดนี้ และเงื่อนไขร้อยละ 5 ที่ประกาศไว้
ไม่ถูกกระตุ้น ข้อจำกัดข้างต้นจึงยังต้องระบุไว้ในฐานะขอบเขตของการตีความ
แต่ไม่ได้ผูกกับผลชุดนี้ในทางปฏิบัติ

### 6.x.9 ข้อจำกัดของตัวชี้วัดการเรียกใช้ skill

ตัวชี้วัดความแม่นของการเรียก skill อาศัย ground truth ที่ระบุว่า skill ใดเกี่ยวข้องกับโจทย์ใด
ซึ่งเป็นการตัดสินของผู้วิจัยจากคำอธิบายที่ผู้วิจัยเขียนเอง

งานนี้จึงประกาศ ground truth **สองชุด** ไว้ล่วงหน้าและรายงานคู่กันเสมอ (Amendment 16):
ชุดหลักตัดสินความเกี่ยวข้องจากคำบรรยายโจทย์ และชุดที่สองตัดสินจากกฎที่วัดจริงในโจทย์
สองชุดนี้ให้คำตอบต่างกันใน 3 จาก 11 โจทย์

การมีสองชุดทำให้เห็นว่า **ข้อสรุปไวต่อการเลือกเกณฑ์แค่ไหน** แต่ไม่ได้ทำให้ ground truth
เป็นอิสระจากผู้สร้างเครื่องมือ หากสองชุดชี้คนละทาง ข้อสรุปเรื่องการเรียกใช้ skill
ต้องอ่อนลง ไม่ใช่เลือกรายงานชุดที่ให้ค่าดีกว่า

**ข้อจำกัดเพิ่มเติมที่พบระหว่างวินิจฉัยรอบแรก:** ตัวตรวจกฎข้อหนึ่งในโจทย์ตระกูล
ข้อกำหนดขัดกัน ผ่านเพียงเพราะเอเจนต์ *เอ่ยชื่อ* ข้อกำหนดทั้งสองข้อในรายการงานที่ทำ
โดยไม่ได้ยืนยันว่าเอเจนต์ *ระบุว่าสองข้อนั้นขัดกัน* ตัวตรวจนี้จึงหลวมและทำให้ตัวเลข
ระดับกฎของมันดูดีเกินจริง ไม่กระทบตัวชี้วัดหลักซึ่งตกที่กฎอีกข้อหนึ่งอยู่แล้ว
**และไม่ได้แก้ระหว่างเก็บข้อมูล เพราะการเปลี่ยนกฎหลังเห็นข้อมูลเป็นสิ่งที่งานนี้ห้ามตัวเองไว้**

### 6.x.10 ขอบเขตของการสรุปอ้างอิง

- **โมเดลเดียว รุ่นเดียว ช่วงเวลาเดียว** — ผลผูกกับรุ่นที่ระบุและวันที่เก็บข้อมูล
  ไม่อ้างว่าเป็นสมบัติทั่วไปของโมเดลภาษาขนาดใหญ่
- **ระบบจำลองหนึ่งระบบ** — สร้างขึ้นเพื่อการทดลอง ใช้สถาปัตยกรรมเฉพาะแบบหนึ่ง
  ไม่ใช่ระบบที่ใช้งานจริง การสรุปไปยังโดเมนอื่นต้องการหลักฐานเพิ่ม
- **ไม่ได้เปรียบเทียบข้ามโมเดล** — ข้อมูลจากโมเดลอื่นที่มีอยู่เป็นหลักฐานเชิงพัฒนา
  เก็บคนละช่วงเวลาและไม่ได้สุ่มข้ามโมเดล จึงใช้เป็นผลพลอยได้เชิงบรรยายเท่านั้น
- **ไม่ได้ประเมินความมั่นคงปลอดภัย** — กลุ่มที่ฝังข้อความล่อเป็นการทดสอบความทนทานแบบอ่อน
  ไม่ใช่การประเมินภายใต้ผู้โจมตีที่ตั้งใจ

### 6.x.11 เหตุการณ์ระหว่างเก็บข้อมูลและผลต่อความถูกต้อง

การเก็บข้อมูลถูกขัดจังหวะหลายครั้งจากสี่สาเหตุที่แยกออกจากกันได้ชัดเจน:
การยืนยันตัวตนหมดอายุ · โปรเซสถูกยุติโดยไม่มีข้อความ · การชนขีดจำกัดการใช้งานรายรอบ
และการที่สภาพ runtime ไม่ตรงกับที่ตรึงไว้

แต่ละแบบทิ้งลายเซ็นต่างกัน (รหัสจบโปรเซส · มีหรือไม่มีข้อความ · fixture lock ค้างหรือถูกปล่อย ·
มีหรือไม่มี artifact ตัวสุดท้าย) จึงแยกกันได้โดยไม่ต้องเดา ตารางเปรียบเทียบอยู่ใน
`evidence/collection-log/README.md`

**เหตุใดจึงไม่กระทบความถูกต้องของข้อมูล**

- ทุก run ถูกบันทึกลงสมุดบันทึกแบบเพิ่มอย่างเดียวก่อนเรียกเอเจนต์ และบันทึกผลทันทีที่ได้กลับมา
  การหยุดกลางคันจึงทิ้งร่องรอยว่า run ใดถูกขัดจังหวะ แยกจาก run ที่ล้มเหลวจริง
- การทำต่อจากจุดที่ค้างจะคัดกรอง run ที่ล้มเหลวออกแล้วเก็บใหม่เสมอ
  ไม่มี cell ใดถูกตรึงเป็นความล้มเหลวถาวร
- สภาพ runtime ถูกตรวจเทียบกับค่าที่ตรึงไว้ทุก run ตลอดการเก็บข้อมูล
  รวมถึงหลังการหยุดและทำต่อทุกครั้ง

**สิ่งที่ต้องระบุ:** การเก็บข้อมูลกินเวลาหลายวันและหลายรอบของการทำต่อ
ซึ่งหมายความว่า run ไม่ได้เกิดขึ้นภายในหน้าต่างเวลาเดียวกัน หากผู้ให้บริการโมเดล
เปลี่ยนแปลงระบบระหว่างนั้นโดยไม่เปลี่ยนหมายเลขรุ่น การทดลองนี้จะตรวจไม่พบ
กลไกที่มีอยู่ตรวจได้เฉพาะการเปลี่ยนแปลงที่ปรากฏในหมายเลขรุ่นของเครื่องมือ
ชุด tool หรือชุด skill เท่านั้น

**ข้อสังเกตเชิงปฏิบัติการ: การยุติโปรเซสโดยไม่มีข้อความ**

การเก็บข้อมูลถูกยุติกลางคันโดยไม่มีข้อความใด ๆ สี่ครั้ง (รหัสจบ 1 · ไม่มีข้อความปิดท้าย ·
ไม่มีข้อความใน stderr เลย · ไม่มี artifact ตัวสุดท้าย · fixture lock ค้าง)
ที่อายุการทำงานต่างกันทุกครั้ง คือ 62, 38, 30 และ 77 นาที

สามครั้งแรกเกิดกับโปรเซสที่ยิงเป็นงานเบื้องหลังของ session ผู้สั่งงาน จึงตั้งสมมติฐานว่า
สาเหตุคืออายุของ session นั้น และเปลี่ยนมายิง runner เป็นโปรเซสแยกที่ไม่ผูกกับ session
(`Start-Process` แบบ detached) **แต่ครั้งที่สี่เกิดกับโปรเซสแยกนี้เอง** สมมติฐานนั้นจึงตกไป

**สาเหตุยังไม่ทราบ** สิ่งที่ตัดออกไปได้แล้วคือ เพดานเวลาคงที่ (อายุต่างกันทุกครั้ง)
และการผูกกับอายุ session ของผู้สั่งงาน ส่วนสมมติฐานเรื่องภาระงานอ่านเขียนไฟล์หนัก
ก็ไม่ตรงกับครั้งที่สามและสี่ การไม่มีข้อความใน stderr เลยบ่งว่าโปรเซสไม่ได้จบด้วย
ข้อผิดพลาดของโปรแกรมตัวเอง แต่ถูกยุติจากภายนอก

เรื่องนี้ไม่กระทบความถูกต้องของข้อมูล เพราะ run ที่ถูกขัดจังหวะไม่มี artifact จึงไม่เข้าชุดข้อมูล
และถูกเก็บซ้ำในรอบถัดไป ทุกครั้งที่เกิด ข้อมูลที่เก็บไว้แล้วไม่สูญหายแม้แต่ run เดียว

**ข้อควรรู้สำหรับผู้ที่จะทำซ้ำการทดลองนี้:** เมื่อสาเหตุของการถูกยุติยังไม่ทราบ
สิ่งที่ป้องกันความเสียหายได้จริงไม่ใช่การเลือกวิธียิงคำสั่ง แต่คือการออกแบบให้ทนการหยุด —
บันทึก checkpoint ทุก run · สมุดบันทึก attempt แบบเพิ่มอย่างเดียวที่แยก "ถูกขัดจังหวะ"
ออกจาก "ล้มเหลวจริง" · และคำสั่งทำต่อที่เก็บซ่อมเฉพาะที่ขาด

*(บันทึกเหตุการณ์ทั้งหมด: `evidence/collection-log/`)*

### 6.x.12 ข้อมูลที่ถูกกันออกจากการวิเคราะห์โดยเจตนา

- **ชุดข้อมูลระหว่างพัฒนา** เก็บภายใต้เพดาน turn ที่ถูกยกเลิกไปแล้ว และภายใต้นิยาม
  การทดลองคนละชุด จึงใช้อ้างเป็นผลไม่ได้ เก็บไว้เป็นหลักฐานเชิงพัฒนาเท่านั้น
- **ความพยายามเก็บข้อมูลที่ล้มเหลวทั้งชุดจากการยืนยันตัวตนหมดอายุ** ไม่มี run ใดได้คะแนน
  ที่ใช้ได้ และไม่มีการตรึงสภาพ runtime จึงไม่ใช่ข้อมูล
- **ตัวเลขจากการทดลอง rule dilution** มาจาก mock adapter ทั้งหมด ห้ามอ้างในเล่มและบนสไลด์
- **run ของรอบที่ 5 จำนวน 17 run** เก็บมาแล้วจริงและไม่มีอะไรผิด แต่ถูกตัดออกตามกฎสำรอง
  ที่ประกาศไว้ล่วงหน้า (Amendment 14) ซึ่งกำหนดให้ตัดรอบ**เท่ากันทุกกลุ่ม** เมื่อชนโควตา
  ถ้าเก็บไว้ จำนวน run ต่อกลุ่มจะไม่เท่ากัน (45 ถึง 50) เพราะรอบสุดท้ายเก็บได้ไม่ครบ
  ซึ่งเป็นความไม่สมดุลที่เกิดจากลำดับการเก็บข้อมูล ไม่ใช่จากการออกแบบ
  run ทั้ง 17 ยังอยู่ครบใน checkpoint และในสมุดบันทึก attempt ตรวจสอบย้อนหลังได้

### 6.x.13 ข้อจำกัดที่เพิ่มขึ้นจากชุดที่ 2

หัวข้อ 6.x.1 ถึง 6.x.12 เขียนไว้ก่อนเห็นผลของชุดที่ 1 และไม่ถูกแก้ย้อนหลัง
หัวข้อนี้เพิ่มสิ่งที่ชุดที่ 2 ทำให้เห็นชัดขึ้นหรือทำให้เกิดขึ้นใหม่

**ก) ตัวชี้วัดหลักของชุดที่ 2 รวมสองสิ่งที่เดินคนละทางเข้าด้วยกัน**

`RCRc` คือผลคูณของ "ทำงานสำเร็จ" กับ "ตามกฎเมื่อสำเร็จ" ข้อจำกัดนี้ถูกประกาศไว้
ล่วงหน้าใน `PRE-REGISTRATION-2.md` §8 ว่าตัวชี้วัดนี้ตอบคำถามว่าทำงานได้ไหม
มากกว่าตามกฎแค่ไหน **และข้อมูลชุดที่ 2 แสดงให้เห็นว่าข้อกังวลนั้นไม่ใช่ทฤษฎี**

กลุ่มที่ไม่มีกฎเลยทำงานสำเร็จมากที่สุด (75.0%) แต่ตามกฎแย่ที่สุด (0.895)
ขณะที่กลุ่มที่มีกฎทุกกลุ่มตามกฎได้เท่ากันที่ 0.967 แต่ทำงานสำเร็จน้อยกว่า
**ผลคูณจึงจัดอันดับกลุ่มไม่เหมือนกับที่แต่ละส่วนจัด** และการอ่านเฉพาะค่ารวม
จะได้ข้อสรุปที่ตรงข้ามกับความจริงในบางคู่

ผลที่ตามมาสำหรับการตีความ: **ตัวเลข `RCRc` ตัวเดียวไม่มีความหมายในตัวเอง**
ต้องอ่านคู่กับตารางแยกส่วนเสมอ บทที่ 5 ของชุดที่ 2 จึงบังคับให้พิมพ์ทั้งสองคอลัมน์
และเตือนไว้ในตัวเอกสาร สิ่งที่ยังไม่มีคือการทดสอบทางสถิติของแต่ละส่วนแยกกัน
ซึ่งไม่ได้ประกาศไว้ล่วงหน้า **จึงห้ามเพิ่มทีหลัง** และต้องยกไปเป็นงานของชุดถัดไป

**ข) A5 ไม่ได้คุมปริมาณข้อความอย่างที่ตั้งใจ และวัดได้ว่าห่างเท่าไร**

A5 ถูกสร้างเพื่อแยกกลไกโหลดตามเงื่อนไขออกจากปริมาณข้อความ แต่มันถือข้อความ
ที่ระดับ **เพดาน** ของ A2 (3,308 token) ขณะที่การวัดในชุดที่ 2 พบว่า A2 โหลด
skill จริงเฉลี่ย **2.36 จาก 4 ตัว และไม่มี run ใดโหลดครบทั้งสี่เลย**
ข้อความที่ A2 เห็นจริงจึงต่ำกว่า A5 อยู่มาก

การเปรียบเทียบ A5 กับ A2 จึงยังผสมกลไกกับปริมาณอยู่ เพียงแต่**รู้ทิศและรู้ขนาด**
ไม่ใช่การคุมตัวแปรที่สะอาด ข้อนี้ต้องระบุทุกครั้งที่อ้างถึงคู่นี้

**ค) ข้อความของ A5 ชักนำพฤติกรรมที่ A2 ไม่ถูกชักนำ**

A5 เกิดจากการนำเนื้อ skill มาต่อกัน วลี "ก่อนอ่าน skill นี้" จึงติดมา 4 จุด
ทั้งที่ A5 ไม่มี skill ติดตั้งเลย ผลคือ **เอเจนต์เรียกเครื่องมือ `Skill` 12 ครั้ง
ใน 9 จาก 44 run และไม่มีครั้งใดโหลดสำเร็จ**

การไม่แก้ข้อความเป็นการตัดสินใจโดยเจตนา เพราะการเขียนวลีนั้นใหม่จะทำให้ข้อความ
ของ A5 ต่างจาก A2 ซึ่งทำลายเหตุผลทั้งหมดของการมี A5 สิ่งที่ทำแทนคือประกาศ
นโยบายไว้ล่วงหน้าแล้ววัดและรายงาน **แต่ข้อเท็จจริงยังคงอยู่ว่า A5 กับ A2
ต่างกันมากกว่าวิธีส่งบริบทอย่างเดียว** และความต่างนั้นวัดได้ที่ 12 ครั้ง

**ง) เอเจนต์เขียนหน่วยความจำถาวรออกนอกพื้นที่ทดลอง**

ระหว่างเก็บชุดที่ 2 เอเจนต์ในกลุ่ม A1 ใช้เครื่องมือ `Write` เขียนไฟล์สองไฟล์ลงใน
โฟลเดอร์หน่วยความจำของเครื่องมือ ซึ่งอยู่นอกพื้นที่ทดลองและอยู่รอดข้าม run ข้ามกลุ่ม
ไฟล์หนึ่งสรุป **กฎของ A1** อีกไฟล์บอกว่า REQ ใดถูกทำไปแล้ว ซึ่งเป็น**เฉลยของ S07**

การตรวจสภาพ runtime จับได้ทันทีที่ run นั้นจบและหยุดการเก็บข้อมูลทั้งชุด
run นั้นถูกปฏิเสธ ไม่มี run ถัดไปเกิดขึ้น และ 148 run ก่อนหน้าผ่านการตรวจเดียวกัน
ทั้งก่อนและหลังทุกครั้ง **ชุดข้อมูลจึงไม่ปนเปื้อน**

**สิ่งที่ต้องเขียนตามตรง:** ช่องทางนี้ไม่ได้อยู่ในรายการตัวแปรควบคุมตั้งแต่ต้น
มันถูกเพิ่มเข้ามาเพราะมีคนเผื่อไว้ว่าหน่วยความจำอัตโนมัติอาจเป็นตัวแปร
**ถ้าไม่ได้เผื่อไว้ การทดลองจะปนเปื้อนโดยไม่มีใครรู้ และตัวเลขจะดูปกติทุกประการ**
เราไม่มีทางรู้ว่ายังมีช่องทางลักษณะเดียวกันที่ยังไม่มีใครนึกถึงอีกกี่ช่อง
ข้อจำกัดนี้เป็นข้อจำกัดของ **วิธีการทั้งวิธี** ไม่ใช่ของการทดลองครั้งนี้เท่านั้น

*(หลักฐานเต็ม: `evidence/memory-contamination-2026-09-19/`)*

**จ) กำลังการทดสอบยังไม่พอ แม้จะซ่อมเครื่องมือวัดแล้ว**

ชุดที่ 2 **ไม่ได้แก้ปัญหานี้** มีโจทย์ที่ให้ผลต่างไม่เป็นศูนย์เพียง 5 ข้อจาก 11
เท่ากับชุดที่ 1 พอดี ค่า p ต่ำสุดที่เป็นไปได้จึงยังคงเป็น 0.0625 เท่าเดิม
**นัยสำคัญที่ระดับ 0.05 เป็นไปไม่ได้ในชุดที่ 2 เช่นเดียวกับชุดที่ 1**
การซ่อมตัวชี้วัดทำให้ค่าประมาณคมขึ้น (p ที่สังเกตได้ 0.500 → 0.250)
แต่ไม่ได้แตะข้อจำกัดที่แท้จริงเลย

แผนที่ประกาศล่วงหน้าคาดไว้ว่า `m` จะอยู่ราว 6 และของจริงได้ 5
**การซ่อมตัวชี้วัดจึงไม่ได้แก้ปัญหาจำนวนโจทย์** ซึ่งเป็นข้อจำกัดที่ 6.x.1 ระบุไว้
ตั้งแต่ต้นว่าเป็นข้อที่หนักที่สุด และยังหนักที่สุดอยู่หลังผ่านไปสองชุด

**ฉ) ชุดที่ 2 ไม่มีข้อสรุปเรื่องความทนทานต่อการฉีดคำสั่ง**
