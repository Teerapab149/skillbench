## 6.x ข้อจำกัดของการวิจัย

### 6.x.1 ข้อจำกัดเชิงกำลังการทดสอบ — ข้อที่หนักที่สุด

**จำนวนโจทย์เป็นเพดาน ไม่ใช่จำนวนรอบ**

การทดสอบหลักเป็น exact sign-flip permutation ที่ระดับโจทย์ หน่วยข้อมูลจึงเป็น **โจทย์**
ไม่ใช่ run การเพิ่มจำนวนรอบต่อโจทย์ช่วยให้ค่าประมาณของแต่ละโจทย์แม่นขึ้น
แต่ไม่ได้เพิ่มจำนวนหน่วยอิสระ ซึ่งคงที่อยู่ที่ 11

ผลที่ตามมาเป็นเรื่องเลขคณิตล้วน ๆ: หากโจทย์ที่ทุกกลุ่มได้คะแนนเท่ากันมีค่าผลต่างเป็นศูนย์
การสลับเครื่องหมายของศูนย์ไม่เปลี่ยนค่าสถิติ โจทย์นั้นจึงไม่ให้ข้อมูล
ถ้าเหลือโจทย์ที่ผลต่างไม่เป็นศูนย์จำนวน `m` ข้อ ค่า p ต่ำที่สุดที่เป็นไปได้คือ `2^(1−m)`

| `m` | p ต่ำสุดที่เป็นไปได้ | ถึงระดับ 0.05 ได้หรือไม่ |
|---:|---|---|
| 4 | 0.125 | **ไม่ได้** |
| 5 | 0.063 | **ไม่ได้** |
| 6 | 0.031 | ได้ |
| 7 | 0.016 | ได้ |

**ต่ำกว่า 6 แปลว่านัยสำคัญเป็นไปไม่ได้ทางคณิตศาสตร์ ไม่ว่าขนาดของผลจะใหญ่เพียงใด**

ค่า `m` ที่ได้จริงในการทดลองนี้คือ `[เติมจากผล]`

**ข้อสรุปที่ต้องเขียนตามนี้เสมอ:** ผลที่ไม่ถึงนัยสำคัญต้องรายงานว่า **"สรุปไม่ได้"**
ไม่ใช่ **"ไม่ต่างกัน"** เพราะการออกแบบไม่มีกำลังพอจะแยกสองอย่างนี้ออกจากกันตั้งแต่ต้น

### 6.x.2 ผลกระทบจากพื้นและเพดานของโจทย์

**สิ่งที่ประกาศรับความเสี่ยงไว้ล่วงหน้า**

เอกสารประกาศแผนวิเคราะห์ล่วงหน้าระบุไว้ในหัวข้อความเสี่ยงที่ยอมรับได้ว่า
โมเดลที่เลือกใช้ *อาจชนพื้นแทนที่จะชนเพดาน* และหากโจทย์ตกไปกองที่ศูนย์มากกว่าที่โมเดล
ที่ใช้ calibration ชนเพดาน เกณฑ์การเลือกโมเดลจะเลือกอีกโมเดลหนึ่ง

กระบวนการเลือกโมเดลนั้นถูกยกเลิกไปด้วยเหตุผลด้านงบเวลา (Amendment 2.1)
และล็อกโมเดลที่ใช้โดยไม่ได้วัดเทียบ **ความเสี่ยงที่ประกาศรับไว้จึงยังคงอยู่**

**สิ่งที่วัดได้จริงจากรอบแรก**

| ชุดข้อมูล | โจทย์ที่แยกแยะได้ | ชนเพดาน | ชนพื้น |
|---|---:|---:|---:|
| calibration บนโมเดลเดิม (53 run ที่ใช้ได้) | 7 | 4 | **0** |
| รอบแรกของชุดนี้ (55 run) | 4 | 2 | **5** |

ประตูตรวจสภาพหลังรอบแรกให้ผลผ่าน เพราะเกณฑ์ที่ประกาศไว้ล่วงหน้าคือ NO-GO
เมื่อโจทย์ที่ได้เต็มหรือศูนย์รวมกันตั้งแต่ 9 ข้อขึ้นไป ผลที่ได้คือ 7 ข้อ
**ผ่านเกณฑ์ แต่ผ่านโดยไม่เหลือระยะห่างมากนัก**

ข้อจำกัดนี้ต้องอ่านคู่กับ 6.x.1 เสมอ เพราะโจทย์ที่ทุกกลุ่มได้เท่ากันคือโจทย์ที่ไม่เข้าสู่การทดสอบ

**ข้อควรระวังในการตีความ:** ข้อมูลรอบแรกมีเพียงหนึ่ง run ต่อกลุ่มต่อโจทย์
จึงแยกไม่ออกระหว่าง *อัตราจริงเป็นศูนย์* กับ *รอบเดียวบังเอิญพลาดทั้งหมด*
ตัวเลขในตารางข้างต้นจึงเป็นสัญญาณเตือน ไม่ใช่ข้อสรุป — ค่าที่ใช้สรุปได้อยู่ในบทที่ 5

### 6.x.3 ตัวชี้วัดหลักเป็นการ "และ" กันของกฎหลายข้อ

`CRIT` นับว่าผ่านก็ต่อเมื่อกฎวิกฤต **ทุกข้อ** ในโจทย์นั้นผ่านพร้อมกัน
ซึ่งมีจำนวน 9–10 ข้อต่อโจทย์ การพลาดกฎข้อเดียวทำให้ทั้ง run ได้ศูนย์

การออกแบบเช่นนี้ตั้งใจให้ตัวชี้วัดเข้มงวด แต่มีผลข้างเคียงสองอย่างที่ต้องระบุ:

1. **ค่าที่ได้จะต่ำและกระจายไปที่ปลายทั้งสอง** ทำให้เกิดสภาพพื้นได้ง่ายกว่าตัวชี้วัดแบบสัดส่วน
2. **ค่า `CRIT` ที่เป็นศูนย์ไม่ได้แปลว่าเอเจนต์ไม่ได้ทำอะไร** — จากการวินิจฉัยรอบแรกพบว่า
   มีโจทย์ที่เอเจนต์ทำงานหลักสำเร็จทุกกลุ่ม รวมถึงผ่านเทสยอมรับที่เอเจนต์มองไม่เห็น
   แต่ `CRIT` เป็นศูนย์เพราะไปตกกฎขอบเขต

ด้วยเหตุนี้ รายงานจึงต้องเสนอ `RCR` ซึ่งเป็นสัดส่วนกฎที่ผ่าน ควบคู่กับ `CRIT` เสมอ
และการอภิปรายต้องอ้างอิงผลระดับกฎ ไม่ใช่ระดับ `CRIT` เพียงอย่างเดียว

*(หลักฐานประกอบ: `evidence/rep0-assay-diagnostics.md`)*

### 6.x.4 ผู้วิจัยเป็นผู้ออกแบบทั้งกฎ โจทย์ และตัวตรวจ

นี่คือข้อจำกัดเชิงโครงสร้างที่ไม่สามารถกำจัดได้ในงานขนาดนี้ สิ่งที่ทำได้คือลดทอนและเปิดเผย

**สิ่งที่ทำเพื่อลดทอน**

- ประกาศชุดกฎ ตัวชี้วัด และแผนวิเคราะห์ล่วงหน้าพร้อมวันที่ ก่อนเก็บข้อมูลเปรียบเทียบ
- ตัวตรวจทุกตัวเป็นโปรแกรมที่ตัดสินแบบ deterministic ห้ามใช้คนหรือ LLM ตัดสิน
- เทสยอมรับต้อง **แดงบนสภาพตั้งต้น** ทุกข้อ มิฉะนั้นวัดอะไรไม่ได้
- เทสยอมรับต้อง **ผ่านเฉลยอ้างอิง** และต้อง **ผ่านเฉลยที่เขียนคนละแบบ** ด้วย
  เพื่อพิสูจน์ว่าเทสวัดพฤติกรรม ไม่ได้วัดความเหมือนกับวิธีเขียนของผู้วิจัย
- เทสยอมรับต้อง **ตกกับเฉลยที่ผิด** เพื่อพิสูจน์ว่าไม่ได้หลวมเกินไป

**สิ่งที่ยังเหลืออยู่**

ความสัมพันธ์ระหว่างกฎกับตัวตรวจยังมาจากผู้เขียนคนเดียวกัน สมมติฐานที่ผิดร่วมกัน
ระหว่างสองสิ่งนี้จะไม่ถูกจับโดยกลไกข้างต้น การให้ผู้อื่นรีวิวชุดกฎก่อนเก็บข้อมูลช่วยได้บางส่วน
แต่ไม่ได้แทนที่การมีผู้ออกแบบตัวตรวจที่เป็นอิสระจากผู้ออกแบบกฎ

### 6.x.5 กลุ่มควบคุมเชิงความยาวไม่ใช่ยาหลอกที่พิสูจน์แล้ว

กลุ่มควบคุมที่จับคู่ความยาว (A3) ได้รับข้อความบริบทโครงการที่ยาวใกล้เคียงกับกลุ่มที่มีกฎ
แต่ไม่มีกฎควบคุมพฤติกรรม **ข้อความดังกล่าวไม่ได้รับการพิสูจน์ว่าไม่มีผลทางความหมาย**
ข้อมูลบริบทอาจช่วยหรือรบกวนเอเจนต์ก็ได้

ผลที่ตามมา:

- ผลที่ว่ากลุ่มที่มีกฎกับกลุ่มควบคุมเชิงความยาวไม่ต่างกัน **ไม่ได้พิสูจน์ว่ากฎไม่มีผล**
- ผลที่ว่ากลุ่มทดลองดีกว่ากลุ่มควบคุมเชิงความยาว **ไม่ได้แยกผลของโครงสร้าง
  ออกจากความยาวหรือความหมายของข้อความได้เด็ดขาด**

การเปรียบเทียบทุกคู่ที่เกี่ยวข้องกับกลุ่มนี้จึงประกาศไว้ล่วงหน้าว่าเป็น secondary
หรือ exploratory และต้องไม่ถูกยกขึ้นเป็นข้อสรุปหลักในภายหลัง

### 6.x.6 ทุกกลุ่มเห็น skill ของเครื่องมือจำนวนหนึ่งเท่ากัน

การตรวจสภาพ runtime ก่อนเก็บข้อมูลพบว่า เครื่องมือบรรทัดคำสั่งที่ใช้รันการทดลอง
มี skill ติดตั้งมาในตัวจำนวน 17 รายการ ซึ่งปรากฏใน available set ของ **ทุกกลุ่ม**
รวมถึงกลุ่มที่นิยามว่าไม่มี skill

รายการเหล่านี้ไม่ใช่การปนเปื้อนจากเครื่องของผู้วิจัย — ยืนยันโดยการย้ายโฟลเดอร์ skill
ส่วนตัวออกทั้งหมดแล้วตรวจซ้ำ ผลไม่เปลี่ยน และแฟล็กที่ระบบใช้อยู่กันดังกล่าวออกได้ครบอยู่แล้ว

**สิ่งที่ต้องระบุในการตีความ:**

> contrast ที่วัดได้จริงคือ **"skill ของการทดลอง 4 ตัว เทียบกับไม่มี บนพื้นเดียวกัน"**
> ไม่ใช่ **"มี skill เทียบกับไม่มี skill เลย"** ซึ่งเป็นคนละข้อความ

การควบคุมที่ทำได้คือชุดนี้ต้องเท่ากันทุก run ซึ่งบังคับด้วยการตรึงไว้ใน runtime manifest
และตรวจซ้ำทุก run หากเปลี่ยนระหว่างเก็บข้อมูล การรันจะหยุดทันที

**ข้อค้นพบระหว่างเก็บข้อมูล: ชุด skill ของเครื่องมือไม่คงที่ตามเวลา**

ระหว่างการเก็บข้อมูลจริง การตรวจสภาพ runtime หยุดการรันหนึ่งครั้งด้วยเหตุผลว่า
baseline skill set เปลี่ยนจาก 18 รายการเหลือ 15 รายการ และเมื่อตรวจซ้ำในเวลาต่อมา
ก็กลับมาเป็น 18 รายการเท่าเดิม

การตรวจย้อนหลังพบว่าชุดนี้เคยเปลี่ยนองค์ประกอบมาก่อนแล้วด้วย — การตรวจสภาพก่อนเริ่มเก็บข้อมูล
เห็นรายการหนึ่งที่ไม่ปรากฏในชุดที่ถูกตรึงไว้ และไม่เห็นอีกสองรายการที่ปรากฏในชุดที่ถูกตรึง
ทั้งหมดนี้เกิดขึ้นโดยที่ผู้วิจัยไม่ได้ติดตั้งหรือถอน skill ใด ๆ

ชุด skill ที่ติดมากับเครื่องมือจึงอยู่ภายใต้การควบคุมของผู้ให้บริการ ไม่ใช่ของผู้วิจัย
และอาจเปลี่ยนตามสถานะบัญชีหรือช่วงเวลา การเปลี่ยนแปลงครั้งที่ตรวจพบเกิดขึ้นหลังจาก
ชนขีดจำกัดการใช้งานรายรอบ ซึ่งเป็นความสัมพันธ์ที่สังเกตได้แต่ยังไม่ได้พิสูจน์กลไก

**ผลต่อความถูกต้องของข้อมูล**

run ที่พบสภาพไม่ตรงกับที่ตรึงไว้ **ถูกปฏิเสธและไม่ถูกบันทึกลงชุดข้อมูล**
ทุก run ที่อยู่ในชุดข้อมูลสุดท้ายจึงเห็น baseline ชุดเดียวกันทั้งหมด ชุดข้อมูลสอดคล้องกันภายใน
สิ่งที่สูญเสียคือเวลาในการเก็บข้อมูล ไม่ใช่ความถูกต้อง ซึ่งเป็นการแลกที่กลไกนี้ออกแบบมาให้เป็น

**สิ่งที่กลไกนี้ยังตรวจไม่ได้**

การตรวจเปรียบเทียบทำได้เฉพาะสิ่งที่ปรากฏใน metadata ของเครื่องมือ คือหมายเลขรุ่น
ชุด tool และชุด skill หากผู้ให้บริการเปลี่ยนพฤติกรรมของโมเดลโดยไม่เปลี่ยนสิ่งเหล่านี้
การทดลองจะตรวจไม่พบ ข้อจำกัดนี้ต้องอ่านคู่กับหัวข้อเรื่องเหตุการณ์ระหว่างเก็บข้อมูล

### 6.x.7 เวลาของระบบจำลองถูกตรึงไว้

ระบบจำลองที่ใช้ทดลองอ่านเวลาปัจจุบันจากตัวแปรสภาพแวดล้อมที่ตรึงไว้ที่วันเวลาเดียว
ทั้งตอนเอเจนต์ทำงานและตอนให้คะแนน (Amendment 17)

**ข้อดี:** ผลทำซ้ำได้และไม่ขึ้นกับวันที่รัน ซึ่งสำคัญเพราะการเก็บข้อมูลกินเวลาหลายวัน
หากไม่ตรึง วันที่รันจะกลายเป็นตัวแปรที่การทดลองไม่ได้ตั้งใจให้มี และโจทย์ที่ไวต่อเวลา
จะให้คำตอบต่างกันโดยไม่เกี่ยวกับตัวแปรต้น

**ข้อจำกัด:** งานนี้จึงไม่ได้วัดพฤติกรรมของเอเจนต์เมื่อเวลาเคลื่อนไปจริงระหว่างทำงาน
ซึ่งเป็นคำถามคนละข้อและอยู่นอกขอบเขต

### 6.x.8 นิยามของ run ที่ใช้ turn จนหมดงบ

run ที่เอเจนต์ใช้ turn จนครบเพดานถือเป็น **พฤติกรรมของเอเจนต์** และถูกนับเข้าผลหลัก
(Amendment 15) ไม่ใช่ความล้มเหลวของเครื่องมือวัด รายงานแสดงผลชุดที่ตัด run เหล่านั้นออก
ควบคู่กันเสมอเพื่อให้เห็นว่าข้อสรุปไวต่อการเลือกเกณฑ์ข้อนี้เพียงใด

**สิ่งที่ต้องระบุ:** คะแนนของ run ที่ชนเพดานสะท้อนงานที่ทำได้ภายในงบ turn ที่ประกาศไว้
**ไม่ใช่ความสามารถสูงสุดของกลุ่มนั้น** ตัวเลขผลหลักจึงเป็นค่าที่ผูกกับเพดาน turn ที่กำหนด

นอกจากนี้ กฎที่ประกาศไว้เองระบุว่าหากกลุ่มใดชนเพดานเกินร้อยละ 5 ให้ถือว่าเพดานยัง binding
และต้องขึ้นเพดานอีก ผลชุดนั้นจะตีความเป็นผลสุดท้ายไม่ได้
อัตราการชนเพดานที่วัดได้จริงคือ `[เติมจากผล]`

### 6.x.9 ข้อจำกัดของตัวชี้วัดการเรียกใช้ skill

ตัวชี้วัดความแม่นของการเรียก skill อาศัย ground truth ที่ระบุว่า skill ใดเกี่ยวข้องกับโจทย์ใด
ซึ่งเป็นการตัดสินของผู้วิจัยจากคำอธิบายที่ผู้วิจัยเขียนเอง

งานนี้จึงประกาศ ground truth **สองชุด** ไว้ล่วงหน้าและรายงานคู่กันเสมอ (Amendment 16):
ชุดหลักตัดสินความเกี่ยวข้องจากคำบรรยายโจทย์ และชุดที่สองตัดสินจากกฎที่วัดจริงในโจทย์
สองชุดนี้ให้คำตอบต่างกันใน 3 จาก 11 โจทย์

การมีสองชุดทำให้เห็นว่า **ข้อสรุปไวต่อการเลือกเกณฑ์แค่ไหน** แต่ไม่ได้ทำให้ ground truth
เป็นอิสระจากผู้สร้างเครื่องมือ หากสองชุดชี้คนละทาง ข้อสรุปเรื่องการเรียกใช้ skill
ต้องอ่อนลง ไม่ใช่เลือกรายงานชุดที่ให้ค่าดีกว่า

**ข้อจำกัดเพิ่มเติมที่พบระหว่างวินิจฉัยรอบแรก:** ตัวตรวจกฎข้อหนึ่งในโจทย์ตระกูล
ข้อกำหนดขัดกัน ผ่านเพียงเพราะเอเจนต์ *เอ่ยชื่อ* ข้อกำหนดทั้งสองข้อในรายการงานที่ทำ
โดยไม่ได้ยืนยันว่าเอเจนต์ *ระบุว่าสองข้อนั้นขัดกัน* ตัวตรวจนี้จึงหลวมและทำให้ตัวเลข
ระดับกฎของมันดูดีเกินจริง ไม่กระทบตัวชี้วัดหลักซึ่งตกที่กฎอีกข้อหนึ่งอยู่แล้ว
**และไม่ได้แก้ระหว่างเก็บข้อมูล เพราะการเปลี่ยนกฎหลังเห็นข้อมูลเป็นสิ่งที่งานนี้ห้ามตัวเองไว้**

### 6.x.10 ขอบเขตของการสรุปอ้างอิง

- **โมเดลเดียว รุ่นเดียว ช่วงเวลาเดียว** — ผลผูกกับรุ่นที่ระบุและวันที่เก็บข้อมูล
  ไม่อ้างว่าเป็นสมบัติทั่วไปของโมเดลภาษาขนาดใหญ่
- **ระบบจำลองหนึ่งระบบ** — สร้างขึ้นเพื่อการทดลอง ใช้สถาปัตยกรรมเฉพาะแบบหนึ่ง
  ไม่ใช่ระบบที่ใช้งานจริง การสรุปไปยังโดเมนอื่นต้องการหลักฐานเพิ่ม
- **ไม่ได้เปรียบเทียบข้ามโมเดล** — ข้อมูลจากโมเดลอื่นที่มีอยู่เป็นหลักฐานเชิงพัฒนา
  เก็บคนละช่วงเวลาและไม่ได้สุ่มข้ามโมเดล จึงใช้เป็นผลพลอยได้เชิงบรรยายเท่านั้น
- **ไม่ได้ประเมินความมั่นคงปลอดภัย** — กลุ่มที่ฝังข้อความล่อเป็นการทดสอบความทนทานแบบอ่อน
  ไม่ใช่การประเมินภายใต้ผู้โจมตีที่ตั้งใจ

### 6.x.11 เหตุการณ์ระหว่างเก็บข้อมูลและผลต่อความถูกต้อง

การเก็บข้อมูลถูกขัดจังหวะหลายครั้งจากสี่สาเหตุที่แยกออกจากกันได้ชัดเจน:
การยืนยันตัวตนหมดอายุ · โปรเซสถูกยุติโดยไม่มีข้อความ · การชนขีดจำกัดการใช้งานรายรอบ
และการที่สภาพ runtime ไม่ตรงกับที่ตรึงไว้

แต่ละแบบทิ้งลายเซ็นต่างกัน (รหัสจบโปรเซส · มีหรือไม่มีข้อความ · fixture lock ค้างหรือถูกปล่อย ·
มีหรือไม่มี artifact ตัวสุดท้าย) จึงแยกกันได้โดยไม่ต้องเดา ตารางเปรียบเทียบอยู่ใน
`evidence/collection-log/README.md`

**เหตุใดจึงไม่กระทบความถูกต้องของข้อมูล**

- ทุก run ถูกบันทึกลงสมุดบันทึกแบบเพิ่มอย่างเดียวก่อนเรียกเอเจนต์ และบันทึกผลทันทีที่ได้กลับมา
  การหยุดกลางคันจึงทิ้งร่องรอยว่า run ใดถูกขัดจังหวะ แยกจาก run ที่ล้มเหลวจริง
- การทำต่อจากจุดที่ค้างจะคัดกรอง run ที่ล้มเหลวออกแล้วเก็บใหม่เสมอ
  ไม่มี cell ใดถูกตรึงเป็นความล้มเหลวถาวร
- สภาพ runtime ถูกตรวจเทียบกับค่าที่ตรึงไว้ทุก run ตลอดการเก็บข้อมูล
  รวมถึงหลังการหยุดและทำต่อทุกครั้ง

**สิ่งที่ต้องระบุ:** การเก็บข้อมูลกินเวลาหลายวันและหลายรอบของการทำต่อ
ซึ่งหมายความว่า run ไม่ได้เกิดขึ้นภายในหน้าต่างเวลาเดียวกัน หากผู้ให้บริการโมเดล
เปลี่ยนแปลงระบบระหว่างนั้นโดยไม่เปลี่ยนหมายเลขรุ่น การทดลองนี้จะตรวจไม่พบ
กลไกที่มีอยู่ตรวจได้เฉพาะการเปลี่ยนแปลงที่ปรากฏในหมายเลขรุ่นของเครื่องมือ
ชุด tool หรือชุด skill เท่านั้น

**ข้อสังเกตเชิงปฏิบัติการ: การยุติโปรเซสโดยไม่มีข้อความ**

การเก็บข้อมูลถูกยุติกลางคันโดยไม่มีข้อความใด ๆ สามครั้ง (รหัสจบ 1 · ไม่มี artifact ตัวสุดท้าย ·
fixture lock ค้าง) ที่อายุการทำงานต่างกัน คือ 62, 38 และ 30 นาที จึงไม่ใช่เพดานเวลาคงที่
ทุกครั้งเกิดขึ้นกับโปรเซสที่ยิงเป็นงานเบื้องหลังของ session ผู้ช่วย

เมื่อเปลี่ยนมายิง runner เป็นโปรเซสแยก (`Start-Process` แบบ detached) ซึ่งไม่ผูกกับอายุ
ของ session การยุติแบบไม่มีข้อความไม่เกิดขึ้นอีก และการรันหยุดเองเฉพาะเมื่อชนขีดจำกัด
การใช้งานรายรอบ ซึ่งเป็นการหยุดที่สะอาด สาเหตุจึงอยู่ที่สภาพแวดล้อมที่ยิงคำสั่ง
ไม่ใช่ที่ตัวโปรแกรมเก็บข้อมูลหรือที่ภาระงานอ่านเขียนไฟล์

เรื่องนี้ไม่กระทบความถูกต้องของข้อมูล เพราะ run ที่ถูกขัดจังหวะไม่มี artifact จึงไม่เข้าชุดข้อมูล
และถูกเก็บซ้ำในรอบถัดไป แต่บันทึกไว้เพราะเป็นข้อควรรู้สำหรับผู้ที่จะทำซ้ำการทดลองนี้:
**งานเก็บข้อมูลที่กินเวลาหลายชั่วโมงไม่ควรผูกกับอายุของ session ที่สั่งงาน**

*(บันทึกเหตุการณ์ทั้งหมด: `evidence/collection-log/`)*

### 6.x.12 ข้อมูลที่ถูกกันออกจากการวิเคราะห์โดยเจตนา

- **ชุดข้อมูลระหว่างพัฒนา** เก็บภายใต้เพดาน turn ที่ถูกยกเลิกไปแล้ว และภายใต้นิยาม
  การทดลองคนละชุด จึงใช้อ้างเป็นผลไม่ได้ เก็บไว้เป็นหลักฐานเชิงพัฒนาเท่านั้น
- **ความพยายามเก็บข้อมูลที่ล้มเหลวทั้งชุดจากการยืนยันตัวตนหมดอายุ** ไม่มี run ใดได้คะแนน
  ที่ใช้ได้ และไม่มีการตรึงสภาพ runtime จึงไม่ใช่ข้อมูล
- **ตัวเลขจากการทดลอง rule dilution** มาจาก mock adapter ทั้งหมด ห้ามอ้างในเล่มและบนสไลด์
