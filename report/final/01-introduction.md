# 1. บทนำ

เอเจนต์เขียนโค้ด (coding agent) คือโปรแกรมที่ใช้โมเดลภาษาขนาดใหญ่ (Large Language Model: LLM) อ่านโค้ด แก้ไฟล์ และรันคำสั่งในเครื่องของนักพัฒนาได้เอง ตัวอย่างที่ใช้กันแพร่หลาย ได้แก่ Claude Code, GitHub Copilot และ Cursor เมื่อนำเครื่องมือกลุ่มนี้ไปใช้ในองค์กร ความสามารถในการแก้ปัญหาเพียงอย่างเดียวไม่พอ ทีมพัฒนาต้องการให้เอเจนต์ทำงานตามกติกาของทีมด้วย เช่น แก้เฉพาะส่วนที่ได้รับมอบหมาย ไม่เพิ่มฟีเจอร์ที่ไม่มีใครขอ ตรวจผลกระทบก่อนแก้ส่วนที่คิดเงิน และไม่รันคำสั่งที่ลบข้อมูล

วิธีที่ใช้บอกกติกาเหล่านี้แก่เอเจนต์ เรียกรวมกันว่า *การจัดการบริบท* (Context Engineering) คือการเตรียมข้อมูลที่เอเจนต์จะเห็นก่อนและระหว่างทำงาน ในทางปฏิบัติมีสองรูปแบบหลัก รูปแบบแรกคือเขียนกฎทั้งหมดไว้ในไฟล์เดียว เช่น `CLAUDE.md` ซึ่งถูกโหลดเข้าบริบททุกครั้งที่เอเจนต์เริ่มงาน รูปแบบที่สองคือ ระบบทักษะเอเจนต์ (Agent Skills) ที่ Anthropic เปิดตัวในปี 2025 ซึ่งแยกกฎเป็นหน่วยย่อยที่มีคำอธิบายสั้น ๆ ว่าใช้เมื่อใด เอเจนต์เห็นเฉพาะคำอธิบายตอนเริ่มงาน และโหลดเนื้อหาเต็มเมื่องานตรงกับคำอธิบาย แนวคิดนี้เรียกว่าการเปิดเผยข้อมูลทีละขั้น (progressive disclosure) (Zhang et al., 2025)

แนวคิดของ Agent Skills ตั้งอยู่บนสมมติฐานว่า การไม่ใส่กฎที่ไม่เกี่ยวข้องเข้าบริบทจะช่วยให้เอเจนต์ทำตามกฎที่เกี่ยวข้องได้ดีขึ้น และประหยัดพื้นที่บริบท สมมติฐานนี้มีเหตุผลรองรับ และเริ่มมีงานที่วัดผลของ Agent Skills และไฟล์กฎแบบ "มีเทียบกับไม่มี" แล้ว (หัวข้อ 2.1.) แต่เท่าที่ผู้วิจัยค้น (ถึงเดือนตุลาคม 2569) ยังไม่พบงานที่เปรียบเทียบโดยตรงว่า เมื่อข้อผูกพันของกฎเท่ากัน การเขียนกฎแบบ Agent Skills ทำให้เอเจนต์ปฏิบัติตามกฎได้ต่างจากการเขียนกฎไว้ในไฟล์เดียวหรือไม่ เกณฑ์มาตรฐานที่มีอยู่อย่าง SWE-bench (Jimenez et al., 2024) วัดว่าเอเจนต์แก้ปัญหาได้หรือไม่ ไม่ได้วัดว่าแก้โดยไม่ทำสิ่งที่ไม่ได้สั่งหรือไม่ ส่วนรายงานสัมมนาในรายวิชานี้เมื่อปีการศึกษา 2568 ได้ศึกษาการทำ Context Engineering กับเอเจนต์เขียนโค้ดเชิงคุณภาพ ด้วยการสาธิตขั้นตอนการทำงาน (ศุภกร กรอบเพ็ชร และ ศศิชา โสมวิภาต, 2568) แต่ยังไม่ได้วัดผลเชิงปริมาณเทียบระหว่างรูปแบบ

คำถามนี้มีผลในทางปฏิบัติ ทีมที่กำลังตัดสินใจว่าจะเขียนกฎให้เอเจนต์แบบใด ต้องรู้ว่ารูปแบบที่ใหม่กว่าให้ผลดีกว่าจริง หรือแค่ต่างกันที่วิธีจัดเก็บ งานนี้จึงสร้างระบบวัดผลที่ให้เอเจนต์ทำโจทย์บนระบบจำลอง แล้วตรวจจากร่องรอยการทำงานจริงด้วยโปรแกรม ว่าเอเจนต์ปฏิบัติตามกฎได้แค่ไหนเมื่อได้รับกฎในรูปแบบต่างกัน

## 1.1. วัตถุประสงค์

1.1.1. เพื่อเปรียบเทียบการปฏิบัติตามกฎของเอเจนต์เขียนโค้ด เมื่อได้รับกฎที่มีข้อผูกพันเท่ากันในรูปแบบ Agent Skills และรูปแบบไฟล์กฎไฟล์เดียว

1.1.2. เพื่อพัฒนาระบบวัดผลที่ตรวจการปฏิบัติตามกฎจากร่องรอยการทำงานจริงของเอเจนต์ และตรวจความถูกต้องของตัวระบบวัดผลเองได้

1.1.3. เพื่อเสนอแนวทางการเขียนกฎให้เอเจนต์เขียนโค้ด สำหรับทีมพัฒนาที่นำเอเจนต์ไปใช้งาน

## 1.2. คำถามวิจัยและสมมติฐาน

**คำถามวิจัยหลัก:** เมื่อให้กฎที่มีข้อผูกพันเท่ากันทุกข้อ การส่งกฎแบบ Agent Skills (กลุ่ม A2) ทำให้เอเจนต์ปฏิบัติตามกฎ ต่างจากการส่งกฎแบบไฟล์เดียวที่โหลดตลอดเวลา (กลุ่ม A1) หรือไม่ ทั้งสองกลุ่มมีข้อผูกพันเท่ากันทั้ง 47 ข้อ (จากกฎ 20 ข้อ) แต่ถ้อยคำและความยาวของข้อความต่างกัน เพราะเป็นการเขียนกฎสองแบบที่ทีมพัฒนาใช้กันจริง คำถามนี้จึงเปรียบเทียบ *ชิ้นงานกฎสองรูปแบบ* ไม่ใช่กลไกการโหลดเพียงอย่างเดียว

ผู้วิจัยประกาศเกณฑ์ตัดสินไว้ล่วงหน้าเป็นสามทาง ได้แก่ *ต่างกัน* (p < 0.05) *เทียบเท่า* (ความต่างอยู่ภายใน ±0.125 ของตัวชี้วัด หรือราวการพลาดกฎสำคัญหนึ่งข้อต่อ run) หรือ *สรุปไม่ได้* และทำนายไว้ก่อนเก็บข้อมูลว่าผลต่างน่าจะใกล้ศูนย์

**คำถามรองหลัก:** เมื่อใช้ข้อความ*เหมือนกันทุกตัวอักษร*กับ Agent Skills แต่โหลดตลอดเวลา (กลุ่ม A5) ผลต่างจาก Agent Skills หรือไม่ คำถามนี้คือคำถามเรื่อง*กลไกการโหลด*โดยตรง เพราะสองกลุ่มต่างกันแค่ว่าข้อความถูกโหลดเมื่อใด แผนกำหนดให้ทดสอบคำถามนี้ได้ก็ต่อเมื่อคำถามหลักพบความต่างอย่างมีนัยสำคัญ

**คำถามประกอบ:** การมีกฎเทียบกับไม่มีกฎ (กลุ่ม A0) ต่างกันแค่ไหน และรูปแบบของกฎมีผลต่อต้นทุนการทำงานหรือไม่ คำถามกลุ่มนี้รายงานเป็นค่าประมาณพร้อมช่วงความเชื่อมั่น ไม่ได้ทดสอบตามแผน

**คำถามด้านเครื่องมือวัด (วัตถุประสงค์ข้อที่ 2):** ระบบวัดผลตรวจพบข้อบกพร่องของตัวเองได้ก่อนข้อบกพร่องนั้นกระทบผลหลักหรือไม่ ตอบด้วยจำนวนข้อบกพร่องที่ด่านตรวจแต่ละขั้นพบ และจำนวนที่หลุดไปถึงช่วงเก็บข้อมูลจริง

## 1.3. ขอบเขต

1.3.1. ใช้เอเจนต์ Claude Code กับโมเดล Claude Sonnet 5 รุ่นเดียว และคำสั่งภาษาไทย ผู้วิจัยเลือก Claude Code เพราะรองรับทั้งไฟล์กฎ `CLAUDE.md` และ Agent Skills ในเครื่องมือเดียว จึงเปรียบเทียบสองรูปแบบได้โดยไม่ต้องเปลี่ยนเอเจนต์

1.3.2. ใช้ระบบจำลองหนึ่งระบบ คือระบบจองเครื่อง GPU แบบเก็บลำดับเหตุการณ์ ที่ผู้วิจัยสร้างขึ้น มีข้อกำหนด 43 ข้อ

1.3.3. ใช้โจทย์ 22 ข้อ แบ่งเป็นโจทย์ที่มีกับดัก 7 ตระกูล 20 ข้อ และโจทย์ธรรมดาที่ไม่มีกับดัก 2 ข้อ กลุ่มทดลอง 4 กลุ่ม และรันซ้ำโจทย์ละ 3 รอบต่อกลุ่ม รวม 264 ครั้ง

1.3.4. วัดเฉพาะกฎที่ตรวจด้วยโปรแกรมได้จากร่องรอยการทำงาน เช่น ไฟล์ที่แก้ คำสั่งที่รัน ข้อความที่ตอบ และผลกระทบต่อข้อมูลย้อนหลัง

## 1.4. ประโยชน์ที่คาดว่าจะได้รับ

1.4.1. ทีมพัฒนาที่ใช้เอเจนต์เขียนโค้ด ได้หลักฐานเชิงปริมาณประกอบการเลือกรูปแบบการเขียนกฎ

1.4.2. ผู้ที่ต้องการวัดพฤติกรรมของเอเจนต์ ได้ระบบวัดผลแบบโอเพนซอร์สและแนวทางตรวจความถูกต้องของเครื่องมือวัด ซึ่งนำไปใช้กับเอเจนต์หรือโจทย์อื่นได้

1.4.3. ได้ตัวอย่างการทดลองกับ AI ที่ประกาศแผนล่วงหน้า และรายงานส่วนเบี่ยงเบนจากแผนครบถ้วน

## 1.5. นิยามศัพท์

**ตารางที่ 1** นิยามศัพท์ที่ใช้ในรายงาน

| คำศัพท์ | ความหมายในรายงานนี้ |
|---|---|
| เอเจนต์ (agent) | โปรแกรมที่ใช้ LLM ตัดสินใจและลงมือทำงานด้วยเครื่องมือ เช่น อ่านไฟล์ แก้ไฟล์ รันคำสั่ง |
| บริบท (context) | ข้อความทั้งหมดที่โมเดลเห็นในขณะหนึ่ง รวมคำสั่ง กฎ ไฟล์ที่อ่าน และผลของเครื่องมือ |
| Agent Skills | รูปแบบการจัดเก็บกฎหรือความรู้เป็นหน่วยย่อย ที่โหลดเนื้อหาเต็มเมื่องานตรงกับคำอธิบาย |
| ข้อผูกพัน | สิ่งที่กฎกำหนดให้ทำหรือห้ามทำหนึ่งข้อ กฎ 20 ข้อของงานนี้แยกได้เป็นข้อผูกพัน 47 ข้อ ซึ่ง A1 และ A2 มีครบเท่ากัน |
| กฎสำคัญ (critical rule) | กฎที่ถ้าละเมิดแล้วงานใช้ไม่ได้หรือเสียหาย ใช้คำนวณตัวชี้วัดหลัก แต่ละโจทย์มีเกณฑ์ตรวจระดับ critical ที่ตรวจข้อผูกพันเหล่านี้ในสถานการณ์ของโจทย์นั้น รวมทั้งชุด 169 เกณฑ์ |
| run | การให้เอเจนต์ทำโจทย์หนึ่งข้อหนึ่งครั้ง ตั้งแต่เริ่มจนจบรอบตอบกลับ |
| รอบตอบกลับ (follow-up) | ข้อความตายตัวที่ส่งให้เอเจนต์หนึ่งครั้งหลังรอบแรก เพื่อให้ทำงานต่อเมื่อไม่มีใครตอบคำถาม |
| RCRc | Requirement Compliance Rate, conditional on completion คือสัดส่วนของกฎสำคัญที่เอเจนต์ปฏิบัติตาม และให้ 0 ถ้างานหลักไม่สำเร็จ (หัวข้อ 3.5.) ตัวชี้วัดหลักของงาน |
| CRIT, SCOPE, pass^k | ตัวชี้วัดประกอบ ได้แก่ สัดส่วน run ที่ผ่านกฎสำคัญครบทุกข้อ (CRIT) สัดส่วน run ที่แก้เฉพาะไฟล์ในขอบเขตงาน (SCOPE) และสัดส่วนโจทย์ที่ผ่านกฎสำคัญครบทุกรอบที่รันซ้ำ (pass^k) |
| จุด (percentage point) | หน่วยของผลต่างระหว่างค่าที่เป็นร้อยละ เช่น 90% กับ 80% ต่างกัน 10 จุด |
| ช่วงความเชื่อมั่น (confidence interval: CI) | ช่วงของค่าที่ผลต่างจริงน่าจะอยู่ CI 95% กว้างกว่า CI 90% งานนี้ใช้ CI 90% ตัดสินความเทียบเท่า และรายงาน CI 95% ประกอบ |
| ค่า p | โอกาสที่จะเห็นผลต่างขนาดนี้หรือมากกว่า ถ้าสองกลุ่มไม่ต่างกันจริง ถ้าน้อยกว่า 0.05 ถือว่าต่างอย่างมีนัยสำคัญ |
| ขอบเขตความเทียบเท่า (equivalence margin) | ขนาดผลต่างที่ประกาศไว้ล่วงหน้าว่าเล็กเกินกว่าจะมีความหมายในทางปฏิบัติ งานนี้ใช้ ±12.5 จุด หรือราวการพลาดกฎสำคัญหนึ่งข้อต่องาน |
| sign-flip test | การทดสอบที่ถามว่า ถ้าสลับป้าย A2/A1 ของแต่ละโจทย์แบบสุ่ม จะได้ผลต่างเฉลี่ยมากเท่าที่เห็นบ่อยแค่ไหน ไม่ต้องสมมติรูปแบบการแจกแจงของข้อมูล |
| TOST | การทดสอบความเทียบเท่า ผ่านเมื่อช่วงความเชื่อมั่น 90% อยู่ในขอบเขตความเทียบเท่าทั้งช่วง |
| การทดสอบแบบลำดับตายตัว (fixed-sequence) | การทดสอบหลายข้อตามลำดับที่ล็อกไว้ ข้อถัดไปทดสอบได้ก็ต่อเมื่อข้อก่อนหน้าผ่าน เพื่อคุมโอกาสสรุปผิดรวม |
| การวิเคราะห์ความไว (sensitivity analysis) | การวิเคราะห์ซ้ำภายใต้สมมติฐานอื่น เพื่อดูว่าข้อสรุปเปลี่ยนหรือไม่ |
| Trigger F1 | ความแม่นของการที่ A2 เลือกโหลด skill ถูกงาน รวมสองด้าน ได้แก่ precision คือในครั้งที่โหลด skill เป็นงานที่ควรโหลดจริงกี่เปอร์เซ็นต์ และ recall คือในงานที่ควรโหลด ได้โหลดจริงกี่เปอร์เซ็นต์ ค่า 1.0 คือถูกทุกครั้ง |
| token | หน่วยย่อยของข้อความที่โมเดลประมวลผล ใช้คิดขนาดบริบทและต้นทุน |
| turn | หนึ่งรอบที่โมเดลตอบหรือเรียกเครื่องมือหนึ่งครั้ง ใช้กำหนดเพดานการทำงานของแต่ละรอบ |
| การประกาศแผนล่วงหน้า (pre-registration) | การล็อกสมมติฐานและวิธีวิเคราะห์ไว้ก่อนเก็บข้อมูล เพื่อกันการเลือกวิเคราะห์หลังเห็นผล |
