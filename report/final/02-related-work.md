# 2. แนวคิดและงานที่เกี่ยวข้อง

## 2.1. Context Engineering และ Agent Skills

Context Engineering คือการจัดเตรียมข้อมูลที่โมเดลจะได้รับก่อนและระหว่างทำงาน เพื่อให้เอเจนต์ทำงานตามที่ต้องการ ในงานพัฒนาซอฟต์แวร์ รูปแบบที่ใช้กันมากคือไฟล์กฎที่โหลดตลอดเวลา เช่น `CLAUDE.md` ของ Claude Code ข้อดีคือเรียบง่าย และแน่ใจได้ว่าเอเจนต์เห็นกฎครบ ข้อเสียคือกฎทุกข้อกินพื้นที่บริบทตลอดเวลา แม้ไม่เกี่ยวกับงานตรงหน้า

Agent Skills แยกกฎเป็นหน่วยย่อย Anthropic (n.d.) และ Zhang et al. (2025) อธิบายการโหลดเป็นสามชั้น ชั้นแรกโหลดเฉพาะชื่อและคำอธิบายของแต่ละ skill ชั้นที่สองโหลดเนื้อหาเต็มเมื่อ skill ถูกเลือก และชั้นที่สามโหลดไฟล์อ้างอิงเพิ่มเมื่อจำเป็น แนวคิดนี้ตั้งอยู่บนสมมติฐานโดยนัยว่า การไม่ใส่ข้อมูลที่ไม่เกี่ยวข้องเข้าบริบทช่วยให้เอเจนต์ทำตามข้อมูลที่เกี่ยวข้องได้ดีขึ้น แต่ยังไม่มีการวัดโดยตรงเมื่อควบคุมเนื้อหาของกฎให้เท่ากัน

## 2.2. การประเมินเอเจนต์ในงานพัฒนาซอฟต์แวร์และการวัดการทำตามคำสั่ง

SWE-bench (Jimenez et al., 2024) เป็นเกณฑ์มาตรฐานที่ใช้อ้างอิงมากที่สุดสำหรับเอเจนต์เขียนโค้ด ประกอบด้วยปัญหาจริงจาก GitHub 2,294 ข้อใน 12 repository ภาษา Python และตัดสินจากการที่ชุดทดสอบของ repository ผ่านหรือไม่ งานที่ตรวจคุณภาพของ SWE-bench (Aleithan et al., 2024) รายงานว่าคำตอบที่ผ่านราวหนึ่งในสาม (32.67%) มาจากเฉลยที่ปรากฏใน issue หรือคอมเมนต์อยู่แล้ว ซึ่งชี้ว่าการวัดด้วยผลของชุดทดสอบอย่างเดียวมีจุดอ่อน ที่สำคัญกว่าสำหรับงานนี้คือ เกณฑ์กลุ่มนี้ถามว่า "เอเจนต์แก้ปัญหาได้หรือไม่" ไม่ได้ถามว่า "แก้โดยไม่ทำสิ่งที่ไม่ได้สั่งหรือไม่" เอเจนต์ที่แก้ปัญหาสำเร็จแต่แก้ไฟล์อื่นพ่วงไปด้วย ยังได้คะแนนเต็ม

ด้านการวัดการทำตามคำสั่ง IFEval (Zhou et al., 2023) เสนอแนวคิดคำสั่งที่ตรวจได้ด้วยโปรแกรม (verifiable instructions) เช่น "เขียนเกินสี่ร้อยคำ" โดยไม่ต้องใช้คนหรือ LLM ตัดสิน งานนี้นำหลักเดียวกันมาใช้ แต่ยกจากระดับข้อความที่โมเดลเขียน ไปสู่ระดับการกระทำต่อระบบจริง คือตรวจจากโค้ดที่เปลี่ยน คำสั่งที่รัน และผลกระทบต่อข้อมูล

## 2.3. ลำดับชั้นของคำสั่ง ความยาวบริบท และความสุ่มของโมเดล

Wallace et al. (2024) เสนอให้ฝึกโมเดลให้ลำดับความสำคัญของคำสั่งตามแหล่งที่มา คือ system message เหนือ user message และเหนือเนื้อหาจากบุคคลที่สาม แต่ Geng et al. (2026) ทดสอบโมเดลชั้นนำหกตัวแล้วพบว่าการแยก system กับ user ไม่ได้สร้างลำดับชั้นที่เชื่อถือได้จริง งานสองชิ้นนี้ทำให้ผู้วิจัยตั้งคำถามว่า รูปแบบที่กฎถูกส่งเข้ามามีผลต่อการทำตามหรือไม่ และเป็นเหตุผลที่ชุดโจทย์มีกับดักแบบคำสั่งฝังในโค้ด ซึ่งเป็นเนื้อหาจากบุคคลที่สาม ส่วนงานด้านความปลอดภัยของ skill อย่าง SkillMutator (Kim et al., 2026) มองจากมุมผู้โจมตีที่ฝังคำสั่งอันตรายไว้ใน skill และพบว่าเครื่องมือสแกน skill ที่มีอยู่จับได้เพียง 2–17% ขณะที่งานนี้มองจากมุมผู้ใช้สุจริตที่เขียน skill เอง

Lost in the Middle (Liu et al., 2024) พบว่าโมเดลใช้ข้อมูลที่อยู่ต้นหรือท้ายบริบทได้ดีกว่าข้อมูลที่อยู่ตรงกลาง แม้ในโมเดลที่ออกแบบมาสำหรับบริบทยาว ข้อค้นพบนี้เป็นเหตุผลเชิงกลไกที่สนับสนุนแนวคิดการโหลดเฉพาะส่วนที่เกี่ยวข้อง แต่วัดจากงานค้นคืนข้อมูล ไม่ใช่งานที่ต้องทำตามกฎ

Ouyang et al. (2025) ศึกษาโจทย์สร้างโค้ด 829 ข้อจากชุดข้อมูลมาตรฐานสามชุด และพบว่าการตั้ง temperature เป็น 0 ไม่รับประกันว่าผลจะเหมือนเดิม ส่วน Song et al. (2024) โต้ว่าการประเมิน LLM ไม่ควรมองข้ามความสุ่ม สองงานนี้ชี้ตรงกันว่าผลจากการรันครั้งเดียวทำให้เข้าใจผิดได้ งานนี้จึงรันซ้ำหลายรอบต่อโจทย์ และรายงานช่วงความเชื่อมั่นคู่กับค่าประมาณทุกตัว

## 2.4. Requirements Traceability Matrix ในบทบาทเครื่องมือวัด

การกู้คืนความเชื่อมโยงระหว่างข้อกำหนดกับโค้ด (traceability link recovery) เป็นสาขาเดิมในวิศวกรรมซอฟต์แวร์ ซึ่งถามว่าจะกู้ความเชื่อมโยงจากสิ่งที่มนุษย์เขียนไว้ได้อย่างไร งานล่าสุดอย่าง TraceLLM (Alturayeif et al., 2026) ใช้ LLM ร่วมกับการออกแบบ prompt เพื่อกู้ความเชื่อมโยงนี้ งานนี้ใช้ RTM ในทิศกลับกัน เมื่อเอเจนต์เป็นผู้แก้โค้ด การแก้แต่ละส่วนสืบย้อนกลับไปยังข้อกำหนดได้หรือไม่ การแก้ที่สืบย้อนไม่ได้คือการทำงานนอกขอบเขต ซึ่งวัดเป็นตัวเลขได้ แนวคิดนี้เชื่อมกับคำว่า gold plating ในมาตรฐานการบริหารโครงการ (Project Management Institute, 2021) ซึ่งหมายถึงการส่งมอบเกินกว่าที่ข้อกำหนดระบุโดยไม่มีผู้ร้องขอ และถือเป็นความเสี่ยง ไม่ใช่คุณค่า

## 2.5. การทดลองแบบมีกลุ่มควบคุมและการประกาศแผนล่วงหน้า

ถ้าเปรียบเทียบเพียงเอเจนต์ที่ไม่มีกฎกับเอเจนต์ที่มี skill ผลที่ดีขึ้นอาจมาจากกฎ หรือจากการมีข้อความเพิ่มในบริบทเฉย ๆ ก็ได้ งานนี้จึงใช้กลุ่มควบคุมแบบ active control คือกฎเนื้อหาเดียวกันแต่จัดวางต่างกัน (A1) และกลุ่มที่ใช้ข้อความเดียวกันแต่โหลดต่างกัน (A5) เพื่อแยกผลของรูปแบบออกจากผลของเนื้อหา

เมื่อผู้วิจัยเป็นผู้ออกแบบทั้งกฎ โจทย์ และตัวตรวจ ความเสี่ยงที่จะเลือกวิธีวิเคราะห์หลังเห็นผลมีสูง งานนี้จึงประกาศสมมติฐาน ตัวชี้วัด และเกณฑ์ตัดสินไว้ล่วงหน้า และล็อกด้วย git tag ก่อนเก็บข้อมูล การเปลี่ยนแปลงหลังจากนั้นบันทึกเป็นส่วนเบี่ยงเบนพร้อมเหตุผลและวันที่

## 2.6. งานที่ใกล้เคียงในรายวิชาและช่องว่างที่งานนี้เติม

รายงานสัมมนาของ ศุภกร กรอบเพ็ชร และ ศศิชา โสมวิภาต (2568) ในรายวิชานี้ ศึกษา Context Engineering ในเอเจนต์ LLM สำหรับงานพัฒนาระบบ โดยทบทวนนิยามและกลยุทธ์ของ Context Engineering แล้วสาธิตกลยุทธ์เขียน เลือก และย่อบริบทกับ GitHub Copilot บนโปรเจกต์ระบบตรวจจับใบหน้า การประเมินผลเปรียบเทียบการทำกับไม่ทำ Context Engineering ด้วยตัวอย่างการทำงาน พบว่าเอเจนต์ที่มีบริบทแนะนำไลบรารีที่เข้ากับโปรเจกต์ และปฏิเสธคำสั่งที่อาจทำลายไฟล์ของโปรเจกต์ ขณะที่เอเจนต์ที่ไม่มีบริบทพยายามทำตามคำสั่งนั้น งานดังกล่าวเป็นการประเมินเชิงคุณภาพจากกรณีตัวอย่าง ไม่ได้รันซ้ำหรือเปรียบเทียบรูปแบบของบริบทด้วยการทดลองที่มีกลุ่มควบคุม
