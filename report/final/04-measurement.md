# 4. ระบบวัดผลและการตรวจเครื่องมือวัด

การวัดพฤติกรรมของเอเจนต์ต้องมีเครื่องมือที่เรียกเอเจนต์ให้ทำงาน เก็บร่องรอย ให้คะแนน และคุมให้ทุก run อยู่ในสภาพเดียวกัน ผู้วิจัยพัฒนาเครื่องมือชุดนี้ขึ้นเองชื่อ SkillBench บทนี้อธิบายการทำงานของเครื่องมือ และวิธีที่ใช้ตรวจว่าเครื่องมือวัดถูกต้อง ซึ่งเป็นส่วนที่ใช้เวลาพัฒนามากที่สุดของงานนี้

## 4.1. สถาปัตยกรรมของระบบวัดผล

SkillBench เขียนด้วย JavaScript บน Node.js โดยไม่ใช้ไลบรารีภายนอก แบ่งเป็นห้าส่วนตามตารางที่ 7

**ตารางที่ 7** ส่วนประกอบของ SkillBench

| ส่วน | หน้าที่ | ไฟล์หลัก |
|---|---|---|
| Adapter | เรียก Claude Code CLI และแปลงผลเป็นรูปแบบกลาง | `src/adapters/claude-cli.mjs` |
| Runner | สุ่มลำดับ ติดตั้งบริบท เก็บผล ตรวจสภาพ และทำต่อเมื่อถูกขัดจังหวะ | `src/runner.mjs` |
| Grader | ให้คะแนนตามกฎของแต่ละโจทย์ | `src/graders.mjs` |
| Stats | สูตรสถิติทั้งหมด | `src/stats.mjs` |
| Analyze | ประกอบรายงานและไฟล์ตัวเลขจากผลที่ให้คะแนนแล้ว | `src/analyze.mjs` |

ขั้นตอนของหนึ่ง run แสดงในรูปที่ 2 ระบบรีเซ็ตโค้ดของระบบจำลองกลับสู่สภาพเริ่มต้น ติดตั้งไฟล์ของกลุ่มทดลองและสภาพเริ่มต้นของโจทย์ วัดค่าตั้งต้น เช่น ยอดใบแจ้งหนี้ย้อนหลัง แล้วเรียกเอเจนต์พร้อมคำสั่ง เมื่อรอบแรกจบ ระบบเก็บภาพของงานไว้ ส่งรอบตอบกลับ แล้วเก็บผลสุดท้าย จากนั้นวัดค่าเดิมซ้ำ ตรวจสภาพการทำงานเทียบกับค่าที่ตรึงไว้ ให้คะแนน และบันทึกลงไฟล์ checkpoint ทันที การบันทึกทุก run ทำให้การเก็บข้อมูลที่ใช้เวลาหลายสิบชั่วโมงทำต่อได้เสมอเมื่อถูกขัดจังหวะ ไม่ว่าจะเพราะโควตาการใช้งานหมดหรือโปรแกรมหยุดทำงาน

> **[รูปที่ 2 ขั้นตอนของหนึ่ง run]** รีเซ็ตระบบจำลอง → ติดตั้งไฟล์ของกลุ่มทดลองและสภาพเริ่มต้นของโจทย์ → วัดค่าตั้งต้น → เอเจนต์ทำงานรอบแรก → เก็บภาพรอบแรก → รอบตอบกลับ → วัดค่าปลายทาง → ตรวจสภาพ runtime → ให้คะแนน → บันทึก checkpoint

รูปที่ 3 เป็นตัวอย่างร่องรอยของรอบแรกจาก run จริงหนึ่ง run คือโจทย์ S10 (ข้อกำหนดขัดกัน) ของกลุ่ม A2 ในรอบแรก เอเจนต์โหลด skill สามตัว อ่านข้อกำหนด เอกสารสถาปัตยกรรม โค้ด เทส และสัญญา API โดยยังไม่แก้ไฟล์ใด แล้วหยุดถามผู้ใช้ว่าจะยึด REQ-24 หรือ REQ-27 เพราะเกณฑ์ยอมรับของสองข้อให้ผลตรงข้ามกันในกรณีเดียวกัน หลังได้รอบตอบกลับ เอเจนต์จึงรันสคริปต์ตรวจยอดใบแจ้งหนี้และเทส แล้วเริ่มแก้โค้ด ร่องรอยทั้งหมดนี้คือข้อมูลที่ตัวตรวจใช้ให้คะแนน run นั้น

> **[รูปที่ 3 ตัวอย่างร่องรอยการทำงานจริงของเอเจนต์]**

## 4.2. การติดตั้งบริบทและการยืนยันว่าเข้าถึงเอเจนต์จริง

ตัวแปรต้นส่งเข้าไปด้วยการวางไฟล์ลงในโฟลเดอร์งานก่อนเอเจนต์เริ่ม A1 และ A5 ได้ไฟล์ `CLAUDE.md` ส่วน A2 ได้ `CLAUDE.md` สั้นกับไฟล์ skill 4 ไฟล์ใน `.claude/skills/` ไฟล์เหล่านี้ถูก commit ทับลงไปทันทีหลังวาง มิฉะนั้นจะปรากฏเป็นไฟล์ที่เอเจนต์สร้างเอง และทำให้กฎเรื่องขอบเขตตกทุก run ทุกกลุ่ม

การวางไฟล์ไม่ได้รับประกันว่าเนื้อหาเข้าไปถึงเอเจนต์ ระบบจึงแยกการวัดออกเป็นสองชั้น ได้แก่ **การเรียก** skill ซึ่งเป็นเจตนาของเอเจนต์ และ **การโหลดสำเร็จ** ซึ่งเนื้อหาเข้าไปในบริบทจริง ทุก run ต้องผ่านเงื่อนไขว่ากลุ่มที่ไม่มี skill ติดตั้งต้องโหลด skill สำเร็จเป็นศูนย์ ถ้าไม่เป็นศูนย์แปลว่าการทดลองปนเปื้อน ตัวเลขชุดนี้เรียกว่าการตรวจสภาพการทดลอง (manipulation check) และรายงานไว้ในหัวข้อ 5.7.

## 4.3. ตัวตรวจกฎ

ตัวตัดสินว่ากฎผ่านหรือไม่เป็นโปรแกรมทั้งหมด และให้ผลเดิมทุกครั้งที่รันซ้ำบนข้อมูลเดิม ตัวตรวจทุกตัวเป็นฟังก์ชันที่รับผลดิบของ run แล้วคืนค่าผ่านหรือตก โดยไม่พึ่งเวลาปัจจุบันหรือค่าสุ่ม คุณสมบัตินี้ทำให้ *ให้คะแนนซ้ำ* ได้ เมื่อแก้ตัวตรวจ ผู้วิจัยรันการให้คะแนนใหม่บนข้อมูลเดิมได้ทันที และแยกได้ว่าคะแนนเปลี่ยนเพราะเครื่องมือหรือเพราะเอเจนต์

ตัวตรวจแบ่งเป็นห้ากลุ่ม คือ ตรวจเนื้อหาของโค้ดที่เปลี่ยน ตรวจขอบเขตไฟล์ที่แตะ ตรวจผลกระทบที่มองไม่เห็น (ค่าย้อนหลังและชุดทดสอบ) ตรวจข้อความที่ตอบผู้ใช้ และตรวจการใช้เครื่องมือกับลำดับของคำสั่ง ผู้วิจัยเลือกให้กฎทุกข้อตรวจด้วยโปรแกรมได้ เพราะถ้าใช้คนหรือโมเดลภาษาตัดสิน ผลจะขึ้นกับผู้ตัดสินและทำซ้ำไม่ได้ ข้อแลกเปลี่ยนคือกฎบางประเภทที่ต้องใช้วิจารณญาณวัดไม่ได้ ซึ่งเป็นข้อจำกัดในหัวข้อ 6.4.

## 4.4. ทำไมระบบวัดเอเจนต์จึงล้มเหลวแบบเงียบ

ในซอฟต์แวร์ทั่วไป ความผิดพลาดมักแสดงตัว เช่น โปรแกรมหยุด หรือเทสไม่ผ่าน แต่เมื่อสิ่งที่ถูกวัดคือเอเจนต์ซึ่งมีความสุ่ม พฤติกรรมของเอเจนต์ปกติกับอาการของเครื่องมือที่พังมีหน้าตาเหมือนกัน ดังตารางที่ 8

**ตารางที่ 8** อาการเดียวกัน สองสาเหตุ

| สิ่งที่เห็น | ถ้าเอเจนต์ทำงานปกติ | ถ้าเครื่องมือวัดพัง |
|---|---|---|
| ไม่แก้ไฟล์เลย | ตัดสินว่างานอยู่นอกขอบเขต | ไม่เคยได้รับคำสั่ง |
| กฎข้อหนึ่งตกทุก run | โจทย์ยากจริง | ตัวตรวจเขียนผิด |
| ทุกกลุ่มได้คะแนนเท่ากัน | วิธีส่งกฎไม่มีผล ซึ่งเป็นข้อค้นพบ | บริบทไม่เคยถูกติดตั้ง |

แถวสุดท้ายสำคัญที่สุดสำหรับงานนี้ เพราะผลแบบ "ไม่ต่างกัน" คือผลที่เป็นไปได้จริงของคำถามวิจัย ถ้าไม่มีกลไกยืนยันว่าเครื่องมือทำงานถูก ผู้วิจัยจะแยกไม่ออกว่ากำลังรายงานข้อค้นพบ หรือรายงานความล้มเหลวของเครื่องมือตัวเอง

หลักที่ใช้รับมือคือ **ป้อนข้อมูลที่รู้คำตอบอยู่แล้ว แล้วตรวจว่าผลออกมาตรง** ตลอดโครงการ ผู้วิจัยพบข้อบกพร่องของเครื่องมือรวมหลายสิบจุด ได้แก่ 23 จุดในช่วงพัฒนาถึง 10 ส.ค. 2569 อีก 15 จุดในรอบตรวจ 4 ก.ย. 2569 และ 8 จุดในรอบนำร่องของชุดที่ 3 แทบไม่มีจุดใดที่การอ่านโค้ดจับได้ สิ่งที่จับได้คือด่านตรวจที่ป้อนข้อมูลรู้คำตอบ ซึ่งรันได้โดยไม่ต้องเรียกเอเจนต์จริง เช่น

- **ด่านตรวจกลุ่มทดลอง** ติดตั้งไฟล์ของทุกกลุ่มลงระบบจริงแล้วตรวจว่าข้อผูกพันทั้ง 47 ข้อครบทั้ง A1 และ A2
- **ด่านยอมรับห้าด่านของโจทย์** (หัวข้อ 3.3.3.) ยืนยันว่าทุกโจทย์มีทางได้คะแนนเต็ม และคำตอบผิดได้คะแนนต่ำจริง
- **เอเจนต์จำลอง** สามแบบ (ไม่ทำอะไร · ทำนิดหน่อยแต่ไม่สำเร็จ · สำเร็จแต่ละเมิดกฎ) ยืนยันว่าตัวชี้วัดไม่ให้รางวัลกับการไม่ทำงาน
- **ข้อความตัวอย่างที่ต้องผ่านและต้องตก** สำหรับกฎที่ตรวจข้อความทุกข้อ รันในชุดทดสอบของระบบ (249 ข้อ ผ่านทั้งหมด ณ วันเก็บข้อมูล)

ตัวอย่างข้อบกพร่องที่จับได้ก่อนชุดที่ 3 คือกฎข้อหนึ่งของ S10 ซึ่งจับคำว่า "ขัด" เพื่อดูว่าเอเจนต์แจ้งข้อกำหนดที่ขัดกันหรือไม่ แต่จับคำว่า "ไม่ขัดกับ" ด้วย run เดียวที่ "ผ่าน" กฎข้อนี้ในชุดที่ 2 จึงเป็นผลบวกลวง

## 4.5. การคุมตัวแปรระหว่างเก็บข้อมูล

การประกาศว่าตัวแปรถูกควบคุมยังไม่พอ ต้องตรวจทุก run ว่าคุมได้จริง SkillBench บังคับเรื่องต่อไปนี้

1. **สภาพ runtime ตรึงไว้ใน manifest** — run แรกบันทึกเวอร์ชัน CLI ชุดเครื่องมือ ชุด skill ที่มากับเครื่องมือ และแหล่งสิทธิ์การใช้งาน run ถัดไปทุก run ต้องตรงกัน ถ้าไม่ตรง ระบบจะหยุดทั้งชุดทันที เช่น เมื่อ CLI อัปเดตตัวเองกลางทาง
2. **ไฟล์ที่นิยามการทดลองถูกล็อกด้วย digest** — ข้อความของกลุ่ม โจทย์ ตัวตรวจ และโค้ดของระบบวัดถูกคำนวณลายนิ้วมือทุก run การแก้ไฟล์เหล่านี้ระหว่างเก็บข้อมูลจะหยุดทั้งชุด
3. **ความจำอัตโนมัติ (auto-memory) ของเอเจนต์** — Claude Code บันทึกความจำข้าม session ได้ ถ้าปล่อยไว้ run หนึ่งจะส่งผลต่อ run ถัดไป ชุดที่ 3 จึงย้ายไฟล์ความจำที่เอเจนต์เขียนไปเก็บเป็นหลักฐานทันทีหลังจบ run และยืนยันว่าความจำว่างก่อน run ถัดไป ในการเก็บข้อมูลหลักเกิดขึ้น 3 ครั้งจาก 264 run
4. **สมุดบันทึกความพยายาม (attempt provenance)** — ทุกครั้งที่เริ่ม run ระบบบันทึกแบบเพิ่มอย่างเดียว ว่าเริ่มเมื่อใด จบอย่างไร และถูกนับหรือไม่ จึงตรวจย้อนได้ว่าไม่มี run ใดถูกรันซ้ำเพื่อเลือกผลที่ดีกว่า
5. **ห้ามดูผลแยกกลุ่มระหว่างเก็บข้อมูล** — ระหว่างเก็บ ผู้วิจัยตรวจได้เฉพาะสุขภาพของเครื่องมือแบบรวมทุกกลุ่ม

กลไกเหล่านี้ทำงานจริงระหว่างเก็บข้อมูลชุดที่ 3 ข้อ 1 หยุดการเก็บข้อมูลหนึ่งครั้ง เมื่อเอเจนต์กลุ่ม A5 เรียก skill ด้วยชื่อที่พิมพ์เพี้ยน และการตรวจสุขภาพแบบรวมทุกกลุ่มพบตัวตรวจที่บกพร่อง 3 จุด ทั้งสองเรื่องจัดการตามกติกาที่ประกาศไว้ และบันทึกเป็นส่วนเบี่ยงเบนจากแผนก่อนดูผล (หัวข้อ 5.1.)

## 4.6. สิ่งที่นำไปใช้กับงานอื่นได้

บทเรียนจากการสร้างเครื่องมือชุดนี้ใช้ได้กับงานใดก็ตามที่วัดพฤติกรรมของเอเจนต์

- ผลแบบ "ไม่ต่างกัน" ต้องมีหลักฐานว่าเครื่องมือทำงาน ก่อนจะนับเป็นข้อค้นพบ
- ทุกตัวตรวจต้องมีกรณีที่รู้คำตอบให้ทดสอบ ทั้งกรณีที่ต้องผ่านและที่ต้องตก
- ตัวแปรควบคุมต้องถูกตรวจทุก run ไม่ใช่แค่ประกาศไว้ในไฟล์ตั้งค่า
- เก็บผลดิบทั้งหมด และเขียนตัวตรวจให้ให้คะแนนซ้ำได้ เพราะข้อบกพร่องมักพบหลังเก็บข้อมูลไปแล้ว
