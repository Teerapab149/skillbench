# 4. ระบบวัดผลและการตรวจเครื่องมือวัด

การวัดพฤติกรรมของเอเจนต์ต้องใช้เครื่องมือที่สั่งให้เอเจนต์ทำงาน เก็บร่องรอย ให้คะแนน และทำให้แต่ละ run เริ่มจากสภาพเดียวกัน ผู้วิจัยจึงสร้างเครื่องมือชื่อ SkillBench ขึ้นเอง บทนี้อธิบายว่าเครื่องมือทำงานอย่างไร และตรวจสอบอย่างไรว่าคะแนนที่ได้มาจากพฤติกรรมของเอเจนต์จริง ไม่ใช่จากข้อผิดพลาดของเครื่องมือ

## 4.1. สถาปัตยกรรมของระบบวัดผล

SkillBench เขียนด้วย JavaScript บน Node.js โดยไม่ใช้ไลบรารีภายนอก และแบ่งการทำงานออกเป็น 5 ส่วนตามตารางที่ 7

**ตารางที่ 7** ส่วนประกอบของ SkillBench

| ส่วน | หน้าที่ | ไฟล์หลัก |
|---|---|---|
| Adapter | เรียก Claude Code CLI และแปลงผลเป็นรูปแบบกลาง | `src/adapters/claude-cli.mjs` |
| Runner | สุ่มลำดับ ติดตั้งบริบท เก็บผล ตรวจสภาพ และทำต่อเมื่อถูกขัดจังหวะ | `src/runner.mjs` |
| Grader | ให้คะแนนตามกฎของแต่ละโจทย์ | `src/graders.mjs` |
| Stats | สูตรสถิติทั้งหมด | `src/stats.mjs` |
| Analyze | ประกอบรายงานและไฟล์ตัวเลขจากผลที่ให้คะแนนแล้ว | `src/analyze.mjs` |

รูปที่ 2 แสดงขั้นตอนของหนึ่ง run เริ่มจากคืนระบบจำลองสู่สภาพเริ่มต้น แล้วติดตั้งไฟล์ของกลุ่มและสภาพเริ่มต้นของโจทย์ ระบบบันทึกค่าก่อนเริ่ม เช่น ยอดใบแจ้งหนี้ย้อนหลัง จากนั้นเรียกเอเจนต์ให้ทำงาน เมื่อรอบแรกจบ ระบบเก็บสำเนาผลไว้ ส่งข้อความตอบกลับ แล้วเก็บผลสุดท้ายอีกครั้ง ก่อนเปรียบเทียบกับค่าตั้งต้นและให้คะแนน ผลของแต่ละ run ถูกบันทึกลงไฟล์ checkpoint ทันที จึงกลับมาทำงานต่อได้หากโควตาหมดหรือโปรแกรมหยุดกลางคัน แม้การเก็บข้อมูลจะใช้เวลาหลายสิบชั่วโมง

> **[รูปที่ 2 ขั้นตอนของหนึ่ง run]** รีเซ็ตระบบจำลอง → ติดตั้งไฟล์ของกลุ่มทดลองและสภาพเริ่มต้นของโจทย์ → วัดค่าตั้งต้น → เอเจนต์ทำงานรอบแรก → เก็บภาพรอบแรก → รอบตอบกลับ → วัดค่าปลายทาง → ตรวจสภาพ runtime → ให้คะแนน → บันทึก checkpoint

รูปที่ 3 แสดงตัวอย่างการทำงานจริงในโจทย์ S10 ซึ่งมีข้อกำหนดขัดกัน ของกลุ่ม A2 ในรอบแรก เอเจนต์โหลด skill 3 ตัว แล้วอ่านข้อกำหนด เอกสารสถาปัตยกรรม โค้ด เทส และสัญญา API โดยยังไม่แก้ไฟล์ จากนั้นหยุดถามว่าควรยึด REQ-24 หรือ REQ-27 เพราะข้อกำหนดทั้งสองให้ผลตรงข้ามกันในกรณีเดียวกัน หลังได้รับข้อความตอบกลับ เอเจนต์จึงเรียกสคริปต์ตรวจยอดใบแจ้งหนี้และรันเทส ก่อนเริ่มแก้โค้ด ระบบใช้ร่องรอยทั้งหมดนี้ในการให้คะแนน run ดังกล่าว

> **[รูปที่ 3 ตัวอย่างร่องรอยการทำงานจริงของเอเจนต์]**

## 4.2. การติดตั้งบริบทและการยืนยันว่าเข้าถึงเอเจนต์จริง

ก่อนเริ่มงาน ผู้วิจัยติดตั้งไฟล์ของแต่ละกลุ่มลงในโฟลเดอร์โปรเจกต์ โดย A1 และ A5 ได้ไฟล์ `CLAUDE.md` ส่วน A2 ได้ไฟล์ CLAUDE.md แบบสั้นและไฟล์ skill 4 ไฟล์ใน `.claude/skills/` หลังติดตั้งจะ commit ไฟล์เหล่านี้ทันที เพื่อไม่ให้ระบบเข้าใจว่าเป็นไฟล์ที่เอเจนต์สร้างขึ้นเอง ซึ่งจะทำให้กฎเรื่องขอบเขตไฟล์ตกทุก run

การติดตั้งไฟล์อย่างเดียวไม่ได้ยืนยันว่าเอเจนต์ได้รับเนื้อหานั้นจริง จึงแยกการตรวจเป็น 2 เรื่อง คือ “**การเรียก** skill” ซึ่งบอกว่าเอเจนต์พยายามเรียกหรือไม่ และ “**การโหลดสำเร็จ**” ซึ่งยืนยันว่าเนื้อหาถูกใส่เข้าไปในบริบทจริง ทุก run ต้องตรวจได้ว่ากลุ่มที่ไม่ได้ติดตั้ง skill มีจำนวนการโหลดสำเร็จเป็นศูนย์ หากพบค่าอื่นแสดงว่าการทดลองอาจปนเปื้อน การตรวจนี้เรียกว่า manipulation check และรายงานไว้ในหัวข้อ 5.7.

## 4.3. ตัวตรวจกฎ

โปรแกรมเป็นผู้ตัดสินว่ากฎผ่านหรือตกทั้งหมด และเมื่อนำข้อมูลเดิมมารันซ้ำต้องได้ผลเหมือนเดิม ตัวตรวจแต่ละตัวรับผลดิบของ run แล้วส่งกลับว่าผ่านหรือตก โดยไม่อิงเวลาปัจจุบันหรือค่าสุ่ม จึงให้คะแนนซ้ำได้ เมื่อแก้ตัวตรวจ ผู้วิจัยสามารถนำข้อมูลเดิมมาคำนวณใหม่และดูได้ว่าคะแนนเปลี่ยนเพราะตัวตรวจหรือเพราะพฤติกรรมของเอเจนต์

ตัวตรวจแบ่งเป็น 5 กลุ่ม ได้แก่ ตรวจโค้ดที่เปลี่ยน ตรวจไฟล์ที่เอเจนต์แตะ ตรวจผลกระทบที่ซ่อนอยู่ เช่น ข้อมูลย้อนหลังและผลทดสอบ ตรวจข้อความตอบผู้ใช้ และตรวจการใช้เครื่องมือกับลำดับคำสั่ง ผู้วิจัยเลือกให้ทุกกฎตรวจด้วยโปรแกรม เพราะหากใช้คนหรือโมเดลภาษาตัดสิน ผลอาจต่างกันตามผู้ตัดสินและทำซ้ำได้ยาก ข้อจำกัดคือกฎบางอย่างที่ต้องอาศัยวิจารณญาณยังวัดไม่ได้ ซึ่งจะกล่าวถึงในหัวข้อ 6.4.

## 4.4. ทำไมระบบวัดเอเจนต์จึงล้มเหลวแบบเงียบ

ในซอฟต์แวร์ทั่วไป ข้อผิดพลาดมักเห็นได้ชัด เช่น โปรแกรมหยุดทำงานหรือเทสไม่ผ่าน แต่เมื่อวัดเอเจนต์ที่มีพฤติกรรมไม่คงที่ อาการที่เกิดจากเอเจนต์จริงกับอาการที่เกิดจากเครื่องมือวัดผิดพลาดอาจดูเหมือนกันได้ ดังตัวอย่างในตารางที่ 8

**ตารางที่ 8** อาการเดียวกัน สองสาเหตุ

| สิ่งที่เห็น | ถ้าเอเจนต์ทำงานปกติ | ถ้าเครื่องมือวัดพัง |
|---|---|---|
| ไม่แก้ไฟล์เลย | ตัดสินว่างานอยู่นอกขอบเขต | ไม่เคยได้รับคำสั่ง |
| กฎข้อหนึ่งตกทุก run | โจทย์ยากจริง | ตัวตรวจเขียนผิด |
| ทุกกลุ่มได้คะแนนเท่ากัน | วิธีส่งกฎไม่มีผล ซึ่งเป็นข้อค้นพบ | บริบทไม่เคยถูกติดตั้ง |

ตัวอย่างแถวสุดท้ายสำคัญเป็นพิเศษ เพราะผล "ไม่พบความต่าง" อาจเป็นคำตอบจริงของงานวิจัยก็ได้ หากไม่ตรวจว่าเครื่องมือทำงานถูกต้อง ผู้วิจัยอาจแยกไม่ออกว่าผลที่รายงานเป็นข้อค้นพบ หรือเป็นผลจากเครื่องมือที่ไม่สามารถตรวจจับความต่างได้

วิธีรับมือคือทดสอบเครื่องมือด้วยข้อมูลที่รู้คำตอบอยู่แล้ว ตลอดโครงการพบข้อบกพร่องของเครื่องมือหลายสิบจุด ได้แก่ 23 จุดในช่วงพัฒนาถึง 10 ส.ค. 2569 อีก 15 จุดในการตรวจวันที่ 4 ก.ย. 2569 และ 8 จุดในการนำร่องชุดที่ 3 ข้อบกพร่องส่วนใหญ่ไม่สามารถพบได้จากการอ่านโค้ดอย่างเดียว แต่ตรวจพบได้ด้วยการป้อนข้อมูลตัวอย่างที่คาดการณ์ผลไว้ก่อน โดยไม่ต้องเรียกเอเจนต์จริง เช่น

- ตรวจกลุ่มทดลอง — ติดตั้งไฟล์ของทุกกลุ่มบนระบบจริง แล้วตรวจว่ากฎที่ต้องมีครบทั้ง 47 ข้อใน A1 และ A2
- ตรวจโจทย์ 5 ด่าน — ยืนยันว่าแต่ละโจทย์มีคำตอบที่ทำคะแนนได้เต็ม และคำตอบผิดได้คะแนนต่ำจริง (ดูหัวข้อ 3.3.3.)
- ทดสอบด้วย**เอเจนต์จำลอง** — ใช้เอเจนต์ 3 แบบ ได้แก่ ไม่ทำอะไร, ทำบางอย่างแต่งานไม่สำเร็จ และทำงานสำเร็จแต่ละเมิดกฎ เพื่อยืนยันว่าตัวชี้วัดไม่ให้รางวัลกับการไม่ทำงาน
- ทดสอบข้อความตัวอย่าง — กฎที่ตรวจข้อความทุกข้อมีตัวอย่างที่ต้องผ่านและต้องตก และรันอยู่ในชุดทดสอบของระบบวัดผล ซึ่งมีทั้งหมด 249 ข้อและผ่านครบ ณ วันเก็บข้อมูล

ตัวอย่างข้อผิดพลาดที่พบก่อนการทดลองชุดที่ 3 คือ ตัวตรวจของ S10 ใช้คำว่า "ขัด" เพื่อตรวจว่าเอเจนต์แจ้งข้อกำหนดที่ขัดกันหรือไม่ แต่ตัวตรวจกลับจับข้อความ "ไม่ขัดกับ" ด้วย ทำให้ข้อความที่บอกว่าไม่มีความขัดแย้งถูกนับผิดเป็นการแจ้งความขัดแย้ง run เดียวที่ "ผ่าน" กฎข้อนี้ในชุดที่ 2 จึงเป็นผลบวกลวง

## 4.5. การคุมตัวแปรระหว่างเก็บข้อมูล

การระบุไว้ในแผนว่าควบคุมตัวแปรแล้ว ยังไม่เพียงพอ ต้องตรวจทุก run ด้วยว่าตัวแปรเหล่านั้นคงที่จริง SkillBench จึงตรวจเงื่อนไขต่อไปนี้ระหว่างเก็บข้อมูล

1. ตรวจสภาพแวดล้อมที่ใช้รัน — บันทึกเวอร์ชัน CLI เครื่องมือ skill ที่ติดมากับเครื่องมือ และแหล่งสิทธิ์ใช้งานจาก run แรก จากนั้นตรวจทุก run ว่าตรงกัน หากไม่ตรงจะหยุดการทดลองทั้งชุด เช่น เมื่อ CLI อัปเดตตัวเองระหว่างทาง
2. ล็อกไฟล์ที่กำหนดการทดลอง — คำนวณค่าลายนิ้วมือดิจิทัล (digest) ของข้อความแต่ละกลุ่ม โจทย์ ตัวตรวจ และโค้ดระบบวัดทุก run หากไฟล์ใดเปลี่ยนระหว่างเก็บข้อมูล ระบบจะหยุดทั้งชุด
3. ป้องกันความจำข้าม run — Claude Code สามารถบันทึกความจำจาก session หนึ่งไปยังอีก session ได้ หากไม่จัดการ ความจำจาก run ก่อนอาจมีผลต่อ run ถัดไป ชุดที่ 3 จึงเก็บไฟล์ความจำที่เอเจนต์สร้างไว้เป็นหลักฐานหลังจบแต่ละ run และตรวจว่าพื้นที่ความจำว่างก่อนเริ่ม run ใหม่ เหตุการณ์นี้เกิดขึ้น 3 ครั้งจาก 264 run
4. บันทึกประวัติ run — ระบบบันทึกแบบเพิ่มข้อมูลอย่างเดียวว่าแต่ละ run เริ่มเมื่อใด จบอย่างไร และถูกนำมานับผลหรือไม่ จึงตรวจย้อนหลังได้ว่าไม่มีการรันซ้ำเพื่อเลือกผลที่ดีกว่า
5. ไม่ดูผลแยกกลุ่มระหว่างเก็บข้อมูล — ระหว่างเก็บข้อมูล ผู้วิจัยตรวจได้เฉพาะสถานะสุขภาพของเครื่องมือโดยรวม ไม่ดูผลของแต่ละกลุ่มแยกกัน

กลไกเหล่านี้ถูกใช้จริงระหว่างการเก็บข้อมูลชุดที่ 3 ข้อแรกทำให้ต้องหยุดการเก็บข้อมูลหนึ่งครั้ง เมื่อเอเจนต์กลุ่ม A5 เรียก skill ด้วยชื่อที่พิมพ์ผิด ส่วนการตรวจสุขภาพเครื่องมือแบบรวมทุกกลุ่มพบตัวตรวจบกพร่อง 3 จุด ผู้วิจัยจัดการทั้งสองเรื่องตามกติกาที่ประกาศไว้ และบันทึกเป็นส่วนเบี่ยงเบนจากแผนก่อนตรวจผลแยกกลุ่ม (หัวข้อ 5.1.)

## 4.6. สิ่งที่นำไปใช้กับงานอื่นได้

หลักจากการสร้าง SkillBench สามารถนำไปใช้กับงานอื่นที่ต้องวัดพฤติกรรมของเอเจนต์ได้เช่นกัน

- หากผลออกมาว่า "ไม่ต่างกัน" ต้องมีหลักฐานยืนยันก่อนว่าเครื่องมือวัดทำงานถูกต้อง
- ตัวตรวจทุกตัวควรมีข้อมูลตัวอย่างที่รู้คำตอบอยู่แล้ว ทั้งกรณีที่ควรผ่านและควรตก
- ตัวแปรควบคุมต้องตรวจจริงในทุก run ไม่ใช่แค่ระบุไว้ในไฟล์ตั้งค่า
- ควรเก็บผลดิบทั้งหมด และออกแบบตัวตรวจให้คำนวณคะแนนซ้ำได้ เพราะอาจพบข้อบกพร่องหลังเก็บข้อมูลไปแล้ว
